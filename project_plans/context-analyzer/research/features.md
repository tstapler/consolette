# Research: Feature Landscape — context-analyzer

Scope: what already exists in consolette that overlaps with
manavgup/context-analyzer's dashboard views, what edge cases the design must
handle, and Tyler's unstated needs for this to actually get used.

## 1. What already exists in this codebase

### Transcript parsing / turn reconstruction — `src/claude_code_session/transcript.rs`

- [`parse_session_file`](../../../src/claude_code_session/transcript.rs#L158) streams `~/.claude/projects/**/*.jsonl` line-by-line, skip-and-warn on unparseable lines (`transcript.rs:176-186`) — the "log-and-skip malformed input" requirement is already the house style here, not something to invent.
- [`TranscriptRow`](../../../src/claude_code_session/transcript.rs#L63) is hand-rolled `Deserialize`/`Serialize` that round-trips every unknown JSON field via `RowFields::extra` (`transcript.rs:32-45`) — deliberately tolerant of transcript schema drift (`compactMetadata`'s `preservedSegment`/`preservedMessages` shape-mismatch regression at `native_compaction.rs:148-180` is the concrete precedent for why).
- [`build_turns`](../../../src/claude_code_session/transcript.rs#L248) reconstructs turns by walking `parentUuid` backward from the last row, with cycle detection (`transcript.rs:264-266`), dangling-parent tolerance (`transcript.rs:278-292`), and parallel-tool-row recovery (siblings sharing an assistant parent, `transcript.rs:298-309`). This is the turn model context-analyzer's "turns" table would need — but it's turn-*shape* reconstruction, not turn-*cost* attribution.
- **Sidechain (subagent) rows are explicitly excluded**, not tracked: `by_uuid` is built from non-sidechain rows only (`transcript.rs:249-254`), and a `parent_uuid` pointing at a sidechain row is treated as "dangling," starting a new chain (`transcript.rs:621-637` test). There is no subagent entity, no subagent-to-parent-session linkage, and no subagent token accounting anywhere in this module — confirmed by `grep -rn "sidechain|subagent" src` returning only this exclusion logic and an identical exclusion in `src/learn/transcript.rs:175-176` (a second, independent JSONL parser for correction-pattern mining — a second precedent for "these two things diverge if you're not careful," see §2).
- [`ChainCoverage`](../../../src/claude_code_session/transcript.rs#L404) quantifies how much of a transcript the active chain covers when there are disconnected conversation roots (repeat `--resume`/`--clear`) — directly reusable for a "some of this session's history is orphaned" indicator context-analyzer doesn't appear to have.

### Session discovery — `src/claude_code_session/discovery.rs`

- [`discover_sessions_glob`](../../../src/claude_code_session/discovery.rs#L74) globs `~/.claude/projects/**/*.jsonl`, stats each file, sorts by recency/size. No file-watching, no incremental/tailing read — every scan is a full re-parse from byte 0 (confirmed: `session_bi.rs`'s 15-minute refresh loop calls `build_session_bi_snapshot` → `parse_session_file` fresh each tick, `session_bi.rs:245-263,324-338`). No Codex CLI path (`~/.codex/sessions/`) is discovered anywhere — `grep -rn codex src/**/*.rs` returns zero matches. Codex ingestion is 100% new work, including figuring out its rollout-log schema from scratch (no vendored fixture, no doc reference in-repo).

### Session-level cost/compaction comparison — `src/claude_code_session/cost_compare.rs`, `session_bi.rs`

- [`compare_compaction_cost`](../../../src/claude_code_session/cost_compare.rs#L70) builds one `CompactionComparison` per session: a no-compaction cost estimate, native (Claude Code) vs. consolette compaction detection/metrics, and chain coverage.
- **Every token count here is `TiktokenEstimator`-derived (`cost_compare.rs:78,82`), never the transcript's own API-reported `usage.*` field.** `grep -rn "cache_read\|cache_creation\|usage\." src/claude_code_session` returns nothing — no code anywhere in `claude_code_session` reads `message.usage.{input_tokens,output_tokens,cache_read_input_tokens,cache_creation_input_tokens}` off an assistant row. This is the single largest gap against the requirement's "parsed for exact API token usage (input/output/cache_read/cache_creation)": today's whole session-cost pipeline is guess-based (tiktoken cl100k/o200k approximation), not ground-truth. context-analyzer's entire "60%+ Tool I/O" and "4.3x cost scaling" claims are built on API-reported counts, which this codebase doesn't parse at all yet.
- [`build_session_bi_snapshot`](../../../src/claude_code_session/session_bi.rs#L245) is the fleet-wide aggregator: bounded concurrency (16), per-file 5s timeout via `spawn_blocking` + `tokio::time::timeout` racing a `JoinHandle` (documented rationale at `session_bi.rs:206-237` — a hard lesson already learned about sync CPU work starving the timeout, worth reusing verbatim for context-analyzer's own per-file scan rather than re-deriving it), refreshed every 15 minutes (`session_bi.rs:29`, `SESSION_BI_REFRESH_INTERVAL`). This is architecturally the closest existing analog to context-analyzer's cross-session `/sessions` table — same "one row per session, best-effort, partial failures don't kill the batch" shape (`SessionBiSnapshot.parse_failures`, `session_bi.rs:96-103`).
- `SessionComparisonRow` (`session_bi.rs:70-84`) fields — `net_advantage_tokens`, `no_compaction_total_tokens`, `chain_coverage_ratio` — are all about compaction ROI, not context composition. There is no "peak context," no "cost/call," no "tool I/O vs conversation vs system" split anywhere in this struct.

### Existing dashboards — two, both distinct from what's being asked for

- `src/dashboard.rs` (`GET /dashboard`) is the **proxy-traffic** dashboard: RPM, provider status/cooldowns, duration histograms, event-loop lag, compression ratio, recent-requests table with a request-body inspection modal (`dashboard.rs:277-289` — a genuinely reusable UI pattern for context-analyzer's "message inspector"), `count_tokens` health. It reflects only traffic actually routed through consolette's proxy — a session run outside consolette (e.g. Claude Code talking directly to Anthropic) is invisible here. Chart.js via CDN (`dashboard.rs:20` `<script src="https://cdn.jsdelivr.net/...">`), not self-hosted.
- `src/cost_metrics/dashboard.html` (served at the *same* `/dashboard` route by `dashboard_router` in `cost_metrics/server.rs:195-198` — **note: `src/dashboard.rs`'s `handle_dashboard` and `cost_metrics/server.rs`'s inline `/dashboard` closure both claim that path; whichever router is `.merge()`d last or first registered wins, worth resolving during planning, not assuming one supersedes the other**) is the session-BI table: filterable/sortable by path/project substring and compaction status, backed by `GET /v1/dashboard/sessions`. Explicitly no-CDN (ADR-015, referenced at `cost_metrics/server.rs:43`) — the project already has a stated preference for self-contained dashboard assets, which context-analyzer's own dashboard (also self-hosted per its README) matches, but consolette's proxy dashboard (`dashboard.rs`) breaks that preference via jsdelivr CDN. New dashboard work should follow the no-CDN ADR-015 convention, not the CDN one.
- Neither dashboard has: a context-growth-per-turn chart, budget threshold lines (200K/500K/700K/1M), an autocompact line, a cache-read churn chart, a composition donut (Tool I/O/Conversation/System), a cost/call vs. peak-context scatter, or a message inspector with collapsible content blocks. All of context-analyzer's "Dashboard Features" section (composition, growth+budget, churn, cross-session scatter, message inspector) is net-new UI.

### Cost store — `src/cost_metrics/store.rs`, `types.rs`

- `SessionCostStore` is a `moka::future::Cache`, **in-memory only**, `max_capacity(1000)`, `time_to_live(1 hour)` (`store.rs:130-136`). This directly answers the requirements doc's open question ("reuse `cost_metrics::store` (currently in-memory) or a new persistent store?") — confirmed in-memory, TTL-evicted, capacity-bounded, with **no persistence layer at all** in this crate today (no sqlite/sled/postgres dependency found in the cost_metrics or claude_code_session modules). A persistent store for context-analyzer parity (sessions/calls/turns/hook-events/subagents surviving process restarts, as context-analyzer's SQLite does) is 100% new infrastructure, not an extension of an existing durable store.
- `CostRecord`/`TierTotals` (`store.rs:56-85`) track compaction-tier cost deltas (counterfactual vs. compacted vs. actual), keyed by `SessionKey` + `RequestId`. This is a different aggregation axis (per-compaction-run) than what a "per-call/per-turn composition" forensics feature needs (per-API-call token *composition*, independent of whether compaction ran).
- `RequestId`, `TokenCount`+`TokenSource` (`Exact` vs. `Estimated{via}`) (`types.rs:22-53`) — the `TokenSource` sum type already models "was this a real API number or an estimate," which is exactly the distinction needed to mark transcript-derived `usage.*` tokens as `Exact` vs. tiktoken-estimated ones as `Estimated` — reusable vocabulary, not reusable data.

### Hook infrastructure — a false friend, confirmed no-reuse

- `src/session_compaction/hooks.rs`'s `CompactHooks` trait (used by `CostTrackingHook` in `cost_metrics/hook.rs`) is an **in-process Rust trait** invoked by consolette's own compaction pipeline (`post_compact(&PostCompactContext)`), unrelated to Claude Code CLI's `~/.claude/settings.json` hook mechanism (shell commands run by the `claude` binary itself on `PostToolUse`/`SessionStart`/etc.). Requirements doc already flags this; confirmed by reading the code — no shared types, no shared install/uninstall logic.
- `grep -rn "settings.json" src/**/*.rs` returns **zero matches**. There is no existing settings.json read/write/backup code anywhere in consolette to build on. `src/main.rs`'s `Command` enum (`main.rs:21-Mcp,CompactSession,ServeCost...`) has no hook-install subcommand precedent either. This entire capability — idempotent, backed-up, reversible settings.json mutation mirroring context-analyzer's `context-tracker up`/`down` — is new from scratch.

### MCP surface — `src/claude_code_session/mcp_server.rs`, `src/mcp_gateway.rs`

- The existing `claude_code_session` MCP server exposes exactly one hand-written tool, `read_omitted_content` (`mcp_server.rs:1-13,82`), scoped by session_id + content_id against `OmissionCache`. No precedent for exposing dashboard/analytics data via MCP tools — that's the open requirements question ("dashboard-only for v1?") and there's no existing MCP tool shape in this codebase to model context-query tools on beyond this one narrow lookup.

## 2. Edge cases and failure modes the design must handle

- **Malformed/partial lines mid-session** — already solved at the row level (`parse_session_file` skip-and-warns per malformed JSON line, `transcript.rs:176-186`) but **not** at the turn or aggregation level for a forensics feature: a truncated final line (the classic "file being written to right now" case — see next bullet) drops silently with no signal to the dashboard that a session's data is incomplete. context-analyzer's ingestion needs to distinguish "genuinely malformed, log and move on" from "the writer just hasn't flushed the next line yet," which matters for a live/active session's dashboard view specifically (a truncated last line should not be reported as an anomaly, just as "wait for more data").
- **Sessions actively being written to by a live Claude Code process** — no file-watching or tailing exists anywhere in this codebase; `discover_sessions_glob` + `parse_session_file` always does a cold full-file re-read. For a "day-to-day useful" dashboard (see §3) this means either (a) accept up-to-15-minutes staleness (current `session_bi` refresh cadence) or (b) build genuine tailing/incremental parsing, which is new work with its own failure mode: reading a file whose last write is in-flight (partial JSON line, or an fsync not yet landed) — must not be misreported as corruption.
- **Sessions with subagents nested inside them** — `build_turns` currently *excludes* sidechain rows entirely from the reconstructed chain (`transcript.rs:249-254,621-637`). For context-analyzer parity ("SubagentStart/SubagentStop" tracking, `subagents`/`subagent_api_calls` tables), sidechain rows must become a first-class entity rather than being dropped — this is a structural change to (or a parallel path alongside) `build_turns`, not a config flag. Getting the parent-session ↔ subagent-session linkage right (Claude Code sidechains: same file? separate file? — needs empirical verification against real transcripts before design, per the requirements doc's own "undocumented, version-drifting" risk) is exactly the kind of schema-archaeology risk flagged in Rabbit Holes.
- **Compaction events splitting a session's context mid-stream** — already modeled at the boundary-detection level (`native_compaction.rs`'s `compact_boundary` rows, `boundary.rs`'s `consoletteCompact` markers), but a context-growth-per-turn chart needs to render the *discontinuity* itself (the autocompact line in context-analyzer's screenshot) — i.e., cumulative-token-count semantics must reset or annotate at each `compact_boundary`, not just detect that one occurred. `chain_coverage`'s "active chain only, dangling parents tolerated" behavior (`transcript.rs:393-421`) means a session with multiple compaction-triggered `--resume` cycles could have most of its real history invisible to any chart built naively on `build_turns` output alone — the growth chart needs the *whole* file's timeline, not just the active chain.
- **Codex CLI's session format differing structurally from Claude Code's** — confirmed zero existing code touches Codex; nothing in-repo constrains this. context-analyzer's own README hedges here too ("compaction/subagent depth remains Claude Code-only" for Codex) — a reasonable scope precedent: Codex ingestion for API-level token forensics only, not full parity, matching the Feasibility Risk already called out.
- **Two independent transcript parsers already diverging** — `src/learn/transcript.rs` and `src/claude_code_session/transcript.rs` both parse the same JSONL format independently (`is_sidechain` skip logic duplicated at `learn/transcript.rs:175-176` and `transcript.rs:249-254` with different downstream purposes). A third bespoke parser for context-analyzer functionality would be a third place for the transcript schema's undocumented quirks (the `preservedSegment` object-vs-number regression at `native_compaction.rs:148-156` is a concrete precedent for what goes wrong) to silently diverge. Whether context-analyzer's ingestion extends `claude_code_session::transcript` or forks it needs to be an explicit planning decision, not a default.
- **`/dashboard` route collision** — `src/dashboard.rs::handle_dashboard` and `cost_metrics/server.rs::dashboard_router`'s inline closure both register `GET /dashboard`. A third dashboard needs its own distinct route (e.g. `/dashboard/context` or a query param) — don't assume the existing route is free to repurpose.
- **Two-way check between transcript-derived and proxy-captured usage** (in scope per requirements — "transcripts primary") — the proxy's own recorded usage (`dashboard.rs`'s `recent_requests`, `cost_metrics`'s reconciled records) only exists for traffic actually routed through consolette; a session run directly against Anthropic/another proxy has no proxy-side data to cross-check against at all. The cross-check must degrade gracefully to "transcript-only, no proxy corroboration available" rather than assuming a proxy record always exists.

## 3. Tyler's unstated needs — what makes this get used, not shelved

Tyler has already built two dashboards for himself (`dashboard.rs`'s proxy metrics, `cost_metrics/dashboard.html`'s session BI table) and, per the requirements doc's own baseline framing, still doesn't have the answer to "where did my tokens go" — which is direct evidence that *having a dashboard* isn't what's been missing; something else is. Candidates a plan should account for, inferred from what's *already* built vs. what's *still* asked for:

- **One URL, not three.** He now has (or will have) three dashboards competing for the same `/dashboard`-shaped mental slot — proxy metrics, session BI, and this new one. If the new view isn't reachable from wherever he already looks first (or doesn't visually/navigationally unify with the existing two — a nav bar, a merged page, something), it becomes a fourth bookmark he stops opening, same as context-analyzer itself became "a second standalone tool" per the Baseline section. The success metric explicitly says "without leaving consolette" — worth holding the plan to *one entry point*, not just "hosted by consolette but still its own siloed page."
- **Exact numbers, because he already has estimates and didn't trust/use them.** The existing session-BI dashboard's whole token pipeline is tiktoken-estimated (§1) — Tyler built that, and the requirements doc is explicit that *this* feature must use exact API-reported `usage.*` fields instead. That's a signal he already judged the estimate-based number insufficiently trustworthy for the "where's my cost going" question, not just a scope note. Any temptation to reuse `TiktokenEstimator` output as a shortcut for the composition breakdown should be treated as reintroducing the thing he already rejected.
- **It has to work without hooks being installed**, or the value proposition regresses versus what he has today. context-analyzer's own README hedges this explicitly ("dashboard works without hooks" in its dev-setup section) — pure transcript ingestion (no settings.json mutation at all) should deliver composition/growth/cross-session/message-inspector value on its own; hooks should be additive (tool-call-level detail, subagent tracking) not a hard prerequisite. Given the Constraints section's anxiety about mutating a live shared settings.json, a design that lets him get most of the value *before* ever touching hooks reduces both risk and the activation-energy barrier to trying it.
- **Given the appetite is already flagged as possibly too large for "Large,"** the two dashboards he's already shipped (`dashboard.rs`, `cost_metrics/dashboard.html`) are proof he *will* finish and use a scoped dashboard, but the Rabbit Holes section is honest that 4 view groups × 2 CLIs × dual data source doesn't fit even a Large appetite. The single highest-leverage subset — given the Success Metrics section explicitly names only two things (top cost contributor per turn/call, and the turn/session that crossed a budget threshold) — is the composition breakdown plus the budget-threshold growth chart, for Claude Code + transcript-only (no hooks, no Codex, no headroom audit) first. That's the smallest slice that satisfies the stated Success Metrics verbatim; everything else in Scope is expansion room once that slice is proven to actually get opened day-to-day.
- **The headroom audit's Python dependency (`headroom-ai`) is a poor fit for a Rust-native tool he's building specifically to avoid a second-language/second-toolchain standalone system** (per the Baseline's own complaint about context-analyzer). Shelling out to a `pip install headroom-ai` dependency to reproduce `audit-headroom` reintroduces exactly the cross-language friction the Problem Statement is trying to escape — worth treating as an explicit deferred/cut candidate rather than a must-have-in-v1, unless a Rust-native approximation is feasible.
