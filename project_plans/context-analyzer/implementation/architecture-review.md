Originally: the plan changed these columns from `NOT NULL` to nullable in a Phase 3 task, but the plan's only migration mechanism (`CREATE TABLE IF NOT EXISTS`) cannot alter an existing table's constraints once Tyler has live Phase-1 data. **Verified fixed**: `cache_creation_input_tokens`/`cache_read_input_tokens` are now defined nullable `INTEGER` (no `NOT NULL`) directly in the Phase 1 `CREATE TABLE api_calls` statement in the Migration Plan SQL block (`project_plans/context-analyzer/implementation/plan.md:124-125`), and Story 1.2.1's own acceptance criteria assert this at schema-creation time (`plan.md:296-297`: "`api_calls.cache_creation_input_tokens`/`cache_read_input_tokens` are nullable `INTEGER` from this first schema, not `NOT NULL`" / AC checks `.schema api_calls` shows no `NOT NULL` on these columns). The Domain Glossary's `ApiCallRow` entry (`plan.md:44`) and Story 3.2.1 (`plan.md:627`) restate the same resolution consistently. No later story attempts an `ALTER`/constraint change on these columns. The blocker's root cause — a schema mechanism that can't loosen `NOT NULL` on an existing table — is fully addressed by getting the constraint right the first time it's ever created.

## Concerns

- [ ] **NEW — cross-session cost aggregation has no specified NULL-handling for the now-nullable cache columns (Story 2.1.1 / Task 2.1.1a)** — a direct side effect of the Blocker fix. Before the fix, `cache_creation_input_tokens`/`cache_read_input_tokens` were `NOT NULL`, so no query touching them ever needed to consider `NULL`. Now they are nullable from Phase 1 onward, but `GET /v1/context/sessions/summary` (`plan.md:503-504`) and its backing `summary_for_all_sessions` query (Task 2.1.1a, `plan.md:507-508`: "`GROUP BY session_id` aggregation over `api_calls`, joined against `PricingTable` cost calculation") are specified with no mention of `COALESCE`/`unwrap_or(0)` for these two columns, and the AC's worked example (`plan.md:504`) only ever exercises Claude Code calls, which always write a real value. This story ships in Phase 2, before Codex rows exist, so it will pass its own tests while quietly encoding an assumption the schema no longer guarantees. Once Phase 3 lands, `summary_for_all_sessions` scans the same `api_calls` table across both sources (the route returns "every stored session," not filtered by `source`) — if the per-row cost expression is plain SQL arithmetic (`cache_creation_input_tokens * cache_creation_usd_per_token`), SQLite's `NULL`-propagation rule means a `NULL` in either cache column makes the *entire row's* multiplication term `NULL`, and depending on how the terms are combined this can silently zero out or drop a Codex row's whole cost contribution (input + output too), not just its cache portion. If the cost calc instead happens in Rust from `Option<u64>` fields, the type system forces explicit handling — but the plan doesn't say which, and no task in Phase 3 revisits Story 2.1.1's query to add the missing-cache-field case.
  **Remediation**: Add an explicit note to Task 2.1.1a (or a Phase 3 follow-up task) that the cost-aggregation query must treat `NULL` cache columns as `0` for cost-summation purposes — e.g. `COALESCE(cache_creation_input_tokens, 0)` if done in SQL, or `.unwrap_or(0)` if the `ApiCallRow`/query-result Rust type carries `Option<u64>` for these fields — and add a test case with a mixed Claude Code + Codex (NULL-cache) session to Story 2.1.1's or Story 3.2.1's test list so this doesn't go unexercised until Tyler's real Codex data surfaces it.

- [ ] **CARRIED FORWARD, still open — `ContextForensicsStore` (Epics 1.2, 2.1, 2.2, 2.3, 3.2, 4.2, 5.2)** — single Repository spans 7 tables / at least 5 distinct aggregates (`sessions`+`turns`+`api_calls`+`native_compaction_events` as one session aggregate, plus independently-lifecycled `hook_events`, `subagents`, `proxy_cross_check`) with 20+ upsert/query methods accreted across all 5 phases. PoEAA's own rule cited in the Pattern Decisions table ("Repository... one per Aggregate Root") is not actually followed here — this is one Repository for at least three separable aggregate roots. The two precedents the plan cites for this pattern (`omission_cache.rs`, 265 lines / 1 table; `cmdcrush/metrics_store.rs`, 186 lines / 1 table) are both single-table stores an order of magnitude smaller than what's being proposed, so "mirrors the existing pattern" understates the scope difference.
  **Remediation**: Split into per-aggregate structs sharing one `Mutex<Connection>` (or one `Arc<Mutex<Connection>>` handle) — e.g., `SessionForensicsStore` (sessions/turns/api_calls/native_compaction_events, the one true aggregate with a real root), `HookEventStore`, `SubagentStore`, `CrossCheckStore` — rather than one struct accumulating all query methods. This can land incrementally: Phase 1 only needs the session-aggregate struct; split out the others as Phases 4–5 land rather than retrofitting later.

- [ ] **CARRIED FORWARD, still open — Domain Glossary: `SessionRow`/`TurnRow`/`ApiCallRow`/`HookEventRow`/`SubagentRow` id fields** — every id field (`session id`, `turn id`, `row_uuid`, `parent_session_id`, `parent_turn_id`) is implied to be a plain `String`/`&str`, with no newtype. The codebase already has an established precedent for exactly this: `session_compaction::session_state::SessionKey(pub String)` exists specifically to avoid raw-string session identifiers. Several store methods take multiple string ids as adjacent parameters (e.g. `upsert_api_call` needs `session_id`, `turn_id`, and `row_uuid` together; `SubagentRow` needs `parent_session_id` and `parent_turn_id` together) — exactly the "two primitives of the same type, easy to swap" shape the `type-driven-design` skill flags.
  **Remediation**: Introduce `SessionId`, `TurnId`, `RowUuid` newtypes (reusing or mirroring `SessionKey`'s shape) at the `context_forensics` module boundary, used in every store method signature and `*Row` struct field in place of bare `String`/`&str`.

- [ ] **CARRIED FORWARD, still open — JSON API / MCP response shapes (Stories 1.4.1, 2.1.1, 2.2.1, 2.3.1, 5.1.1)** — no response DTO types are specified; the acceptance criteria describe response shapes only as ad hoc JSON object literals (`{id, source, project, ...}`), and Story 5.1.1 requires the MCP tool result to match the HTTP route's JSON "byte-for-byte," implying both serialize the same underlying store `*Row`/query-result types directly. This is consistent with the existing `cost_metrics/server.rs` convention (`Json(report)` on a domain struct, verified at `src/cost_metrics/server.rs:180,211` — no separate DTO layer there either), so it isn't a new pattern being introduced, but the surface area here (5+ routes × row types, mirrored again in MCP tool results) is large enough that a later store-schema change (e.g., renaming a column, or the Blocker's fix above turning two `INTEGER NOT NULL` columns into `Option<u64>`) will silently change two independent wire formats at once.
  **Remediation**: Not a blocking change given existing-convention consistency, but worth naming a boundary explicitly rather than leaving it implicit: either (a) accept the coupling as a deliberate, documented trade-off (add one line to the module doc comment in `server.rs`/`mcp_server.rs` saying so), or (b) add thin `#[derive(Serialize)]` response structs distinct from the store's row types, so a store-internal rename doesn't need a synchronized edit in two presentation-layer files.

## Nitpicks

- `dashboard.html` accumulates chart/table/modal logic across all 5 phases (composition donut, growth+threshold chart, cross-session table+scatter, cache-churn bars, message inspector modal) into one file with no internal organization convention specified. This matches the deliberate zero-build-step, zero-dependency convention `research/build-vs-buy.md` §2 already justified, so it's not wrong, but by Phase 5 this file will likely exceed 1500 lines; consider naming a lightweight internal-section convention (e.g., a comment-delimited section per view) in an early task so it doesn't need retrofitting later.
- `ContextForensicsStore` is a concrete struct, not a trait/port, so `server.rs`/`ingest_*.rs` depend on a concrete type rather than an abstraction (a literal Dependency-Inversion read of SOLID's "D"). In practice this is mitigated by SQLite's cheap `:memory:` mode making real-DB tests as fast as mocks would be, and matches the codebase's own existing precedent (`OmissionCache` is likewise a concrete, non-trait struct) — flagged only as a nitpick, not a concern, since introducing a trait for a single-implementation local store would be speculative abstraction the `design-patterns` skill itself would flag as over-engineering.
