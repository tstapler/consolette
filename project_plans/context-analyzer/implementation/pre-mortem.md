# Pre-mortem: context-analyzer
**Date**: 2026-08-24

Both prior blockers (nullable-column migration bug, store-open fail-safety gap) are already fixed and verified — see `architecture-review.md`. This pre-mortem looks for failure modes those reviews did not already surface: architecture-review.md covered store/type-design and NULL-handling; adversarial-review.md covered settings.json write races, hook latency, and missing test coverage for live-tailing/UI/timing. The five below are new angles, weighted toward this project's two named risk concentrations — a live, shared `~/.claude/settings.json`, and a codebase where a transcript parser has already drifted from a sibling implementation once before.

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Phase 4 (hook install + hook-event ingestion) — the only piece that captures compaction events and subagent activity, both explicitly In Scope in requirements.md — never lands within the 3-6 week appetite, because Phase 1 alone already "satisfies both Success Metrics" and so gets treated as a natural stopping point under schedule pressure. The shipped feature quietly becomes the "extend only the proxy-based pipeline" alternative requirements.md explicitly rejected. | Tyler notices the dashboard has no subagent/compaction-hook data weeks after "shipping," and there is no `context-tracker up` command yet — the gap is discovered by absence, not by an error. | Add an explicit go/no-go checkpoint to plan.md after Phase 1 ships: either commit Phase 4 to a hard date within the appetite, or formally re-scope requirements.md's In-Scope list (hook capture) to Out of Scope / a follow-up, the same way the headroom audit was explicitly deferred via ADR-003. Silent scope-drift is the failure mode; an explicit, written re-scope is not. | P2 |
| 2 | `context-tracker up`'s array-append (ADR-002) is correct for *preserving* Tyler's existing hook entries (e.g., RTK's `PostToolUse` command-rewrite hook, or hooks the `update-config`/`fewer-permission-prompts` skills previously installed) but is never tested for *execution-order/interaction* with them — e.g., whether a pre-existing hook's exit code, stdout, or short-circuit behavior changes depending on whether consolette's entry runs before or after it in the same event array. This is a runtime-semantics risk on top of the write-race risk adversarial-review.md already flagged. | RTK command rewriting stops working, or an unrelated existing hook starts failing/timing out, immediately after running `context-tracker up` — with no error from consolette itself, since its own hook succeeds in isolation. | Add an acceptance criterion to Story 4.1.2 that `up` appends after existing entries (never prepends), and add a test that seeds a settings.json fixture with a real-shaped pre-existing hook (one that itself writes stdout / exits non-zero) both before and after `up` runs, asserting that entry's behavior and position are unaffected. Document array-order as a stated invariant in ADR-002, not just an implementation detail. | P1 |
| 3 | `classify_call_composition` (Story 1.3.1) is a hand-rolled, closed match/if-chain over today's known content-block types. When Claude Code ships a new content-block kind (new tool-result subtype, new `thinking`/`redacted_thinking` variant, etc.) sometime in the following weeks, tokens for that block silently fall into the wrong bucket (or the nearest default arm) instead of erroring — the dashboard keeps rendering a plausible-looking, quietly-wrong composition breakdown. This is the same failure class the prompt's "two transcript parsers already drifting apart" history names: a parser that stops matching upstream reality without ever failing loudly. | Composition percentages stop summing sensibly, or a new content type consistently inflates one category (often "System") after a Claude Code CLI update — noticed only by Tyler eyeballing numbers that "feel wrong," not by any error or test failure. | Give `classify_call_composition` an explicit fallback arm for unrecognized block types that logs `tracing::warn!` with the block's raw `type` field and accumulates it into a new `unclassified_tokens` counter on `CompositionBreakdown`, surfaced in the dashboard's numeric table (not silently folded into an existing category). Add a test asserting an unknown/synthetic block type increments `unclassified_tokens` rather than being absorbed. | P2 |
| 4 | The MCP tool `get_turn_content` (Story 5.1.1) exposes full raw conversation/tool-I/O content for *any* stored session, with no access-scoping beyond "the process that holds a `consolette mcp` connection." Unlike the dashboard, which the requirements' security classification implicitly scopes to "localhost, Tyler at the keyboard," the MCP surface is reachable by whatever other agent or automation Tyler has wired to consolette's MCP server (Tyler's own environment already runs multi-agent MCP orchestration) — a broader exposure surface than requirements.md's "store and dashboard must stay local" bullet actually analyzed, since it only discussed the store and dashboard, not the MCP tool surface added later in the plan. | An unrelated agent/session pulls raw content from a past, unrelated (possibly sensitive) Claude Code session via `get_turn_content` while doing something else, and that content later surfaces somewhere Tyler didn't intend (a Slack post, an artifact, another agent's context) — discovered after the fact, not at the point of exposure. | Add an acceptance criterion to Story 5.1.1 restricting `get_turn_content`/`get_session_composition` to sessions under the current project/cwd by default (matching how other consolette MCP tools are presumably scoped), or require an explicit opt-in flag per call for cross-session/cross-project reads; note the broader-than-dashboard exposure explicitly in the module doc comment so it isn't assumed to inherit the dashboard's implicit localhost-only threat model for free. | P3 |
| 5 | The `HookMarker` command string `up` writes into settings.json presumably resolves `consolette` via `PATH` (or a path baked in at install time). During weeks of active solo development the consolette binary gets rebuilt/reinstalled/moved repeatedly (debug build → release build, a later `cargo install`, a different machine per the dotfiles repo's Manjaro/macOS/WSL2 spread) — if the installed command ever stops resolving, hook-event ingestion silently stops while the rest of the dashboard (which doesn't depend on hooks) keeps rendering old data and looking healthy. | `hook_events`/`subagents` rows stop growing while Claude Code sessions keep happening — invisible unless Tyler specifically checks "most recent hook event timestamp" against "most recent transcript activity," which nothing in the plan computes or surfaces. | Add a staleness check to the dashboard (or a `context-tracker doctor` subcommand mentioned in ADR-002/Story 4.1.2): compare `MAX(hook_events.received_at)` against `MAX(sessions.last_ingested_at)` (evidence Claude Code was actually active) and show a banner when hooks appear installed but haven't fired despite recent transcript activity. | P2 |
