# Pre-mortem: anthropic-upstream-base-url
**Date**: 2026-09-25

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Story 3.1.1's acceptance criteria ask a test to assert `AnthropicProvider`'s private `base_url`/`is_default_endpoint` fields directly off `build_providers`'s return value, but `build_providers` returns `Vec<(String, Arc<dyn Provider>)>` — a trait object with no `as_any`/downcast support anywhere in `Provider` (`src/providers/mod.rs:155`) and no public getters on `AnthropicProvider`. As literally specified, that test cannot be written; it will either be silently descoped during implementation or replaced with a weaker check, leaving the actual trim+gate wiring in `router.rs:89-94` (Task 3.1.1b) with zero test coverage through its real call path — only Phase 4's tests exist, and those bypass `build_providers` entirely by calling `AnthropicProvider::new` directly with hand-supplied `base_url`/`is_default_endpoint` values. | A future refactor of `router.rs`'s `Anthropic` arm (e.g. swapping which value gets trimmed, or computing `is_default_endpoint` from the untrimmed string) passes CI green because no test exercises `build_providers` end-to-end for this variant, and the bug ships. Symptom in production: Bedrock-shaped model ids silently corrupted (or left uncorrupted) against the wrong endpoint, discovered only when a user reports "model not found" or "invalid model" errors from a custom relay or from the real Anthropic API. | Add a concrete task: either (a) give `AnthropicProvider` `pub(crate) fn base_url(&self) -> &str` / `is_default_endpoint(&self) -> bool` accessors and have the Story 3.1.1 test downcast (`Arc::downcast` needs `Any` — add `as_any(&self) -> &dyn std::any::Any` to `Provider`, or narrow the test to construct via `build_providers` and then make a real HTTP call to a mock server bound at the configured `base_url`, proving the wiring end-to-end without introspecting private state at all — this also happens to close finding #2 below in the same stroke. | P1 |
| 2 | Phase 4's mock-server tests (4.1.1b/c, 4.1.2a/b) all construct `AnthropicProvider` directly, hand-supplying `is_default_endpoint` and `base_url` as independent, uncoupled arguments — never through `build_providers`/`router.rs`'s trim-and-compare logic. So no test in the whole plan exercises the actual trim → compare → construct pipeline against a real network call; the trim/compare logic (Task 3.1.1b) and the request-honoring logic (Phase 4) are tested in isolation and never integrated. | Same root cause as #1: a bug in how `router.rs` computes/passes `is_default_endpoint` relative to the trimmed `base_url` (e.g. comparing before vs after trim, or trimming inconsistently) ships undetected because every test either hand-supplies both values in lockstep or checks the string comparison in isolation from the HTTP call. | Add one integration-shaped test that builds a real `Config` with a `base_url` pointed at a mock server (Task 4.1.1a's helper) via `references`-style TOML or a `Config` literal, runs it through `build_providers`, and asserts the resulting provider (found by name in the returned `Vec`) actually hits the mock server with the expected normalization behavior — using whichever accessor mechanism #1's fix adds. | P2 |
| 3 | `is_default_endpoint` is computed via a single exact-string comparison (`trimmed_base_url == default_anthropic_base_url()`) with no scheme/case normalization. An operator who writes `base_url = "https://API.anthropic.com"` (case typo) or `"http://api.anthropic.com"` (scheme typo) is still hitting the real Anthropic API in effect (DNS/TLS treat host case-insensitively; a corporate TLS-terminating proxy might even accept `http://`), but `is_default_endpoint` evaluates `false`, silently disabling Bedrock-id normalization against the real API. | Claude Code sends a Bedrock-shaped model id (`us.anthropic.claude-3-5-sonnet-20241022-v1:0`); the real Anthropic API rejects it with a 400 "model not found" error that didn't happen before this change, and the operator's `base_url` looks correct at a glance (only differs by case or scheme). | Document in validation.md/plan.md that `is_default_endpoint` is a byte-exact match, not a semantic "is this really api.anthropic.com" check, and note in the reference TOML comment (Task 5.1.1a) that the override must match the canonical default string exactly (including scheme/case) to retain normalization — or normalize case/scheme before comparing in `build_providers`. | P2 |
| 4 | `AnthropicCountTokensEstimator::new`'s Story 3.1.3 fix (`estimator.rs`) copies `base_url` straight out of `UpstreamKind::Anthropic { base_url }` with no trailing-slash trim, unlike `router.rs`'s Task 3.1.1b which trims. The two call sites deriving a base URL from the same config field now disagree on normalization, so the day someone wires this estimator into the live per-request path (explicitly anticipated by the plan's own rationale for Story 3.1.3), a `base_url` ending in `/` produces a double-slash URL in cost-estimation requests even though the equivalent `AnthropicProvider` path already closed that exact bug. | Once `AnthropicCountTokensEstimator::new` gets a real call site, requests to a `base_url` configured with a trailing slash 404 or error against the token-counting endpoint while the main chat path (via `AnthropicProvider`) works fine — a confusing, provider-specific-looking bug that's actually just missing trim reuse. | Extract the trim into a small shared helper (e.g. `fn normalized_anthropic_base_url(raw: &str) -> String` in `schema.rs`, called from both `router.rs::build_providers` and `estimator.rs::new`) instead of duplicating `trim_end_matches('/')` in only one of the two places touching this exact field. | P2 |
| 5 | The plan's prose describes the trailing-slash fix as "trim a trailing `/` once" / "trim exactly one trailing `/`" (Revision log item 7, Pattern Decisions row), but the actual code in Task 3.1.1b uses `base_url.trim_end_matches('/')`, which strips *all* trailing slashes, not just one. The behavior is actually correct for the `"https://host///"` multi-slash case (it fully normalizes), but the plan's own prose is wrong about what the code does — a reviewer or future maintainer reading only the prose (not the code block) could reasonably "fix" the code to match the prose by switching to a single-trim implementation (e.g. `if let Some(s) = base_url.strip_suffix('/') { s } else { &base_url }`), which would reintroduce exactly the multi-slash misclassification bug concern 7 was meant to close. | A future PR "fixing" the trim to match the documented "exactly one" behavior reintroduces the bug: `base_url = "https://api.anthropic.com//"` (double trailing slash) trims to `"https://api.anthropic.com/"`, fails the equality check against `default_anthropic_base_url()`, and `is_default_endpoint` becomes `false` again — silently disabling normalization, with no test catching it since no test in Phase 4 uses a multi-slash input. | Fix the prose to say "trim all trailing slashes via `trim_end_matches('/')`" (matching the code), and add one test case to Task 1.1.1c or Story 3.1.1 covering a multi-trailing-slash `base_url` (`"https://api.anthropic.com//"` or `"///"`) to lock the actual (correct) behavior in place, not just the single-slash case already covered. | P3 |

## P1 Items (address before implementation)
- [x] Failure #1 — **Fixed** in plan.md Revision log 2, item 8. Story 3.1.1's acceptance
  criteria now test a new pure function, `resolve_anthropic_endpoint(base_url: &str) -> (String,
  bool)`, directly (Task 3.1.1c, no `Provider` downcast needed), plus a new Story 4.1.3 /
  Task 4.1.3a end-to-end test that drives the real `build_providers` output through the
  `Provider` trait's public `send` method against a mock server — closing this exactly via the
  "end-to-end HTTP assertion reached through `build_providers`" option this row proposed.

## P2/P3 items (noted, not blocking — see plan.md Revision log 2 for disposition)
- [x] Failure #2 — **Substantially closed as a side effect**: the new Story 4.1.3 test (above)
  runs a trailing-slash `base_url` through both the trim/compare logic and a live mock-server
  request in the same test, which is what this finding asked for.
- [ ] Failure #3 — **Not fixed, accepted as a known limitation** (plan.md Revision log 2, item
  12): no scheme/case normalization on the `is_default_endpoint` comparison. Low likelihood,
  recoverable failure mode; follow-up if a real user hits it.
- [x] Failure #4 — **Fixed** in plan.md Revision log 2, item 10: `AnthropicCountTokensEstimator`'s
  Story 3.1.3 now reuses `resolve_anthropic_endpoint` (made `pub(crate)`) instead of copying
  `base_url` verbatim, so the two config-derived-`base_url` paths can't drift.
- [x] Failure #5 — **Fixed** in plan.md Revision log 2, item 9 (prose corrected to match the
  `trim_end_matches` code) and covered by one of Task 3.1.1c's three new unit tests
  (`resolve_anthropic_endpoint_should_trim_all_trailing_slashes_and_flag_a_custom_host`, which
  uses a triple-trailing-slash input specifically to lock in the multi-slash behavior this
  finding was worried about silently regressing).
