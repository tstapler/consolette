## Blockers (re-reviewed)

Both previously-BLOCKED items are **RESOLVED**. Full re-review detail below;
no new blockers were introduced by the repair.

**RESOLVED — Item 1: `openrouter`-kind upstream usable under `Fallback`/`Weighted`, bypassing cache population.** The plan now closes this both structurally and with a symmetric validation rule, matching the remediation this review originally proposed almost verbatim:
  - **(a) Structural fix**: cache population is now an invariant of `OpenrouterProvider::new()` itself, not of `Router::from_config`'s `OpenrouterScored` match arm. `new()` is built via `Arc::new_cyclic` and, per Task 2.1.2a/2.1.2b (plan.md:726-754), unconditionally awaits one eager `model_cache.refresh()` and spawns the `Weak`-ref background refresh task before returning — for *every* `openrouter`-kind upstream `build_providers` constructs, regardless of which `Strategy` (if any) later references it. Story 2.1.2's third acceptance criterion (plan.md:707-714) is an explicit Given-When-Then for exactly this: *given* a config with an `openrouter`-kind upstream referenced only by a `Strategy::Fallback` route (no `OpenrouterScored` route anywhere), *when* `build_providers` runs, *then* that upstream's cache is populated identically to the `OpenrouterScored` case.
  - **(b) Symmetric validation rule**: Story 4.3.1 (plan.md:1480-1573), specifically Task 4.3.1d, adds a validation pass run for *every* route (not just ones that reach the `OpenrouterScored` match arm) rejecting any route that references an `openrouter`-kind upstream under a `Strategy` other than `OpenrouterScored`, with a concrete Given-When-Then acceptance criterion covering three cases: `Fallback` + openrouter upstream → `Err` naming route and upstream; `Weighted` + openrouter upstream → `Err`; and a mixed-upstream `Fallback` route (openrouter upstream alongside a non-openrouter one) → still `Err` (plan.md:1508-1524).
  - Both halves are implemented as concrete tasks with acceptance tests (Task 2.1.2d, Task 4.3.1e), not just narrative acknowledgment. The Pattern Decisions table (plan.md:79) documents the "why" (population conditional on strategy choice → structural fix moves it into construction; validation rule is defense-in-depth on top, not instead of, the structural fix) — this is a real design change, not a sentence papering over the gap.

**RESOLVED — Item 2: free→paid mid-TTL produces a billed response nothing else catches.** The plan now implements a genuine two-part backstop plus explicit residual-risk disclosure, per ADR-001's Amendment (2026-09-05) and plan.md's Money-Safety Backstop subsection of Risk Control (plan.md:126-151):
  - **Cache stores `(id, price)` tuples, not bare ids**: `FreeModelEntry { id, price_prompt, price_completion }` replaces the original bare `Vec<String>` (Story 1.2.2, Story 2.1.1, ADR-001 Amendment mechanism 1). `OpenrouterProvider::send()`'s pre-flight check (Task 2.1.2c, plan.md:756-774) verifies the *specific selected model's* cached price is `(0.0, 0.0)`, not just that its id is present — a real code-level mechanism, with a unit test asserting zero mock-server calls when a cached entry has a nonzero price (Task 2.1.2d). The plan is honest that this alone is defense-in-depth against a filter bug, not a fix for the mid-TTL window itself (both ADR-001's Amendment and Task 2.1.2c's text say so explicitly).
  - **Nonzero-cost backstop**: Story 1.2.4 (plan.md:530-591) adds a post-hoc check in `send()`'s success path — if OpenRouter's response reports nonzero cost for a request dispatched to a nominally-free model, `send()` hard-invalidates the cache immediately (not waiting for TTL), sets `last_invalidation_reason`, and logs at `tracing::error!`. This is the actual mechanism that can catch a bill inside the TTL window, with concrete Given-When-Then acceptance criteria (plan.md:548-556) and a dedicated unit-test task (Task 1.2.4c).
  - **Genuine, honestly-flagged contingency**: whether this backstop is more than a documented no-op depends on Task 1.2.4a confirming OpenRouter's API actually exposes a per-request cost field — unconfirmed as of this plan and correctly listed as an Unresolved Question (plan.md:177-185), not silently assumed. Critically, the plan does not let this uncertainty stand in for a fix: if Task 1.2.4a finds no such field, plan.md's own text (Story 1.2.4's third acceptance criterion, plan.md:557-561, and the Risk Control section, plan.md:144-151) requires that finding be brought back to Tyler explicitly as a residual-risk sign-off decision, rather than silently shipped. This satisfies this review's original remediation's disjunction directly: a real detection layer was implemented (price tuples + cost-field check), *and* the residual risk (if the cost field turns out not to exist) is now explicitly surfaced in plan.md's own Risk Control section by name, not buried only in ADR-001's Context prose as before.
  - This is a materially different plan than "TTL bound with different words" — two concrete code mechanisms were added, one unconditional (price recheck) and one conditional on a fact the plan schedules itself to go verify first, with an explicit non-silent escalation path if that verification comes back negative.

## Concerns

- [ ] **Task 2.1.2a/2.1.2b (`Router::from_config`'s `OpenrouterScored` arm)** — SRP erosion: OpenRouter-specific bootstrap (locating the upstream index, awaiting an eager refresh, spawning and managing a `Weak`-ref background task) is inlined directly into the router's central, otherwise-generic assembly function. `from_config`'s job is to assemble generic router pieces (candidates, health, admission, strategy); knowing how to bootstrap one specific strategy's async lifecycle is a second responsibility bolted onto it.
  - **Recommendation**: extract Epic 2.1.2's eager-refresh + background-task-spawn logic into an associated async constructor on `OpenrouterScoringStrategy` (e.g. `OpenrouterScoringStrategy::build(provider: Arc<OpenrouterProvider>, index: usize, ...) -> Self`, itself calling `model_cache.refresh()` and spawning its own background task), so `from_config`'s `OpenrouterScored` match arm shrinks to roughly one call, matching how the other two strategies are one-liners in the same match.

- [x] **RESOLVED (verified in repair-loop re-check) — Story 3.1.2 / `research/architecture.md` §3.4 (`already_tried` widening) undocumented behavior change for non-OpenRouter model-pinned routes.** Task 3.1.2f (plan.md:1083-1101) adds `dispatch_should_not_poison_sibling_model_pin_at_same_index_for_fallback_strategy`, a `Fallback`/`Weighted` (deliberately non-OpenRouter) test with two `RouteUpstreamRef`s at the same index differing only in `model`, asserting a failure on one leaves the other selectable in the same `dispatch()` call — with a doc comment stating this is the intentional, disclosed side effect this Concern asked for, not a silent regression. Story 3.1.2's Acceptance Criteria (plan.md:1010-1027) also states the behavior-change rationale explicitly. This is the exact test/acceptance-criterion this Concern's recommendation asked for.

- [ ] **Story 4.2.2 (`select()` epsilon-greedy)** — the acceptance criteria require a statistically-asserted property ("A is picked in roughly 91% ± generous statistical margin... over 200 trials") built on Rust's global, unseeded `rand::thread_rng()`, with the plan's own task text deferring the fix ("use a generous margin / seeded RNG if determinism is needed for CI stability") to implementation time rather than making it now. This is a real CI-flakiness risk for a property meant to be a testable guarantee, and it's avoidable: the plan already uses an injectable-for-tests pattern elsewhere in this same design (`ModelListCache::new_with_ttl`, Task 2.1.1b, mirroring `SessionCostStore::new_with_ttl`'s precedent).
  - **Recommendation**: give `OpenrouterScoringStrategy` an injectable/seedable RNG (e.g. a `rng: Mutex<StdRng>` field with a `#[cfg(test)]` seeded constructor, matching the cache's own test-seam precedent) instead of a hardcoded `thread_rng()` call inside `select()`, and pin the statistical test to a fixed seed for deterministic CI runs.

- [ ] **Task 2.1.2a (single-upstream assumption) × Story 4.3.1 (validation)** — Task 2.1.2a describes locating "the route's Openrouter-kind upstream's index" in the singular, with no stated behavior if a route (or the config) contains more than one `openrouter`-kind upstream — plausible given nothing in the schema caps the count. Combined with the asymmetric-validation Blocker above, this is an under-specified edge case in the same validation pass.
  - **Recommendation**: fold a "reject more than one `openrouter`-kind upstream referenced by an `OpenrouterScored` route" check into Story 4.3.1's validation task, alongside the two checks already planned there.

## Nitpicks

- `src/providers/openrouter/models.rs`'s planned `fetch_models_raw()` (Task 1.2.2b) duplicates the GET-and-parse-JSON *shape* of `OpenaiProvider::fetch_models` (`src/providers/openai.rs:167-192`) rather than sharing it, unlike the plan's genuinely-reused Anthropic↔OpenAI translation functions (`crate::providers::translate_anthropic_request_to_openai`/`translate_openai_response_to_anthropic`, verified to be free functions at `providers::mod` level, not `OpenaiProvider`-only methods — so that reuse claim in Story 1.2.1's acceptance criteria holds up). The HTTP-shell duplication is low-risk and consistent with how Gemini/Bedrock already each carry their own fetch boilerplate, so not a required fix — just worth a one-line comment pointing at the parallel if a third near-identical copy ever appears.
- `warned_unranked: DashSet<String>` (Task 4.2.1c) has no stated GC, unlike `model_stats`, which Task 4.2.4b explicitly `retain`s against the current cache snapshot on every `expand_candidates` call. Likely immaterial (bounded by total distinct model ids ever seen by a single long-running process), but worth the same one-line `retain` for consistency with the project's own stated eviction convention if the churn assumption in `research/pitfalls.md` §5 (unbounded-cardinality discovered lists) is being taken seriously elsewhere.
- `UpstreamRef.model: Option<String>` and `UpstreamRef.name: String` are adjacent, same-typed (`String`) fields threaded through `record_outcome`/`expand_candidates`, with no newtype distinguishing "model id" from "upstream name" — the plan explicitly considered and rejected a `ModelId` newtype elsewhere (Pattern Decisions table) for good, stated reasons, so this is an already-adjudicated tradeoff, not a fresh gap; noted only for completeness.
