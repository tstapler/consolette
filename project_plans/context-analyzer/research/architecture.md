## 1. Integration points: new top-level module, depending on both existing modules — extending neither

**Recommendation**: `src/context_forensics/` (name TBD in Phase 3), a new sibling top-level module alongside `claude_code_session`, `cost_metrics`, `metrics`, `ratelimit`, `routing`. It *depends on* both existing modules for narrow, specific reuse; it does not extend either.

### Why not extend `src/claude_code_session/`

`claude_code_session/mod.rs:1-5`'s own doc comment scopes the module to "Claude Code session transcript compaction," citing ADR-008 for why it's a self-contained top-level module in the first place. Every file in it (`boundary.rs`, `cost_compare.rs`, `native_compaction.rs`, `session_bi.rs`, `prune.rs`, `summarize.rs`, `writer.rs`) serves consolette's own offline-compaction and session-BI-dashboard use case — parsing and *estimating*, never persisting to disk, never mutating `~/.claude/settings.json`, and never touching Codex CLI. Adding a rusqlite-backed persistent store, a settings.json installer, and a second CLI's ingestion path to this module would be three new responsibilities bolted onto a module whose name and doc comment promise one (Claude Code transcripts only, read-only, in-memory). Same reasoning the compaction-bi-dashboard research already applied when it kept `session_bi.rs`'s multi-session aggregation out of `cost_compare.rs` (single-session) — a difference of *scope*, not just size.

### Why not extend `src/cost_metrics/`

`cost_metrics/mod.rs:1-6`'s doc comment: "Per-session actual-vs-counterfactual token/cost accounting for `SessionCompactionPipeline`." That's a different domain than context-analyzer's: `cost_metrics` exists to answer "did consolette's own compaction pipeline save money on *this* request," keyed by `(SessionKey, RequestId)` inside `SessionCompactionPipeline::apply` (see the compaction-cost-metrics research doc's §1/§5). context-analyzer's domain is "where did *any* Claude Code or Codex session's context budget go," independent of whether consolette's compaction pipeline ever touched that session. `SessionCostStore` (`src/cost_metrics/store.rs:124-184`) is also the wrong *shape*: a `moka::future::Cache<SessionKey, Arc<RwLock<SessionCostState>>>` with `max_capacity(1000)` and `time_to_live(1hr)` (store.rs:131-134) — an in-memory, TTL-evicted cache scoped to a single process's lifetime. Requirements' Scope explicitly wants a "Persistent store... local disk only" surviving process restarts and supporting cross-session historical queries — the opposite NFR from `SessionCostStore`'s design, and a materially stronger requirement than compaction-bi-dashboard's own explicit "no new datastore, in-memory only, rebuilt on process restart" constraint (that doc, §3). Extending `SessionCostStore` to be both TTL-evicted *and* durable would fight its own cache semantics.

### What NOT to reuse — extract new instead

- **`providers::extract_usage`** (`src/providers/mod.rs:457-470`) only reads `usage.input_tokens`/`usage.output_tokens` from a *proxied Anthropic API response* — it has no `cache_creation_input_tokens`/`cache_read_input_tokens` fields at all, and it operates on a live HTTP response shape, not a transcript row. Verified directly against a real transcript (`~/.claude/projects/-home-tstapler-dotfiles/*.jsonl`, an assistant row's `message.usage`): real transcripts carry the full `{input_tokens, cache_creation_input_tokens, cache_read_input_tokens, output_tokens, cache_creation: {ephemeral_1h_input_tokens, ephemeral_5m_input_tokens}, ...}` shape. This feature needs a **new** extraction function, e.g. `context_forensics::ingest::extract_call_usage(row: &TranscriptRow) -> Option<CallUsage>`, reading `row.fields().message.get("usage")` directly (the whole `message` object is already captured verbatim as `Option<Value>` in `RowFields` per `transcript.rs:33-45`, so every usage sub-field — including ones this schema might add later — round-trips through `serde_json::Value` with no struct to keep in sync). This is the "exact API token usage (input/output/cache_read/cache_creation)" requirement, satisfied by a genuinely new, small function — not a gap in existing code, just an unclaimed one.
- **`claude_code_session::boundary`**'s `CompactionMetrics`/`is_compacted` — these are *consolette's own* compaction-marker convention (its own doc comment says so, `boundary.rs:1-8`), unrelated to Claude Code's native hook events this feature needs to capture (`PostToolUse`, `SessionStart`, etc., per context-analyzer's own hook list — see §3). Not reusable for hook-event capture at all; that's a new, orthogonal ingestion path (settings.json hooks invoking a consolette subcommand), with no transcript-parsing precedent in this codebase.
- **`session_compaction::hooks::CompactHooks`** — the requirements already state this explicitly (Constraints: "consolette's existing `session_compaction::hooks` is an in-process proxy-side hook trait, unrelated to Claude Code CLI's settings.json hooks — no reuse there"). Confirmed independently: `grep -rn "settings.json" src/` returns zero hits anywhere in the codebase — there is no existing settings.json read/write code of any kind to build on or collide with. This is genuinely new territory.
- **Codex CLI parsing** — `grep -rln "codex" src/ -i` returns zero hits. No existing code, no schema assumptions baked in anywhere. Confirmed Tyler has no local `~/.codex/sessions/` directory either (checked directly — path doesn't exist on this machine), so the Codex rollout-log schema can't be verified against real local data the way the Claude Code transcript schema was above; treat it as the higher-risk half of ingestion (see Feasibility Risks in requirements.md — "transcript schema drift" applies doubly here since there's no local fixture to validate against).

### Persistence backend: `rusqlite`, already a dependency, with two direct precedents

This resolves the requirements' open question ("Reuse `cost_metrics::store` or new persistent store — which backend?") concretely: **new store, `rusqlite`-backed**, not `moka` (moka is the right tool for the TTL in-memory cache `SessionCostStore` already is, and the wrong tool for data that must survive a process restart, which context-analyzer's Scope explicitly requires — see the §1 comparison above).

`rusqlite = { version = "0.40", features = ["bundled"] }` is already in `Cargo.toml:95` — no new dependency needed. Two existing modules already use it for exactly this shape of problem, both worth copying from directly:

1. **`claude_code_session::omission_cache::OmissionCache`** (`omission_cache.rs:36-38`): `Mutex<Connection>` (not moka), `CREATE TABLE IF NOT EXISTS` schema-on-open, WAL mode, and — notably — permission hardening (`omission_cache.rs:41-69`: `0700` on the parent directory, `0600` on the sqlite file, because "this cache stores raw, unredacted tool output, potentially including secrets"). context-analyzer's store will similarly hold raw tool I/O and conversation text, so the same hardening applies verbatim.
2. **`bin/cmdcrush/metrics_store::SqliteMetricsExporter`** (`metrics_store.rs:17-19, 45-69`): `Mutex<Connection>`, `CREATE TABLE IF NOT EXISTS`, WAL mode — a second, independent confirmation this is the established local pattern for "durable local metrics/event sink" in this codebase, not a one-off.

Recommended schema, adapted from context-analyzer's own (fetched from its README — see §3): tables `sessions`, `api_calls` (or `calls`), `turns`, `hook_events`, `subagents`, with a `source` discriminant column on `sessions` (see §2). Eight tables is context-analyzer's count (`sessions, api_calls, blocks, turns, hook_events, subagents, subagent_api_calls, tool_result_offloads`); consolette's version can start smaller and grow — the Scope's four dashboard view groups (composition, growth, cross-session, message inspector) plus cache-read-churn don't obviously need `blocks` or `tool_result_offloads` as separate tables on day one (offloaded/omitted tool output already has a precedent to reuse: `OmissionCache` itself, if that turns out to be needed).

## 2. Data flow, and where Codex diverges

```
transcript file (Claude Code .jsonl / Codex rollout log)
  -> discover_sessions[_glob] (existing, Claude Code only — Codex needs its own discovery fn)
  -> parse (existing parse_session_file for Claude Code; new parser for Codex)
  -> build_turns (existing, Claude Code; Codex's turn/call boundary shape unknown — new)
  -> per-call/per-turn extraction: composition split (Turn's existing user/assistant/tool_rows
     partition) + exact usage (new extract_call_usage) + native-compaction events (existing
     native_compaction.rs)
  -> upsert into rusqlite store (new), rows keyed by (session_id, source, call/turn id)
  -> dashboard query (new SQL aggregation functions, e.g. report_composition_for_session,
     report_growth_for_session, report_cross_session_table)
  -> JSON route (new, merged into serve-cost's router per §1) -> client-side chart render
     (same include_str!/fetch-and-render pattern as dashboard.html, cost_metrics/server.rs:41-45)
```

Hook events are a **separate, event-driven ingestion path** feeding the same store — see §3.

**Where Codex diverges — answer: same store schema with a `source` discriminant, not parallel pipelines merged only at the dashboard layer.** Concretely: a `source TEXT CHECK(source IN ('claude_code','codex'))` column on `sessions` (and denormalized onto `api_calls`/`turns` if query performance needs it), with two independent ingestion functions (`ingest_claude_code_session(path) -> Vec<ApiCallRow>` reusing `transcript::parse_session_file`/`build_turns`, and `ingest_codex_session(path) -> Vec<ApiCallRow>` with its own from-scratch parser) that both converge on one common `ApiCallRow`/`TurnRow` shape before insert.

Rationale: this is the same pattern `session_bi.rs` already uses for a structurally identical problem — `CompactionStatus::from_flags(native: bool, consolette: bool)` (`session_bi.rs:38-53`) treats "native vs. consolette compaction" as one discriminated sum type feeding one `SessionComparisonRow`, not two parallel row types merged at render time. Requirements' Scope explicitly wants cross-session analytics ("sortable table," "cost/call vs peak context... trends") spanning *both* CLIs in one view — a single `source`-discriminated table answers that with one SQL query (`GROUP BY`/`ORDER BY` across all rows, optionally `WHERE source = ?`); parallel pipelines merged only at the dashboard layer would push that merge logic into every handler that needs a cross-CLI view, duplicating it per query instead of once per schema.

The real Codex-specific risk isn't the store schema (settled above) — it's that the *rollout-log row shape* is unverified: no local `~/.codex/sessions/` fixture exists on this machine (see §1) and no code in this repo has ever parsed one. `ingest_codex_session` should be planned as its own spike/story with a real fixture obtained before implementation, separate from (and likely later than) the Claude Code ingestion path, which already has a verified-against-real-data schema (transcript.rs's existing parser plus the `usage` shape confirmed in §1).

## 3. Consistency requirements: batch/on-demand rescan, not live tailing — matches both context-analyzer's own design and consolette's existing precedent

Fetched context-analyzer's README architecture section directly. Key facts:

- **Ingestion model**: "batch ingestion on-demand," with "SQLite persistence stores session data for fast queries and cross-session analysis" and auto-ingest occurring "on first access" — i.e. not a live-tailing daemon watching files for appends. context-analyzer re-parses/upserts when a session is queried, not continuously.
- **Hook events captured**: `PostToolUse`, `PostToolUseFailure`, `PreCompact`, `PostCompact`, `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `SubagentStart`, `SubagentStop`, `InstructionsLoaded` — via hooks installed by `context-tracker up` into `~/.claude/settings.json`, described as "idempotent, backs up your settings first, and leaves any other hooks you have configured untouched," reversed by `context-tracker down`.
- **Store**: SQLite, 8 tables (`sessions, api_calls, blocks, turns, hook_events, subagents, subagent_api_calls, tool_result_offloads`).

**This is a two-track ingestion model, not one**, and consolette should mirror both tracks rather than trying to unify them into a single mechanism:

1. **Transcript-file ingestion (batch, periodic rescan)** — for the JSONL-file-derived data (composition, growth, native compaction, turns). Directly matches consolette's own existing, already-implemented precedent: `session_bi.rs`'s `spawn_session_bi_refresh_task` (a background task on a fixed interval, `SESSION_BI_REFRESH_INTERVAL = Duration::from_mins(15)` at `session_bi.rs:29`) plus an eager initial scan at process startup (`cost_metrics::server::CostServerState::build_with_session_glob`, `server.rs:115-121`, run *before* spawning the periodic task "so the very first `/dashboard` request after startup doesn't race an empty snapshot"). Because JSONL transcripts are append-only, a periodic re-glob-and-reparse naturally picks up a still-being-written live session on its next scan without needing true tailing — upserts into the rusqlite store should be idempotent (keyed by row uuid or `(session_id, call_index)`) so re-ingesting a growing file is safe. Given this is a personal tool with no freshness SLO (requirements' Non-functional Requirements: "Performance SLO: none — personal tool"), the existing `dashboard_router`'s watch-channel-plus-manual-refresh-endpoint idea from compaction-bi-dashboard's research (§3 there) is worth carrying over verbatim: periodic background rescan + an optional manual "refresh now" route, no websocket/live-update mechanism (matches Out of Scope's "no live-update mechanism" pattern already established for `session_bi`).

2. **Hook-event ingestion (event-driven, not polling)** — for `PostToolUse`/`SessionStart`/etc. This is inherently different: Claude Code's own process invokes a hook command synchronously as each event fires (that's what a settings.json hook *is* — a subprocess Claude Code spawns and waits on, per Claude Code's hook contract). The natural shape here is a small, fast `consolette context-hook <event-name>` subcommand (reads the hook payload from stdin, per Claude Code's hook JSON-over-stdin convention) that writes one row directly into the same rusqlite store and exits — no daemon, no polling, no tailing. This is a second, much simpler ingestion path than the transcript scan, and it's the one genuinely "live" component of the system — but "live" here means "invoked once per event by Claude Code itself," not "consolette watches a file."

Neither track requires a live-tailing daemon or a file-watcher (`notify`/`inotify`) dependency — confirmed this isn't needed by context-analyzer's own design choice ("batch ingestion on-demand," not tailing) and matches consolette's existing pattern (`session_bi`'s periodic-rescan, not a watcher). This should be called out explicitly to Phase 3: **no new dependency for file watching is needed**, only the existing `tokio::spawn` + interval pattern already proven in `session_bi.rs`, plus one new lightweight CLI subcommand for hook events.

## 4. Hook install/uninstall state — a small table, not a full Event-Command-Policy model

This is reporting/CRUD over existing read paths for the ingestion/dashboard side (per the task's own framing — no Event-Command-Policy table needed there). The one place with genuine multi-step state worth a small table is hook install/uninstall, since it's a two-state, backup-guarded, idempotent state machine — mirroring context-analyzer's own `up`/`down` design (§3 above) closely enough that the state machine itself can be copied conceptually:

| State | Command | Effect | Idempotency |
|---|---|---|---|
| `NotInstalled` | `up` | Back up `~/.claude/settings.json` (if not already backed up), merge new hook entries into existing `hooks` config without touching any hook Tyler already has configured, write the file back | If already `Installed`, `up` is a no-op (or re-verifies the hook entries are still present, self-healing if something else removed them) — never double-backs-up or double-inserts |
| `Installed` | `down` | Remove exactly the hook entries `up` added (not a blind restore-from-backup, which would also discard any *other* changes made to settings.json since `up` ran) | If already `NotInstalled`, `down` is a no-op |

The riskiest correctness property — "additive, backed up, reversible" (Constraints) — is best satisfied by `down` removing only the specific entries `up` added (tracked by a marker, e.g. a distinctive `source`/comment-equivalent field consolette's own entries carry) rather than restoring the whole file from the pre-`up` backup, since a naive restore would silently discard any unrelated settings.json edits Tyler made in between. This single design decision (targeted removal vs. whole-file restore) is worth flagging explicitly for Phase 3's task breakdown — it's the one place in this feature with real "what if this runs twice, or out of order" business logic, everything else is straightforward parse-store-query.
