# Pre-mortem: gemini-provider
**Date**: 2026-09-04

Scenario: it's early 2027. `UpstreamKind::Gemini` shipped (all three phases) months ago. It hasn't
delivered the value Tyler expected, or it broke in a way the plan didn't fully close. This document
imagines that failure and works backward.

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Google changes the Cloud Code Assist wire shape; `ResponseShapeMismatch`/cooldown fire correctly, but because the shipped example config uses `Strategy::Fallback` with Gemini listed last, every request silently and successfully falls back to Anthropic/Bedrock — the router "works," so nothing looks broken, and Tyler (checking the dashboard rarely, per single-operator usage) doesn't notice Gemini has been dead for weeks. | Dashboard shows `status-schema-drift` (violet) on the `gemini` row, but end-to-end request behavior is indistinguishable from normal — no user-visible error, no missed answers, just silent reversion to Claude/Bedrock. | Add a visible, cumulative counter (not just instantaneous status) of consecutive drift-cooldown trips over the last N days on the dashboard, and a `RELEASE.md`/runbook line stating explicitly that detection is by dashboard observation only (no push alerting exists) — so "check the gemini row periodically" becomes a documented operating habit, not an assumption. | P2 |

The Large-appetite (3-6 week) investment ships a feature that is technically correct but, by its own safest configuration, almost never executes in normal operation — so it never displaces Tyler's habit of opening the Antigravity IDE directly for deliberate Gemini use. | Weeks after shipping, `/metrics`'s per-upstream request counters show near-zero traffic on `gemini` even though the upstream reports healthy — not because it's broken, but because it's structurally never selected. | Before finalizing Story 1.8.1's example config, decide explicitly whether Fallback-last is really the intended day-to-day usage pattern or just the safe rollout default — if the actual goal is deliberate Gemini use (not just a safety net), pair the config with a documented per-session override workflow (`routing/session_overrides.rs` already exists for this) and set a concrete 2-4 week check-in on the real request-count metric to decide whether to shift weight toward Gemini or accept that the appetite bought a rarely-used safety net. | P2 |

## P1 Items (address before implementation)
- [x] **#2 (account suspension)** — addressed: Task 1.3.4c now logs a distinct message when
  `classify_gemini_error` returns `Auth` from a real Gemini HTTP 401/403 (server-rejected a
  locally-non-expired token, a suspension/revocation signal) versus Story 1.2.2's
  locally-detected-expiry message — see `plan.md` Task 1.3.4c.
- [x] **#3 (no refresh mechanism)** — addressed with a correction: this recommendation's literal
  prevention ("attempt the refresh-token grant directly against Google's OAuth endpoint") would
  require extracting a client_id from the `agy` binary, which is exactly the harvested-credential
  approach `requirements.md`'s Constraints section and ADR-001 already rule out — implementing it
  would resolve this pre-mortem finding by violating an already-deliberate, higher-priority
  decision. Instead, `plan.md`'s Risk Control now adds an explicit go/no-go checkpoint: run Phase
  1 for a week of real (including SSH) use and observe actual re-auth cadence before investing
  Phase 2/3's remaining budget, rather than discovering the cadence only after all three phases
  ship. This addresses the underlying risk (sinking the full appetite before knowing whether the
  auth story is workable) without reintroducing a rejected auth mechanism.

## Summary
2 P1, 3 P2, 0 P3.

Top failure mode: the plan detects and fails closed on expired tokens (Story 1.2.2) but never
implements or verifies a refresh path, and the pitfalls research already on file
(`antigravity-cli#57`) documents this exact tool forcing full interactive browser re-auth roughly
once per terminal session in headless/SSH environments — which is this machine's own normal usage
pattern — so the most likely near-term outcome isn't a dramatic outage but a Gemini upstream that
needs manual, interactive attention so often it stops being worth routing real traffic through.
