# Research: Features & Prior Art — openai-model-resolution

## 1. This repo's prior art

### `src/routing/family.rs` — "auto-model-family" (NOT on `main`; lives on the unmerged `feat/auto-model-family` branch, PR #18, commits `13a8a07`/`7f7aab1`/`5aa3059`)

Confirmed via `git branch -a` and `git merge-base --is-ancestor 5aa3059 HEAD` (false) — this file does not exist in the working tree (`find`/`Read` both fail on `src/routing/family.rs`); pulled via `git show 7c61443:src/routing/family.rs` (`7c61443` = the PR's merge commit into its own line, not `main`). Solves a *different* problem (cross-upstream health/latency selection among a config-declared, fixed member list) than this project (within-one-upstream discovery of an *unknown-in-advance* catalog via `/v1/models`), per requirements.md's Out-of-Scope note — but its **caching/invalidation/exclusion pattern is directly reusable**:

- **Layered exclusion, not a single boolean "is this model bad"**: `decide_route` (family.rs:495) composes multiple independent exclusion mechanisms with different scopes and different TTLs, then partitions the candidate pool into `under_cap` / `over_cap` / `bypassable`:
  - **Denylist** (member-scoped, ~1h TTL per the doc comment at family.rs:487) — fed *only* by `Validation(_, 404)` (never a raw 400) or `ModelUnsupported`. This is exactly this project's "deprecated model" signal.
  - **Index cooldown** (upstream-scoped) — fed by 429s; has a carve-out so a sibling model on the *same* upstream stays eligible when the cool is 429-driven and that specific member has no personal 429 mark ("shared-upstream-429 rule").
  - **Personal backpressure** (member-scoped, separate from denylist) — presumably concurrency/latency-based, not error-based.
  - Comment at family.rs:484-487 explicitly calls out the same race this project must handle: *"First request after a fresh delist still fails: providers map 404 to `ProviderError::Validation` and dispatch returns immediately on `is_validation` with no failover — that failure feeds the denylist, so requests N+1.. skip the dead ID until the TTL expires."* I.e., the first probe of a dead model is allowed to fail and surface to the caller; only the *next* request benefits from the exclusion. This project's design should decide up front whether a first-touch failure surfaces to the real caller (probably not acceptable per requirements' "recovers automatically... within N requests" — implies some in-band retry) or is absorbed by resolution logic before any client-visible response.
  - **`Unavailable { all_denylisted: bool }`** distinguishes "every candidate is a confirmed-dead 404" (surface a validation-flavored error, no bypass) from "everything is merely rate-limited" (error without retry, don't hammer a 429'd upstream) — a three-way outcome, not a binary fail/succeed. Directly analogous to this project's candidate-list-exhaustion case.
  - **`Bypass`** (family.rs:449) is a deliberate "serve something anyway" escape hatch when only *cooldown*-scoped exclusions apply (never for denylist/404), logged at WARN with a counter bump — the equivalent of this project's Observability Requirement ("all fallbacks dead" signal), but note family.rs treats denylist-exhaustion and cooldown-exhaustion as different severities, only bypassing the latter.
- **Ranking with hysteresis + exploration probe** (`FamilyResolver::rank`, family.rs:333; `serve_decision`, family.rs:579): the ranked pick is sticky (`runtime.last_pick(alias)` biases against needless churn — "cold" vs ranked-pick vs probe reasons are distinguished, `FamilyReason::{ColdDefault,RankedPick,Probe}`), and every `PROBE_EVERY_N` resolutions it deliberately samples a *non-pick* member to keep stats fresh on alternatives — this is the mechanism this project's "cache invalidated on failure, not blind TTL" requirement is gesturing at, but family.rs additionally re-validates *good* choices occasionally rather than only reacting to failure. Worth deciding whether this project wants a similar low-frequency reprobe of the incumbent (to catch e.g. a model coming back after transient issues) or purely failure-reactive invalidation as requirements.md specifies.
- **Rebuild-safe state**: `FamilyTable::drop_stale_keys` (family.rs:100) scope-clears denylist/exclusion state for members no longer present after a config hot-reload, so a stale exclusion on a member that's been reconfigured away can never resurface. Directly relevant: this project's cache is keyed by upstream+family; a config reload changing the family prefix should similarly invalidate rather than leak stale resolved-model state.
- **Where state lives**: `FamilyRuntime`, owned by `MetricsCollector`, outlives a `post_route` hot-swap; the `FamilyTable` itself is immutable and rebuilt each reload. This is the established pattern in this codebase for "mutable per-alias/per-member runtime state that survives config hot-reload but not process restart" — likely the right home (or a sibling of it) for this project's per-upstream resolved-model cache, rather than inventing a new state-lifecycle mechanism.

### `src/routing/session_overrides.rs` (on `main`, exists today)

Much simpler, but establishes the codebase's minimal in-memory-`Mutex<HashMap>` convention for ephemeral, per-process, non-persisted state (`SessionOverrideStore`, session_overrides.rs:26) — deliberately *not* persisted to disk since scope is "one session's lifetime," contrasted in its own doc comment with `runtime-overrides.toml`, which *is* meant to survive a restart. This project's per-upstream resolved-model cache is the same shape of decision: requirements.md says "resolution state is per-process" and doesn't ask for persistence, so the `Mutex<HashMap<UpstreamKey, ResolvedModel>>` pattern here (not `family.rs`'s heavier `MetricsCollector`-owned runtime) may be the simpler, sufficient precedent — `family.rs`'s extra machinery (hysteresis, probe cadence, paid-guard, concurrency-cap partition) solves problems (multi-member health ranking, free/paid isolation) this project doesn't have, per its Out-of-Scope section. Recommend borrowing the *exclusion-then-cache* shape from `family.rs` but the *lightweight storage* shape from `session_overrides.rs`.

## 2. Industry prior art

### LiteLLM (Router — retries/fallbacks/cooldowns)
- **Cooldown = circuit breaker, not deprecation detection**: a model is cooled down after crossing a failure-count threshold (`allowed_fails`, default 3 fails/minute) for a fixed duration (default 60s), then failure counter resets and it's retried. This is tuned for *transient* failures (rate limits, timeouts), not permanent deprecation — cooling down and later re-trying a genuinely-deprecated model wastes a request every cooldown cycle forever. Consolette's design must not blindly adopt this for the 404-deprecation case; it needs a longer-lived or non-expiring exclusion for confirmed-dead candidates, closer to `family.rs`'s member denylist (1h TTL, fed only by 404/`ModelUnsupported`) than to a generic error-count cooldown.
- **Retry exhaustion and fallback are coupled, and coupling them wrong is a known live bug**: [BerriAI/litellm#19985](https://github.com/BerriAI/litellm/issues/19985) reports fallback resetting the retry cycle instead of terminating, causing the same fallback model to be retried repeatedly rather than the retry budget being respected end-to-end. Direct lesson for this project: the candidate-list walk and any per-candidate retry policy must share one exhaustion budget, not two independently-resetting counters — otherwise a family with N candidates × M retries-each can multiply unexpectedly under sustained failure.
- **Fallback strategy varies by error class**: LiteLLM distinguishes context-window fallbacks, content-policy fallbacks, and general fallbacks — i.e. different failure *kinds* should route to different remediation, not just "next candidate." Reinforces requirements.md's Rabbit Hole about needing real error classification (deprecation vs. wrong-endpoint vs. transient) rather than a blanket "failed → next."

Source: [Reliability - Retries, Fallbacks | liteLLM](https://docs.litellm.ai/docs/completion/reliable_completions), [Fallbacks (Provider Failover) | liteLLM](https://docs.litellm.ai/docs/proxy/reliability), [Fallbacks and Retries | DeepWiki](https://deepwiki.com/BerriAI/litellm/7.1-fallbacks-and-retries), [Cooldown period for failing models | The Neural Base](https://theneuralbase.com/litellm/learn/advanced/cooldown-period-for-failing-models/), [litellm#19985](https://github.com/BerriAI/litellm/issues/19985).

### OpenRouter (provider routing + real-world 404/deprecation bug reports)
- OpenRouter's own docs: **a 404 is deliberately non-retryable at the transport layer** — it means "wrong slug, deprecated, or every backing provider is momentarily down," and OpenRouter's advice to *users* is "verify the exact model id... models get deprecated... pin to a current id or add a fallback" — i.e., OpenRouter pushes exactly this project's problem (deprecation-aware fallback) onto the *caller*, it does not solve it centrally. Confirms this is a real, unsolved-upstream gap this project is right to close at the consolette layer rather than expecting the OpenAI-compatible upstream to handle it.
- **Real bug pattern — 404 payload shape varies and breaks naive classifiers**: [openclaw#51571](https://github.com/openclaw/openclaw/issues/51571) — a JSON-wrapped 404 wasn't recognized as `model_not_found` because the classifier keyed on the literal string "not found" in the error text while the actual payload used different wording, so fallback silently never triggered and the same dead candidate kept getting retried. Directly validates requirements.md's Open Question about whether error classification should be a hardcoded code/type list or something more general — a purely string-matching classifier is fragile in practice; prefer matching on structured fields (HTTP status + a `type`/`code` field) over free-text message matching, and treat "the message changed" as an expected failure mode to test against.
- **Real bug pattern — deprecated *default* model shipped by an application**: [claude-mem PR #3662](https://github.com/thedotmack/claude-mem/pull/3662) — a tool shipped with a now-deprecated default model; the fix explicitly created a distinct `model_deprecated` error classification (never retried against the *same* model) and fell back to a different default *once*, while explicitly declining to fall back when already on the default (avoid infinite loop) or on a custom/unrecognized gateway (avoid assuming OpenRouter's model-id semantics apply). This "don't fall back when there's nowhere else defensible to go, and don't loop back onto yourself" logic maps directly onto this project's candidate-list-exhaustion case.
- **Real-world churn observation**: a developer building against OpenRouter's free tier found free models are "added, removed, rate-limited, or quietly replaced" continuously, producing 404s and 429s across multiple fallback candidates *in sequence* within one request — i.e. exhausting 2-3 candidates before finding a working one is normal, expected steady-state, not a rare edge case. This argues for the candidate list actually being tried breadth-first with cheap probes (as requirements.md's Rabbit Holes note) rather than assuming resolution is a rare cold-start-only event.

Source: [Provider Routing | OpenRouter](https://openrouter.ai/docs/guides/routing/provider-selection), [Fix OpenRouter 404 | manifest.build](https://manifest.build/errors/openrouter/404-model-not-found/), [openclaw#51571](https://github.com/openclaw/openclaw/issues/51571), [claude-mem PR #3662](https://github.com/thedotmack/claude-mem/pull/3662), [Free LLMs on OpenRouter Keep Going 404 | DEV Community](https://dev.to/josh_green_dev/free-llms-on-openrouter-keep-going-404-i-fixed-it-with-120-lines-of-python-43i1).

(Portkey was not separately researched in depth — time-boxed to the two most load-bearing comparators, LiteLLM for the OSS-proxy retry/cooldown-taxonomy angle and OpenRouter for the closest analog of *this exact* deprecation-discovery problem on OpenAI-compatible model catalogs. If a reviewer wants Portkey specifically, its public docs describe a similar conditional-routing/fallback config surface — same shape of prior art as LiteLLM's, not flagged as adding a new pattern.)

## 3. Edge cases and failure modes this design should handle

Synthesized from requirements.md's own Rabbit Holes/Feasibility Risks plus the prior art above:

1. **Partial candidate-list exhaustion mid-request vs. mid-resolution.** If candidate 1 fails with a classified-deprecated error, candidate 2 must be tried *before* any response reaches the caller for that request (per requirements.md's "recovers automatically... within N requests" framing, this project seems to intend in-request fallback, not just next-request cache invalidation — confirm in planning: does "N requests" mean N *client* requests, each individually probing one candidate and failing until the cache catches up, or one client request internally walking the whole list?). `family.rs`'s "first request after fresh delist still fails" behavior (family.rs:484) shows the alternative (surface failure once, exclude for next time) is a real, accepted design choice elsewhere in this codebase — worth deciding explicitly rather than defaulting into it.
2. **All candidates exhausted (family.rs's `Unavailable{all_denylisted}` case).** Needs a distinct terminal state from "one candidate temporarily down" — surfaced to the caller as an actionable error (not a generic 500), and per requirements.md's Observability Requirements, a log line/dashboard indicator distinct from routine per-attempt counters.
3. **Races between concurrent requests during re-resolution.** requirements.md's per-process cache with failure-triggered invalidation is a classic thundering-herd setup: if N concurrent requests are in-flight against the cached model when it starts failing, do all N independently discover the failure and each walk the candidate list (N× redundant probe traffic — real, billable, per the Rabbit Holes' "probing has real side effects" note), or does the first failure lock re-resolution while others wait/use the stale cache once more? `session_overrides.rs`'s `Mutex<HashMap>` is coarse enough to serialize this cheaply if the invalidation-and-reresolve path holds the lock across the whole walk — but that risks serializing all requests to that upstream behind one slow re-resolution. Needs an explicit decision (accept redundant probes across a bounded race window vs. single-flight re-resolution) rather than an accidental one.
4. **A model that works for text but not tool_use (or not streaming).** Requirements.md's success metric requires tool_use/streaming parity for whatever model resolution lands on — but resolution as scoped tries a *cheap probe* (minimal tokens, no tool calls, per Rabbit Holes) to decide "this candidate works," which by construction cannot observe a tool_use-specific or streaming-specific failure. A candidate could pass the probe, get cached, and then fail on the *next* real request that happens to use tools/streaming — which per the failure-triggered-invalidation model would then correctly evict it, but only after a client-visible failure on a capability the cheap probe never exercised. Worth flagging as an inherent limitation of "probe with one cheap shape, trust it for all shapes" rather than something the current scope actually solves; requirements.md doesn't ask for per-capability caching (one cache entry per upstream, not per upstream×capability), so this should be named as a known gap, not silently assumed away.
5. **`max_completion_tokens` vs `max_tokens` correctness interacting with resolution.** If the compatibility rule (Scope item 3) is itself probed-and-cached (per the Open Questions), it's a second axis of per-model state alongside "which model id is alive" — two probes/caches per candidate, or one combined probe that tests both at once during resolution's own candidate-selection attempts (cheaper, and this project's Rabbit Holes note already assumes resolution *is* real attempted requests, so a single attempt could validate both signals for free). Recommend the plan phase treat this as one combined cache entry (model id → {works, needs_max_completion_tokens}), not two independently-invalidated ones, to avoid the two caches drifting out of sync (e.g. re-resolving the model id but not re-checking the token-param rule, or vice versa).
6. **Deprecation-signal drift / string-matching fragility** (OpenRouter's openclaw#51571 lesson): classify on structured fields (HTTP status + OpenAI's `error.type`/`error.code`, e.g. `model_not_found`, `invalid_request_error` with a specific `code`) rather than substring-matching the human-readable `message`, since the upstream in this project's own motivating case already demonstrated an inconsistent signal (`shutdown_date: null` yet 400s at request time) — the classifier's job is exactly to not trust the catalog metadata and instead trust the structured error shape from a real attempt.
7. **Config hot-reload changing the family prefix or removing the field.** Per `family.rs`'s `drop_stale_keys` precedent, a reload that changes which models match a family (or removes `model_family`/`resolve` entirely, reverting to a static pin) must not leave a stale cached resolution pointing at a model no longer considered part of the family — cache keys should be invalidated on config reload, not just on failure.
8. **Retry-budget double-counting** (LiteLLM's #19985 lesson): if resolution's own candidate walk has retries *and* consolette's existing per-upstream/route retry or multi-upstream-fallback logic (`routes[].upstreams`) also wraps it, define one shared exhaustion budget up front rather than letting the two retry loops compound unboundedly.

## 4. Operators' unstated needs (beyond explicit requirements)

- **Visibility into *why* a particular model was chosen**, not just *that* resolution happened. requirements.md's Observability Requirements ask for a per-attempt success/failure counter and an all-candidates-exhausted signal, but an operator debugging "why is my route on gpt-5.1 and not gpt-5.2" wants a current-resolution-state view (comparable to `family.rs`'s dashboard card and `/metrics` family section, or this project's own per-upstream health display in `src/dashboard.rs`) showing: the active pin, when it was last (re-)resolved, why (cold start vs. failure-triggered), and which candidates were rejected and for what classified reason. Without this, "the feature is silently doing the wrong thing" (e.g. stuck on an older-than-necessary candidate because a newer one's probe hit a transient error that got misclassified as permanent) is invisible until a human notices unexpectedly-old behavior.
- **Ability to pin/exclude a specific candidate** — e.g. an operator who knows `gpt-5.2-codex` has a known regression for their use case wants to keep auto-resolution active for everything else in the family but exclude that one id, without reverting to a fully static pin (which would lose future auto-recovery). Not in requirements.md's scope; worth flagging in planning as a candidate cheap addition (a denylist entry in config, analogous to `family.rs`'s runtime denylist but operator-declared rather than failure-derived) or an explicit non-goal to state.
- **A way to force re-resolution without restarting the process** — since cache invalidation is failure-triggered, an operator who *knows* a new better candidate exists (e.g. after manually verifying `gpt-5.3-codex` now works) has no way to make consolette pick it up before the current cached choice happens to fail on its own. A manual "re-resolve now" trigger (admin endpoint, or reusing whatever mechanism triggers `post_route`/config hot-reload) is a plausible unstated need, mirroring how `family.rs`'s table rebuilds on `post_route` even though its runtime stats are otherwise sticky.
- **Confidence that probing itself is cheap and safe to enable widely** — since probing is real billable/logged traffic (Rabbit Holes), an operator turning this on for a new upstream wants some signal (dry-run, or a documented worst-case "at most K probe requests per family per hour" bound) before trusting it not to spam an unfamiliar or rate-limited upstream. Not explicit in requirements.md's Observability Requirements, which cover *attempt outcomes* but not *attempt volume/rate as a cost signal* the operator might want capped or alerted on.
