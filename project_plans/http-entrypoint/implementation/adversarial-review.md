# Adversarial Review: http-entrypoint

**Date**: 2026-08-21
**Verdict**: CONCERNS

## Blockers (original pass, both resolved — see Re-review below)

- [x] **`translate_and_record` is called with a signature it doesn't have (Story 3.1.1, Task 3.1.1.2).** The plan's handler code calls `translate_and_record(&state.cost_tracker, &session_key, request_id, &model, &json).await` — five arguments including a `model: &str`. The real function (`src/providers/mod.rs:335-340`) is `pub async fn translate_and_record(tracker: &CostTracker, session_key: &SessionKey, request_id: RequestId, anthropic: &serde_json::Value) -> serde_json::Value` — four arguments, no `model` parameter (it pulls `model` out of `anthropic.get("model")` itself), and it returns a plain `serde_json::Value`, not something the handler branches on for recording purposes (the recording already happened inside the call). As written, Task 3.1.1.2 will not compile. Fix the task text to match the real signature (drop the `model` argument, treat the return value as the OpenAI-shaped body directly) before Epic 3.1 starts.

- [x] **The 529/"exhausted failover" error mapping in Story 2.1.3 is not implementable against `Router::dispatch`'s actual return values.** The plan's acceptance criteria require `map_provider_error_anthropic` to map "`ProviderError::Timeout` or any exhausted-failover condition (all candidates unhealthy/exhausted)" to `529 overloaded_error`, while a separate acceptance criterion maps `ProviderError::Upstream{status, body}` to `(status, api_error)` for "an otherwise-unmapped status." But `Router::dispatch`'s actual exhaustion path (`src/routing/router.rs:113-116`) returns exactly `ProviderError::Upstream{status: 503, body: "no healthy upstreams available"}` — the same variant and shape a real upstream returning a genuine 503 would also produce via `AnthropicProvider`/`BedrockProvider`. There is no field on `ProviderError` that lets `map_provider_error_anthropic` tell these two cases apart, so the two acceptance criteria contradict each other for this exact case (503 vs. 529, api_error vs. overloaded_error). This needs a design decision before Story 2.1.3/3.1.2 are implemented — e.g. a dedicated `ProviderError::Exhausted` variant returned by `dispatch` instead of reusing `Upstream{503,..}`, or dropping the 529 special-case and accepting 503/api_error for both.

## Concerns

- [ ] **Cost data recorded by `consolette run` has no reachable query path.** `SessionCostStore` (`src/cost_metrics/store.rs:124-136`) is an in-memory-only `moka::Cache` with no persistence, and `EntrypointState::build` constructs a brand-new `CostTracker` local to the `consolette run` process. `serve-cost` (`Command::ServeCost`) is a *separate* CLI invocation/process with its own independently-constructed `CostTracker` (`src/cost_metrics/server.rs`) — the two never share state. Requirements.md states cost-metrics recording "doubles as the primary observability signal for request volume and outcome," but as planned a user running `consolette run` has no way to see that data: it isn't exposed on the new entrypoint router (Out of Scope explicitly excludes admin/metrics endpoints "beyond what already exists for serve-cost"), and `serve-cost` can't see it either. Recommend either sharing one `CostTracker`/`EntrypointState` across `run` and an in-process `serve-cost` mount, or explicitly documenting this as a known limitation before shipping, since it undercuts a stated success metric.
- [ ] **Two independent SSE-parsing implementations for the same wire format, in the same module.** `CostTrackingStream` (Task 2.2.1.2) hand-rolls scanning a raw byte buffer for `\n\n`-terminated frames and manually splitting `event:`/`data:` lines. `OpenAiStreamTranslator` (Story 3.2.1), which wraps `CostTrackingStream`'s own output one layer up, instead uses the already-a-dependency `eventsource_stream::Eventsource::eventsource()` for the identical job. Maintaining two SSE parsers for the same Anthropic SSE format is exactly the kind of "easy to get subtly wrong" logic requirements.md's own Rabbit Holes section calls out (framing edge cases, partial frames across poll boundaries). Recommend building `CostTrackingStream` on `eventsource_stream` too, or explicitly justifying the hand-rolled version (e.g. needing untouched raw-byte passthrough) in the plan.
- [ ] **`est_tokens` heuristic silently changes the behavior of an already-shipped, tested subsystem.** Task 2.1.1.2's `body.to_string().len() as u32 / 4` feeds directly into `Router::dispatch`'s `AdmissionControl::admit` call (ADR-004's rate limiter), which can `Shed` (reject) a request based on this number. No acceptance criteria bound its error tolerance, and nothing flags the risk that a crude heuristic could cause spurious throttling or blow through real per-minute token budgets for JSON-heavy/tool-call payloads. The plan is careful to flag `eventsource-stream 0.2` as an inherited pre-1.0 risk; this heuristic deserves the same explicit risk callout since it changes real behavior of existing, tested rate-limiting code.
- [ ] **Malformed/non-JSON request bodies aren't mapped to either wire format's error envelope.** Both handlers use axum's `Json<serde_json::Value>` extractor. On invalid JSON or a wrong `Content-Type`, axum's own default rejection response fires *before* the handler runs, in axum's own shape — not the Anthropic `{"type":"error",...}` or OpenAI `{"error":{...}}` envelopes Stories 2.1.3/3.1.2 build. Since those stories' explicit "so that" is "my SDK raises the correct typed exception instead of a generic parse failure," a malformed body (a routine real-world case: bad content-type, truncated request) is precisely the case left unhandled. No task adds a custom rejection type/handler for the `Json` extractor.
- [ ] **Judgment calls left in "Unresolved Questions" are already baked into testable acceptance criteria elsewhere.** The "warn and use the first route" default (feeding Story 1.1.2's acceptance criteria directly) and the exact OpenAI error `type`/`code` strings (feeding Story 3.1.2) are flagged as open questions for the feature owner / "whoever implements Phase 3" to confirm, yet the plan's acceptance criteria already assume specific answers. This is the SDD plan gate — these should be confirmed now, not carried as TODOs into Phase 5.

## Minors

- Task 1.2.3.2 introduces `serve_entrypoint_with_shutdown` for testability but never states explicitly that production `serve_entrypoint` becomes a thin wrapper over it — implied, but worth spelling out as the contract so a later refactor doesn't quietly diverge the two paths.
- Story 1.4.2's acceptance criteria phrase the loopback test as "proof the server never listens on a non-loopback interface," but the actual test only asserts `local_addr().ip() == 127.0.0.1` for the one hardcoded bind call — true and sufficient given the hardcoded octets, but the phrasing overclaims what a single assertion demonstrates versus what is guaranteed by code structure.
- Graceful shutdown (Story 1.2.3) isn't tested against a client holding an SSE stream open — axum's default `with_graceful_shutdown` waits for in-flight connections to finish rather than force-closing them, so a stalled/long-lived streaming client could delay `consolette run`'s Ctrl-C from actually exiting. Low risk for a single-user local tool, but worth a one-line note in the Observability/Risk section if not addressed.

## Re-review (iteration 2)

Scope: only the two blockers above. The 5 concerns and 3 minors from the 2026-08-21 pass were not re-litigated and remain outstanding (carried forward unchanged above).

### Blocker 1 — `translate_and_record` signature — RESOLVED

Read `src/providers/mod.rs:335-366` directly. The real signature is:

```rust
pub async fn translate_and_record(
    tracker: &crate::cost_metrics::tracker::CostTracker,
    session_key: &crate::session_compaction::SessionKey,
    request_id: crate::cost_metrics::types::RequestId,
    anthropic: &serde_json::Value,
) -> serde_json::Value
```

four args, no `model` parameter, returns the OpenAI-shaped `Value` directly. `plan.md`'s Story 3.1.1 acceptance criteria (line 563) and Task 3.1.1.2 (line 574-575) now call it as `translate_and_record(&state.cost_tracker, &session_key, request_id, &anthropic_json).await` — exactly four arguments, no `model` — and both explicitly annotate "no `model` parameter... it pulls `model` out of `anthropic_json.get("model")` internally... returns the OpenAI-shaped body directly." This matches the real function. **Resolved.**

### Blocker 2 — 529 vs 503 ambiguity — RESOLVED

(a) **Internal consistency**: Task 2.1.3.1 (new, under Story 2.1.3) adds `ProviderError::Exhausted` and changes `Router::dispatch`'s exhaustion fallback to return it. Story 2.1.3's acceptance criteria (lines 439-442) and Story 3.1.2's acceptance criteria (lines 595-597) both key off the same `Exhausted` variant, both cite Task 2.1.3.1 as the source, and Story 3.1.2's Files line (600) correctly states "relies on the `ProviderError::Exhausted` variant added in Story 2.1.3, Task 2.1.3.1 — no additional `src/providers`/`src/routing` change needed here" (avoiding a duplicate/conflicting second implementation). Task numbering is consistent — no orphaned or duplicate task IDs found.

(b) **Design soundness**: verified by reading `src/providers/mod.rs:32-46` (the current `ProviderError` enum, 7 variants, none of which distinguish exhaustion from a genuine upstream error) and `src/routing/router.rs:113-116` (the current fallback: `Err(last_error.unwrap_or(ProviderError::Upstream { status: 503, body: "no healthy upstreams available".to_string() }))`). Today this is genuinely indistinguishable from an `AnthropicProvider`/`BedrockProvider` returning a real `Upstream{503, body}`. Adding a unit variant `Exhausted` and changing this one call site to `Err(last_error.unwrap_or(ProviderError::Exhausted))` does make the two cases distinguishable by construction: after the change, `map_provider_error_anthropic`/`map_provider_error_openai` can `match` `Exhausted` → 529/overloaded_error (Anthropic) or 503/server_error (OpenAI) separately from `Upstream{status, body}` → `(status, api_error)`/`(status, server_error)`. This is implementable and unambiguous as designed.

(c) **Containment**: grepped `src/routing/router.rs` for other returns of `ProviderError::Upstream{503, ..}` or other exhaustion-shaped errors — the fallback at line 113 is the only synthesized `ProviderError` in the file; every other `Err` in `dispatch`'s loop (`Err(e) if e.is_validation() || e.is_auth() => return Err(e)`, `Err(e) if e.is_rate_limited() => { ...; last_error = Some(e); }`, `Err(e) => { last_error = Some(e); }`) is a `ProviderError` a `Provider::send` implementation already returned, not synthesized by `Router` itself — matching the plan's claim that this is the only return site needing a change. One adjacent detail not called out by the plan: `ProviderError::is_transient()` (`src/providers/mod.rs:86-91`) matches `Timeout | Upstream{..}` but not the new `Exhausted` variant. This does not break anything today — `is_transient()` is called only from that method's own unit tests (`src/providers/mod.rs:396,405,410,415`), never from `Router::dispatch`'s loop or from anywhere in `plan.md`'s stories — so the omission is inert for this plan's scope, not a hidden entanglement. Worth a one-line note if a later feature ever branches on `is_transient()` for retry/backoff logic, but it does not block this plan.

One citation-accuracy nit (not a blocker): the plan cites the fallback at `src/routing/router.rs:110-114`; the actual lines are 113-116 (three-line drift). Purely cosmetic — the code content quoted is exact.

**Verdict on scope**: both targeted blockers are RESOLVED as fixed. The plan's Exhausted-variant design is sound, self-consistent across Story 2.1.3/3.1.2, and as contained as claimed (one enum variant, one call-site change).
