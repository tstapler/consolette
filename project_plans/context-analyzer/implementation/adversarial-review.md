## Concerns

- [ ] **No test coverage for reading a transcript while Claude Code is actively appending to it.** `research/pitfalls.md` §1 explicitly flags this as needing "new test infrastructure (a background thread/task appending on a delay while the ingester polls) that doesn't exist anywhere in the repo yet" — but no task in Epic 1.3 (or Phase 3's Codex equivalent) adds it. The full-reparse-every-15-minutes design (Pattern Decisions) mitigates the specific "partial line permanently dropped" failure mode pitfalls.md worried about (a skipped partial line gets re-attempted whole on the next cycle), but the torn-read/EOF-ambiguity risk during a scan that races an active append is still real and untested either way.
  — **Recommendation**: add one live-tailing integration test per ingester (Claude Code, Codex) that appends to a fixture file on a delay while ingestion runs concurrently, asserting no panic and eventual consistency.

- [ ] **`SettingsJsonGateway`'s read-modify-write has no compare-and-swap against concurrent writers.** Story 4.1.1's atomic tmp-file+`rename()` write protects Claude Code (or llm-sync) from ever reading a *torn* file, but nothing checks whether `settings.json` changed between the gateway's `read()` and its later `write()`. If Claude Code or `stapler-scripts/llm-sync` writes to the file in that window — both explicitly named as candidate concurrent writers in `research/pitfalls.md` §3 and Unresolved Questions — `up`/`down`'s write silently clobbers that concurrent change based on a stale in-memory snapshot (a lost-update race, distinct from the torn-read case the plan does cover).
  — **Recommendation**: capture the file's mtime/hash at `read()` time and refuse to `write()` (or re-read-and-retry) if it changed, rather than blind overwrite.

- [ ] **No dry-run/preview mode for `context-tracker up`/`down`**, despite `research/pitfalls.md` §3 explicitly recommending one and requirements.md's Feasibility Risks calling this component out as having "blast radius beyond this feature." Tyler's first real invocation of `up` runs directly against his live, hand-edited `settings.json` with no preview step to catch a bad diff before it's written.
  — **Recommendation**: add a `--dry-run` flag to Story 4.1.2/4.1.3 that prints the diff without writing.

- [ ] **Hook-write vs. background-rescan lock contention is unaddressed.** `consolette context-hook` (Story 4.2.1) fires on *every* Claude Code tool call and writes to the same SQLite file, under the same WAL + 5-second `busy_timeout` (per the `omission_cache.rs` precedent this plan copies), as the 15-minute background rescan's bulk upserts (Story 1.3.3). SQLite WAL still serializes writers — if the rescan holds a write transaction when a hook fires, the hook call (and therefore the live tool call it's blocking on, per pitfalls.md's own warning about hook latency) can stall up to the busy_timeout. Nothing in the plan batches rescan writes into short transactions or otherwise bounds this, even though `research/pitfalls.md` §3 calls hook latency "the single biggest way this feature could make Tyler's actual daily driver feel slower."
  — **Recommendation**: keep rescan upsert transactions short (e.g., commit per session file, not per whole corpus) and/or give the hook-write path a much shorter busy_timeout with a "log and drop" fallback rather than blocking the tool call.

- [ ] **No mtime-based skip-if-unchanged check before re-parsing a session file each rescan cycle**, even though `SessionRow.last_ingested_at` is already in the Phase-1 schema and looks purpose-built for this. `session_bi.rs`'s precedent has the same full-reparse-every-cycle behavior, but that module only produces an in-memory display snapshot; this feature adds real SQLite upsert I/O per turn/call per file per cycle, so the cost compounds indefinitely as Tyler's historical corpus grows over months/years with no cap or skip logic.
  — **Recommendation**: compare each discovered file's mtime against the stored `last_ingested_at` and skip re-ingestion when unchanged.

- [ ] **UI acceptance criteria have no corresponding test tasks.** Every Task under Stories 1.4.2, 1.4.3, 2.1.2, 2.2.2, and 5.3.2 is implementation-only — arrow-key scrubber operability, `aria-live` announcements, sortable-column behavior, and click-through navigation are all stated as acceptance criteria but never given a browser-level verification task, unlike the store/route layers (which get explicit `Task ...: Tests` entries throughout Phases 1–5).
  — **Recommendation**: add at least a smoke-level Playwright/browser test task per dashboard story, or explicitly note manual verification as the accepted testing strategy for the HTML/JS layer.

- [ ] **Story 4.2.1's "timing test" (Task 4.2.1c) doesn't specify whether it measures real subprocess latency.** The actual risk `research/pitfalls.md` §3 names is process-spawn overhead (`consolette context-hook` is a fresh CLI invocation per tool call — fork/exec/binary-startup/SQLite-open), not in-process function speed. A typical Rust unit test calling the handler function directly would not catch that; the plan doesn't say the test instead shells out to the built binary.
  — **Recommendation**: make at least one test invoke the actual compiled `consolette context-hook` binary via `std::process::Command` and assert wall-clock latency, not just the in-process function.

## Minors

- Migration Plan's schema-by-phase table ("Phase 1 creates sessions/turns/api_calls/native_compaction_events. Phase 4 adds hook_events/subagents. Phase 5 adds proxy_cross_check.") omits the `message_json` column Task 2.2.1a adds to `api_calls` in Phase 2 — a small documentation gap worth fixing before implementation starts so schema evolution stays traceable.
- The MCP tool set (Phase 5, Story 5.1.1: 4 tools) doesn't expose cross-check status (`proxy_cross_check`/`CrossCheckStatus`, Phase 5.2), while nothing in Phase 5.3's dashboard stories explicitly surfaces it either — a minor surface-parity/coverage gap worth a one-line check when Phase 5 is implemented. (Re-review note: the subagent-spend half of this gap, as originally written, is now moot — per the ADR-004 scope-down above, neither the dashboard nor the MCP tools expose subagent spend in v1, so there's no parity gap on that axis anymore.)
- No data-retention/pruning policy is stated for `context-forensics.sqlite`, which duplicates raw conversation content already present in `~/.claude/projects/*.jsonl`/`~/.codex/sessions/`. For a tool meant to run indefinitely as a background daemon, this could grow unbounded over months/years with no stated cap or cleanup path — likely fine to defer, but worth a one-line acknowledgment.
- No scope drift found against requirements.md's Out of Scope list: no package-publishing work, no porting of context-analyzer's Python code/DB, no Windows-specific path handling, and the headroom/compression-ceiling audit is correctly absent from every phase (only referenced via ADR-003's deferral). All eight In Scope bullets map to a concrete epic/story.
