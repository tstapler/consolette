# Architecture Review: openai-model-resolution
**Date**: 2026-09-18 (Phase 3 re-review, iteration 2)
**Verdict**: CONCERNS

## Constitution Violations
- [ ] None — no ADR-000 found (checked `docs/adr/ADR-000-architecture-constitution.md`; `docs/adr/` does not exist in this repo).

## Blockers

- [x] **RESOLVED — Epic 2.2 (Story 2.2.1, Task 2.2.1c)**: the original blocker (`OpenaiProvider::new`-construction-time threading is structurally impossible, since `build_providers` builds one provider per `config.upstreams` entry before any route/`RouteUpstreamRef` is in scope) is closed by the plan's new Epic 1.3 ("Per-Request `model_family` Threading"). Verified against the real call chain, not just the plan prose:
  - **`UpstreamRef` widening (Story 1.3.1)** is the right place: `src/routing/strategy.rs:17-22` is a plain `#[derive(Debug, Clone, PartialEq)] struct` with a flat `index, name, weight, model` shape; adding a sibling `model_family: Option<String>` mirrors `model` exactly, and populating it at `router.rs:373-378` (the existing `candidates.push(UpstreamRef { .. model: route_upstream.model.clone() })` loop) is the same site `model` is populated at today. Sound.
  - **The dispatch-time mutation point (Story 1.3.2) is reachable and correctly ordered.** Confirmed by reading `Router::dispatch` directly: `chosen: UpstreamRef` is in scope from `self.strategy.select(&healthy)` at `router.rs:512`, and the `request_body` match block the plan targets (`router.rs:532-539`, mutating `body["model"]` when `chosen.model` is `Some`) runs *before* `provider.send(request_body, ..)` is called on `router.rs:541`. Adding a parallel branch that sets `request_body["__consolette_model_family"]` from `chosen.model_family` in that same block is a straightforward, independent addition — `provider.send` genuinely receives the mutated body, not a stale copy.
  - **The strip point (Story 1.3.3) is ordered correctly to prevent a leak, for the `OpenaiProvider` path.** `OpenaiProvider::send` (`src/providers/openai.rs:339-371`) receives `body: Value` as its first statement and only calls `super::translate_anthropic_request_to_openai(&body)` at line 354 — so an extract-and-strip step at the top of `send()` (as Task 1.3.3b specifies) runs strictly before the only place that body is forwarded/translated. No leak risk on this path as long as implementation preserves that ordering (a mechanical detail — `body` needs `mut`, not currently declared so — not a structural gap).
  - Net: the wiring mechanism itself is sound and matches the real dispatch path. This blocker is resolved.

- [x] **RESOLVED (iteration 3, applied directly to plan.md by the coordinator) — validation gap that let `model_family` leak to non-OpenAI upstreams' real HTTP bodies.** Story 1.2.2 (retitled "Reject configs that set both `model` and `model_family` (and neither), and reject `model_family` on non-OpenAI upstreams") now adds a third acceptance criterion and `ConfigError::ModelFamilyOnNonOpenaiUpstream { route, upstream, kind }` variant: any `RouteUpstreamRef` with `model_family: Some(_)` whose upstream `kind != Openai` is rejected at config-load time by `validate_model_selectors` (Task 1.2.2b), before it can ever reach `Router::dispatch`. Task 1.2.2c adds the corresponding test. This closes the gap at the same validation layer as the other two `model`/`model_family` checks, per the original remediation suggestion — no change to Epic 1.3's wiring mechanism itself was needed.

## Concerns

- [ ] **Story 1.2.1/1.2.2 (Domain Glossary: `model`/`model_family`)** — `model: Option<String>` and `model_family: Option<String>` as two independently-optional fields where "exactly one... may be set" is a textbook illegal-states-representable gap (type-driven-design skill's own canonical `Contact{Email: Option, Phone: Option}` example): the type system permits `{None, None}` and `{Some, Some}`, and both are only rejected by a separate runtime validation pass (Story 1.2.2's `validate_model_selectors`) that must be kept in sync by hand. The plan's own architecture.md §3.1 acknowledges this and defends it on the grounds that `RouteUpstreamRef` is a flat `#[serde(deny_unknown_fields)]` struct matching `model`'s existing precedent — a reasonable TOML-ergonomics tradeoff, but worth stating as a conscious "extend as-is, not refactor" choice in the plan itself (per the code-architecture-best-practices "never pick extend-as-is silently" rule) rather than only in architecture research.
  - **Recommendation**: Either accept explicitly in plan.md (one sentence) that this is a deliberate flat-struct/runtime-validation tradeoff consistent with existing `model` precedent, or consider a custom `Deserialize` producing an internal `enum ModelSelector { Pin(String), Family(String) }` immediately after deserialization so the "exactly one" invariant is enforced once, at the parse boundary, rather than by a separately-maintained validator that every future field addition to this struct must remember to extend.

- [ ] **Story 4.1.2 / Task 4.1.2a** — proposes adding an optional `token_param` parameter to `translate_anthropic_request_to_openai` (`src/providers/mod.rs:693`), but this function is not `OpenaiProvider`-private: it is also called from `OpenrouterProvider::send` (`src/providers/openrouter/mod.rs:605`), with its own existing test coverage (`src/providers/mod.rs:1703,1720,2379,2387`). Story 4.1.2's "Files" list (`src/providers/mod.rs` only) and Task 4.1.2a's (`src/providers/mod.rs`, `src/providers/openai.rs`) omit `src/providers/openrouter/mod.rs` entirely, understating the change's real blast radius — a signature change to a function shared by two unrelated providers for a feature scoped to one of them.
  - **Recommendation**: Do the `max_tokens`→`max_completion_tokens` substitution as a post-processing step inside `OpenaiProvider::send` on the `Value` the shared function already returns (`if let Some(TokenParamStyle::MaxCompletionTokens) = ... { rename the key }`), rather than widening the shared function's signature. This keeps `OpenrouterProvider`'s call site and its four existing tests byte-for-byte untouched, which is a more direct way to satisfy the "zero regression for non-opted-in upstreams" success metric than adding a parameter every non-OpenAI-resolution caller must pass as `None`.

- [ ] **Epic 2.3 (Story 2.3.2d) / Epic 6.1 (Story 6.1.2)** — Story 2.3.2d's test double needs "a fake OpenAI HTTP layer (probe-level, not full reqwest/TCP)," and the Dependency Visualization sequences the real HTTP-mocking test infrastructure (Epic 6.1) into Phase 6, *after* Phase 2's resolution-core stories that actually need it to write real acceptance tests. The plan also doesn't cite the harness already built for exactly this purpose in this repo: `src/cost_metrics/test_support.rs::MockServer` (a deliberate "no wiremock/mockito" bare-`TcpListener`+`axum` local server, explicitly built to avoid this class of gap and already reused by `src/cost_metrics/estimator.rs` and independently reinvented once more at `src/providers/openrouter/models.rs:127-215`). `OpenaiProvider::new` already takes `base_url: String` as a plain runtime parameter (confirmed via its own test helper at `src/providers/openai.rs:766-775`), so pointing it at a local `MockServer` instance requires no production-code changes — the seam already exists.
  - **Recommendation**: Pull `cost_metrics::test_support::MockServer` (or extract a shared version if it needs to move) into Phase 2's test stories now, rather than treating "which mocking pattern to use" as an open question to "verify... first" during Epic 6.1. This is the Reuse Check the code-architecture-best-practices skill calls out as the first thing to do before writing new test infrastructure, and skipping it risks two independently-reinvented local mock-server implementations for the same purpose (`openrouter/models.rs`'s is already the second copy of `cost_metrics`'s pattern) becoming three.

- [ ] **ADR-001 (`OpenaiProvider` scope growth)** — ADR-001 explicitly accepts that `OpenaiProvider` "gains responsibility beyond translate and forward one request" as the smaller cost versus a decorator's field-privacy friction. That tradeoff is reasonable, but the plan doesn't require any internal decomposition to keep the accreting responsibilities (chat/completions transport, Responses transport, candidate discovery/ranking, error classification, probe-and-walk resolution, single-flight guarding) separable — Epic 2.1-2.3's tasks read as a growing set of free functions and fields directly on `OpenaiProvider`'s impl block, in the same module that Epic 3.1 is simultaneously splitting specifically because one file was already doing too much for the *other* wire protocol.
  - **Recommendation**: Not a blocker, but worth a one-line plan addendum: consider grouping the resolution-specific state and methods (`ResolutionCache`, `SingleFlightGuard`, `filter_candidates`/`rank_candidates`/`classify_openai_error`/probe-and-walk loop) behind a small internal `struct ResolutionEngine` owned by `OpenaiProvider`, rather than as loose fields/functions — cheap now, and keeps `OpenaiProvider` itself closer to "transport + one delegated concern" than "transport + inlined resolution logic," matching the module-per-concern precedent Epic 3.1 is establishing for Responses API support.

## Nitpicks
- Story 2.3.3 only triggers cache invalidation on a `Deprecated`-classified failure of a real (non-probe) request against the cached model; a `WrongEndpoint` misclassification surviving into steady state (e.g. an endpoint choice made incorrectly during a race, or a model that becomes Responses-only after being cached as chat/completions) has no explicit real-request re-resolution trigger — likely caught eventually by the secondary TTL (Story 2.3.3's second criterion), but this isn't stated, only implied.
- Task 2.3.2c's per-candidate timeout carve-out doesn't mention that `OpenaiProvider`'s `reqwest::Client` bakes `read_timeout` in at construction (`src/providers/openai.rs:73-78`); the mechanism to apply a *shorter* timeout to just the probe requests within a resolution walk is `reqwest::RequestBuilder::timeout(..)` (a per-request override), not a second `Client` — worth a one-line implementation note so this isn't rediscovered mid-story.
