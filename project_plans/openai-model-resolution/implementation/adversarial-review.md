# Adversarial Review: openai-model-resolution

**Date**: 2026-09-18 (iteration 2 re-review)
**Verdict**: CONCERNS — all 5 prior blockers resolved. Remaining items are the pre-existing Concerns/Minors below (not re-litigated), unchanged.

## Blockers (iteration 2 re-review)

- [x] **No handling for `/v1/models` fetch failure during resolution.** Resolved by new Story 2.1.3 (`project_plans/openai-model-resolution/implementation/plan.md:338-350`). Acceptance criteria explicitly cover network error, non-200, and malformed/unparseable JSON, all treated identically to `Transient` from Story 2.3.2's walk: abort immediately, no cache mutation, feeds Story 2.2.3's backoff, surfaces as transient — never `Exhausted`. Task 2.1.3b requires a test for all three failure modes asserting no cache mutation and a transient error. Concrete, not just a summary claim.

- [x] **No backoff/negative-cache for repeated sequential resolution on a cold cache during outage.** Resolved by new Story 2.2.3 (`plan.md:400-417`). A per-family negative-cache entry records last-failure timestamp + error after an `Exhausted` or `fetch_models()` failure outcome; a default 30s backoff window short-circuits sequential requests with the recorded error and zero HTTP calls, verified via `tokio::time::pause()`/`advance()` tests for both "within window" (T+5s, fails fast) and "after window" (T+31s, re-attempts) cases (Task 2.2.3c). Acceptance criteria explicitly state this must be strictly better than today's static-pin fail-fast behavior, not worse — directly answers the concern.

- [x] **429/RateLimited-during-candidate-walk had no story/acceptance criterion/test.** Resolved: Story 2.3.2 (`plan.md:436-467`) now has an explicit acceptance criterion (4th bullet) stating a 429/`RateLimited` result from any candidate aborts immediately like `Transient` — never advances, never writes cache — and specifies the walk loop must check for `RateLimited` *before* calling `classify_openai_error` at all, closing the exact ambiguity flagged (silent misroute into `Other`/`Deprecated`). Task 2.3.2a codifies the check-order in the implementation task itself, and Task 2.3.2e is a dedicated test confirming zero advancement, zero cache write, and that `classify_openai_error` is never invoked for the 429 candidate.

- [x] **No inter-candidate probe spacing.** Resolved by new Story 2.3.5 (`plan.md:501-511`). Task 2.3.5a adds `tokio::time::sleep(Duration::from_secs(capability::EVAL_PROBE_SPACING_SECS))` between candidates in the walk loop, reusing the cited constant directly rather than duplicating its value. Verified in the codebase: `capability::EVAL_PROBE_SPACING_SECS` is a real, `pub` constant — `src/routing/capability.rs:44: pub const EVAL_PROBE_SPACING_SECS: u64 = 3;` — already used the same way at `capability.rs:235` (`tokio::time::sleep(Duration::from_secs(EVAL_PROBE_SPACING_SECS)).await`), so the plan's reuse is mechanically sound, not aspirational. Task 2.3.5b requires a `pause()`/`advance()`-based test, not a flaky real-time assertion.

- [x] **Single-flight guard had no release-on-panic/cancellation path.** Resolved by rewritten Story 2.2.2 (`plan.md:374-398`). `SingleFlightPermit` is now specified as an RAII wrapper (Task 2.2.2a) whose `Drop` impl unconditionally clears the flag and calls `Notify::notify_waiters()` "regardless of how the holder's scope exits" (Task 2.2.2b) — covering early return, `?`-propagated error, and panic-unwind. The bounded-wait-then-stale-or-propagate policy for concurrent callers (`min(remaining request budget, 5s ceiling)`, then re-check cache, else propagate transient error) is now decided in the plan itself, not deferred to implementation. Task 2.2.2e is a dedicated panic/early-return release test. The plan's own acceptance criteria (`plan.md:382`) note the RAII-release claim depends on unwind (not abort) semantics and cite this explicitly ("this crate does not set `panic = "abort"` in `Cargo.toml` — verified, so `Drop` runs") — confirmed against the real `Cargo.toml`: no `[profile.*]` section anywhere sets `panic = "abort"` (only `[profile.dist]` exists, setting `inherits = "release"` and `lto = "thin"`), so the crate uses Rust's default unwind panic strategy and the Drop-runs-on-panic assumption holds.

All 5 blockers are resolved with concrete plan text (stories, tasks, acceptance criteria with Given/When/Then, and named tests), not summary-only claims, and the two codebase facts the fixes depend on (`EVAL_PROBE_SPACING_SECS` existing as `pub`, and unwind — not abort — panic semantics) are verified true in the current repo.

## Concerns

- [ ] **Resolution logic isn't actually split out of `openai/mod.rs`.** The plan justifies splitting `responses.rs` out on architectural grounds ("two structurally incompatible wire protocols... would make this worse" — Tech Debt Disposition), but leaves candidate ranking, the resolution cache, the single-flight guard, error classification, and the probe-walk loop all inside `openai/mod.rs` alongside existing HTTP transport/header-building code. By the plan's own stated logic (isolate structurally distinct concerns into their own module), this is inconsistent — `openai/mod.rs` ends the project larger and more mixed-concern than before, not less. — Consider a `openai/resolution.rs` module for Epics 1.1/2.1/2.2/2.3/4.1's logic.

- [ ] **Story 2.3.4's verification gate has an escape hatch that could ship the exact regression pitfalls.md calls "the single most important thing to guard."** If the before/after `HealthRegistry` test fails (i.e., resolution failures *do* leak into cross-upstream health state), Task 2.3.4b says to "file it as a finding," not block. Given pitfalls.md explicitly names this as the top risk, a failing result here should block ship, not just get logged as a note for later. — Escalate: if 2.3.4's test fails, this should gate Phase 2 completion, not just get documented.

- [ ] **Single-flight design decision deferred to implementation ("Task 2.2.2b's decision").** Whether concurrent callers wait for the in-flight resolution or fall back to attempting a stale/no cached model is a real behavioral and latency tradeoff (blocking vs. best-effort), not a mechanical detail — it affects tail latency and the possibility of two different requests getting two different models mid-transition. Leaving it as "decided during implementation" for something this consequential risks an under-considered choice made under time pressure with no review. — Resolve this in the plan (pick one, state the tradeoff), not at implementation time.

- [ ] **`thinking` block `signature` field strategy ("placeholder/opaque passthrough token... decided during implementation") is deferred without flagging the compatibility risk.** If any downstream consumer treats the `signature` as meaningful (verification, replay-to-Anthropic-proper, etc.) rather than fully opaque, a fabricated placeholder could silently produce wrong behavior that's hard to detect since nothing on the wire visibly fails. — Confirm during Phase 2 research/implementation kickoff whether any known client validates this field before treating "any non-empty string" as sufficient, and note the finding either way.

- [ ] **Per-probe timeout carve-out (Task 2.3.2c: `request_timeout_secs / candidate_count`, floor at 10s) has no ceiling protection and no test for the large-candidate-list case.** A family with many candidates could produce very small per-probe timeouts (bounded only by the floor), causing spurious timeout-based `Transient` results on a slow-but-healthy upstream during the very first (cold-cache) resolution — ironically the highest-stakes moment for this feature to work. — Add a floor *and* a sanity check on realistic candidate-list sizes (2-5 in practice per requirements.md's own examples), or explicitly bound `candidate_count` in the divisor.

- [ ] **`ResolutionCache`/`SingleFlightGuard` keyed only by family string, not by upstream+family.** Two different upstreams (or two different routes pointing at the same upstream name under different auth) that happen to configure the same `model_family` string would collide in the same process-global cache/guard keyspace unless the key is composite. The plan's Domain Glossary says the cache is "owned by `OpenaiProvider`" (implying one instance per upstream, so this may already be safe), but this isn't stated as an explicit invariant or tested. — Confirm and state explicitly that `OpenaiProvider` instances are per-upstream (not shared/pooled) so the bare-string key is safe, or key by `(upstream_name, family)`.

- [ ] **Interim fixture fallback in Story 6.1.2 undermines its own stated purpose.** Task 6.1.2a allows falling back to "OpenAI's own publicly documented example transcripts" if real Model Gateway capture is unavailable — but the entire point of this story (per pitfalls.md §5) is that hand-written/vendor-generic fixtures miss the real gateway's quirks (the same class of gap that produced this project's original trigger bug: `shutdown_date: null` being unreliable was only found by hitting the real thing). A generic OpenAI example transcript is not meaningfully different from a hand-written one for this purpose. — If the interim fallback is used, flag it loudly as a known gap in the PR/ship notes, not just an implementation-time footnote.

## Minors

- No story validates the case where a `RouteUpstreamRef` sets **neither** `model` nor `model_family` for a `kind = "openai"` upstream — likely already an existing validation error, but not explicitly cross-checked against the new mutual-exclusivity story.
- `resolution_attempts: DashMap<(String, String, String, String), AtomicU64>` (Story 5.1.1) is an unbounded-cardinality key (arbitrary candidate model ids over time); fine at current scale (NFR says single local daemon) but worth a one-line note if candidate churn is high over a long-running process's lifetime.
- Story 6.2.1's docs task list has no acceptance criterion tying it back to the ExampleCorp-plugin follow-up's actual field name — low risk since it's out-of-repo, but a naming mismatch between this repo's `model_family` and whatever the `ndotfiles` PR ends up calling it would only surface at that later PR's review.
