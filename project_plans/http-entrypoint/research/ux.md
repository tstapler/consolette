# UX Research: HTTP Entrypoint

**Scope note up front**: consolette's HTTP entrypoint has no rendered UI and no human end user interacting with a screen. The "UX" here is entirely API-consumer ergonomics — how well the wire contract, error shapes, and process behavior match what an existing Anthropic/OpenAI-compatible client (Claude Code, an SDK, curl) already expects. That reframing is deliberate and holds for all five questions below.

## 1. Comparable local-proxy patterns

Four tools solve close variants of "bind a local port, speak a known API dialect, forward to real upstreams," and the patterns that work converge on the same handful of ideas:

- **Ollama** (`OLLAMA_HOST`, default `127.0.0.1:11434`): the entire interaction model is "point your existing tool's base URL at me." It ships both its native API *and* an OpenAI-compatible shim at `/v1/chat/completions` so tools built for either ecosystem work unmodified. No auth by default (loopback-only trust model). Errors are plain JSON `{"error": "..."}` with a conventional HTTP status — minimal but consistent, and every error is one `.error` field away, which is what makes it trivial for client libraries to surface upstream.
- **LM Studio's local server**: same "OpenAI-compatible drop-in" positioning, explicitly documented as "point your OpenAI SDK's `base_url` here." Its value proposition is zero client-side code change — the base URL is the entire integration surface. This is the same shape consolette is going for with Claude Code.
- **litellm proxy**: the most directly analogous tool — a local/self-hosted gateway that fans out to many upstream providers behind one Anthropic- or OpenAI-shaped endpoint, with routing/failover/cost-tracking, which is nearly consolette's exact feature set. Its documented lessons: (a) it deliberately mirrors the *exact* upstream error JSON shape per provider family rather than inventing its own envelope, because client SDKs pattern-match on that shape; (b) it exposes `/v1/models` so clients and health-checks can introspect what's routable without a real inference call; (b) streaming failures are surfaced as an SSE `error` event rather than silently closing the connection, matching what this project's own ADR-003 rabbit-hole already anticipates.
- **claude-code-router**: purpose-built for exactly consolette's primary consumer (Claude Code itself) — it intercepts Claude Code's Anthropic-shaped requests and re-routes them to other backends. The lesson that transfers directly: Claude Code is a specific, inspectable client with specific expectations (it retries on some status codes, treats others as terminal, and has particular tolerance for stream interruption) — testing against the real Claude Code binary (not just a hand-rolled curl/SSE client) is the highest-value validation available, because it's the actual target consumer named in the requirements doc.

**Convergent pattern across all four**: bind loopback by default, support the exact wire format of a real, widely-adopted API (don't invent a new one), make the base-URL swap the entire integration step, and treat "does the real client tool work unmodified" as the acceptance test — not "does my hand-written test client work." consolette's requirements doc already encodes this instinct (dispatch through the same `Router::dispatch` regardless of entry format), so this is a validation of direction rather than a new finding.

## 2. What a "drop-in" compatible endpoint must get right

For a client (SDK or Claude Code itself) to treat consolette as interchangeable with the real API, three things must match at the wire level, listed by how loudly they fail if wrong:

- **Error response body shape** — Anthropic's real API returns `{"type": "error", "error": {"type": "<error_type>", "message": "..."}}` with matching HTTP status (400 invalid_request_error, 401 authentication_error, 403 permission_error, 404 not_found_error, 429 rate_limit_error, 500/529 api_error/overloaded_error). OpenAI's shape is `{"error": {"message": "...", "type": "...", "param": ..., "code": ...}}`. Client SDKs (including Anthropic's own) parse these fields to decide retry behavior and to construct typed exceptions — a mismatched shape means the SDK throws a generic/opaque error instead of the specific exception type the caller's code may already be catching (e.g. `anthropic.RateLimitError`). This is the single highest-leverage compatibility detail: get the envelope wrong and every downstream error-handling branch in the client degrades silently.
- **Status codes** — must match the real API's mapping, not just "some 4xx/5xx." A 429 from consolette must actually be 429 (many client SDKs use status code alone, before even parsing the body, to decide whether to retry with backoff).
- **Content-Type and SSE framing** — `text/event-stream` with correct `event:`/`data:` framing and the exact event sequence Anthropic's streaming API uses (`message_start`, `content_block_start/delta/stop`, `message_delta`, `message_stop`, plus `ping` keepalives). SDKs' streaming helpers are written against that exact state machine; a stream that's byte-for-byte JSON-valid but sequences events differently (e.g. omitting `message_start` or not closing with `message_stop`) can hang a client's async iterator or drop the final usage/stop-reason data silently rather than raising a visible error. Same logic applies to the OpenAI SSE shape (`data: [DONE]` sentinel, `chat.completion.chunk` objects) for the OpenAI-compatible path.

Net: "drop-in" is graded entirely on whether an *unmodified* real SDK or CLI, with zero special-casing for consolette, behaves the same pointed at consolette as pointed at the real API. Anything a human would call "close enough" but a client's parser treats as a different shape is a compatibility bug, not a cosmetic one.

## 3. Accessibility (WCAG/ARIA)

**Not applicable, and stated explicitly rather than by omission.** WCAG and ARIA are standards for rendered, perceivable user interfaces (visual, auditory, or their assistive-tech equivalents) consumed by a human through a browser or native UI. This entrypoint has no such surface: it is an HTTP API with no HTML, no visual output, and no interactive control surface for a human. The "consumers" enumerated in the requirements doc are other programs (Claude Code, OpenAI/Anthropic-compatible clients) and the maintainer via CLI/logs — neither is a WCAG/ARIA audience. The relevant accessibility-adjacent surface for this feature, if any exists in the whole project, would live in `consolette`'s own CLI output (tracing/log readability), not in this HTTP entrypoint, and that's already out of this feature's scope per the requirements doc (Observability Requirements section covers logging, not UI).

## 4. Graceful error states from the API-consumer's perspective

Every one of these needs a response the calling client's normal error-handling path can parse without special-casing consolette — i.e., shaped like the upstream API's own errors (per §2), not a bespoke consolette envelope:

- **All configured upstreams down / exhausted failover** — should surface as a `529 overloaded_error` (Anthropic) or `503`/`429`-with-retry (OpenAI convention varies by cause) rather than a raw connection reset or a 500 with a stack trace. The message body should be informative enough for a human tailing logs or reading the error in a terminal to know it's a total-outage condition, not "your request was malformed" — this is the difference between a client backing off correctly and a client repeatedly retrying a request that can never succeed.
- **Auth/credential failure at the exec-helper/keychain layer (ADR-007)** — must map to `401 authentication_error`, not a generic 500. Critically, the message must never leak the resolved secret value or the exec-helper command's raw output (which could itself contain a token) — this is a hard requirement carried over from NFR-6 ("secrets ... never logged"), and it applies equally to what goes in the HTTP response body, not just log lines.
- **Malformed client request (bad JSON, missing required field, unsupported `model`)** — `400 invalid_request_error`/`invalid_request_error` equivalent, with the message identifying the offending field the way Anthropic's real API does (e.g. naming the field in `error.message`), since that's what lets a developer fix their own request instead of escalating to consolette's maintainer.
- **Mid-stream upstream failure (post-first-byte)** — per ADR-003's streaming-failover boundary and this feature's own Rabbit Holes section, this cannot become a transparent retry once bytes are flushed. It must surface as an in-band SSE `error` event using the same event framing the client is already parsing (not a raw connection close, which most SSE client libraries surface as an ambiguous/silent failure rather than a catchable error).
- **Rate limiting from upstream, propagated** — `429` with `retry_after` (already modeled in `ProviderError::RateLimitedWithRetry` in `src/providers/mod.rs`) should propagate as a real `Retry-After` header plus matching body field, since Anthropic/OpenAI SDKs read exactly that to back off correctly instead of hot-looping retries against a proxy that's already struggling.

The unifying principle: every error path's response shape is dictated by "what does the real upstream API return for this condition," not by what's convenient to construct internally — this is the same drop-in-compatibility discipline as §2, just applied to the failure paths instead of the success path.

## 5. Jobs-to-be-done

- **Functional job**: "Let me keep using the CLI tool I already have configured (Claude Code, an SDK, a script) and get multi-provider routing, failover, and cost tracking for free by changing one base-URL setting — no code change in the client, no new client library to adopt." The entrypoint's entire functional value is that it's invisible at the call site.
- **Emotional job**: confidence that switching upstreams (Anthropic direct vs. Bedrock, or failing over between them) never surfaces as a scary, unfamiliar error the developer has to reverse-engineer — a matched, expected error shape (or a clean success) means the developer never has to wonder "is this a consolette bug or a real API problem," which is exactly the ambiguity that erodes trust in infrastructure tooling fast. Given the requirements doc's constraint that this ships with no feature flag and rollback is a binary reinstall, the emotional stakes for the maintainer specifically are "did this bind cleanly and route correctly the first time," since there's no staged rollout to catch a regression gently.
- **Social job** (in the loose sense of "job that matters to the developer's relationship to their own tools/workflow," since there's no literal team/social audience for a single-user local tool): the ability to say "I run everything through my own proxy" without that costing anything in compatibility — i.e., consolette earns its place in the stack by being unremarkable. The measure of success for this feature is genuinely that a user of Claude Code pointed at consolette has no idea, moment to moment, that consolette is even there.

## Bottom line

This feature's UX surface reduces almost entirely to API-contract fidelity: matching Anthropic's and OpenAI's real error envelopes, status codes, and SSE event sequencing closely enough that unmodified client SDKs and Claude Code itself can't tell the difference from talking to the real API. There is no separate "interaction design" layer to design beyond that contract — the requirements doc's own Success Metrics (real client sends a real request, gets a real routed response) already is the UX acceptance test. The one piece worth adding to planning that isn't yet explicit in the requirements doc: validate against the real Claude Code binary (not just a hand-rolled test client) for at least the primary `/v1/messages` streaming path, since claude-code-router's experience suggests that's where undocumented client-side assumptions (retry behavior, stream-tolerance) actually surface.
