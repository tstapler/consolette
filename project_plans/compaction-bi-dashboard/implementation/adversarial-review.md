## New concern introduced by the blocker-3 fix

- [ ] **Task 3.3.1c's new integration test uses `CostServerState::build()` (real `$HOME`) rather than `build_with_session_glob()` with a fixture.** Task 3.3.1c (`tests/cost_metrics_end_to_end.rs`) adds a test that builds state "via `CostServerState::build()`" to assert `GET /dashboard` and `GET /v1/dashboard/sessions` respond `200`. That performs a genuine scan of the developer's real `~/.claude/projects/**/*.jsonl` tree (7,840+ files per `research/pitfalls.md`) on every `cargo test` run — precisely the cost the two-constructor split exists to keep out of the test suite. It won't break correctness or race (nothing else in the suite mutates `HOME`, and an empty/absent corpus on a CI box still satisfies the test's assertions), so this is not a hermeticity bug in the blocker-3 sense — but it's an unforced, easily-avoided regression in test suite speed and determinism that sits awkwardly next to the plan's own stated rationale in Task 3.1.1b and the Step 6 summary ("tests that need a fixture corpus call `build_with_session_glob(...)` directly"). **Recommendation**: change Task 3.3.1c to call `build_with_session_glob("<fixture-dir>/**/*.jsonl")` with a small fixture directory, consistent with every other new test in this plan. Not blocking — the existing pre-existing test at `server.rs:204-206` already established that a `build()` call site in the test suite is accepted behavior — but it's the one place this plan is inconsistent with its own hermeticity argument, and the fix is a one-line change.

## Concerns (unchanged — not affected by the blocker-1/2/3 fixes; re-copied from the prior review)

- [ ] **No `spawn_blocking`/`block_in_place` anywhere in the chosen approach, despite research explicitly requiring it.** `research/pitfalls.md` §2 states, as confirmed fact (not speculation): `parse_session_file` and `discover_sessions_glob` are synchronous I/O with "no `spawn_blocking`" today, and doing this "1,135+ times in one request... will stall the whole server," recommending wrapping the aggregation loop in `spawn_blocking`/`block_in_place`. `grep -n -i spawn_blocking plan.md` finds it only inside Approach B's (rejected) risk description — the chosen Approach A's tasks (2.1.3b, 2.2.1a, 3.1.1b) never wrap the per-file work in `spawn_blocking`. `buffer_unordered(16)` bounds *concurrency*, not *which thread runs the sync work* — each of those 16 concurrent futures still runs `parse_session_file`'s synchronous `File::open`/`BufReader::lines()` directly on an axum worker thread. Both the eager startup scan and every 15-minute background refresh will therefore periodically occupy runtime worker threads for however long a 7,840-file scan takes, competing with the pre-existing `/v1/cost/{session_key}` route on the same runtime. — **Recommendation**: wrap `build_session_comparison_row`'s call into `tokio::task::spawn_blocking`, or the whole `build_session_bi_snapshot` loop's per-file work, before implementation.

- [ ] **The per-file `tokio::time::timeout` cannot actually bound a pathological synchronous parse.** `tokio::time::timeout` only preempts at `.await` points inside the wrapped future. `build_session_comparison_row`'s hot path (`parse_session_file`, `build_turns`) is fully synchronous — no `.await` — so a single huge/pathological file (exactly the risk `research/pitfalls.md` §2 names: "a single pathological file... can still dominate wall-clock time") can run past the 5s `SESSION_BI_PER_FILE_TIMEOUT` budget uninterrupted, because the timeout's internal sleep can't be raced against a future that never yields control back to the executor. This is the same root cause as the `spawn_blocking` concern above and is fixed by the same change (moving the sync work to a blocking thread pool, where a timeout can at least abandon the polling task even if the blocking thread itself leaks).

- [ ] **Hardcoded, non-configurable scan constants.** `SESSION_BI_SCAN_CONCURRENCY = 16`, `SESSION_BI_PER_FILE_TIMEOUT = 5s`, and `SESSION_BI_REFRESH_INTERVAL = 15min` are `pub const`s with no CLI flag or env var to tune them. The corpus size already grew 7x past the number cited in `requirements.md` (1,135 → 7,840, noted directly in `research/pitfalls.md`'s header) mid-project — there's no reason to believe it's done growing, and the only way to change these constants today is editing source and rebuilding. Low cost to at least read overrides from env vars (`SESSION_BI_*`) given the operator is the sole consumer and already comfortable with env-var-driven config elsewhere in the codebase (e.g. `HOME`, `LITELLM_PRICING_URL`).

- [ ] **`SessionComparisonRow` is both the internal aggregation type and the literal wire format.** `#[derive(Serialize)]` sits directly on the domain struct in `session_bi.rs`; there's no DTO/serialization boundary. This is acceptable for a single-operator, unversioned internal endpoint, but it means any future Rust-side rename/refactor of that struct is silently also an API-breaking change for `dashboard.html`'s JS (`row.foo` field accesses) — worth a one-line comment on the struct noting the coupling, if not a boundary, so the next edit doesn't break the JS by surprise.

- [ ] **Concurrent-write and mid-scan corpus growth are not explicitly designed for, only accidentally tolerated.** A session file actively being appended by a live Claude Code process while `build_session_bi_snapshot` scans it (a real scenario — the operator runs consolette *while* using Claude Code) isn't discussed anywhere in the plan. It likely degrades gracefully today only because `parse_session_file` already skips-and-warns on a malformed trailing line (an incidental property of unrelated code, not a designed guarantee for this feature) — worth one explicit test/acknowledgment rather than leaving it purely coincidental.

- [ ] **`#status-banner` has no specified state machine.** *(Note: partially addressed as a side effect of the blocker-1 fix — Task 3.2.2a now distinguishes a fetch-error banner from a genuinely-empty-corpus banner, and Task 3.2.3b adds a distinct empty-after-filter banner plus the `parse_failure_count` note. Left open here, unchanged from the prior review, only because this re-review's scope was limited to the three blockers and this concern was not one of them — worth closing out explicitly in the next pass rather than assumed-fixed.)* `research/ux.md` §4 calls for at least three visually distinct banner states (loading / fetch-error / empty-after-filter) plus a parse-failure-count note, explicitly warning that collapsing "no rows" and "fetch failed" into the same blank appearance would cause the operator to draw a wrong and consequential conclusion.
