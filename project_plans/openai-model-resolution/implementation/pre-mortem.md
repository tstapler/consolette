# Pre-mortem: openai-model-resolution
**Date**: 2026-09-18

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The real ExampleCorp Model Gateway's deprecation/wrong-endpoint message wording doesn't exactly match the two hardcoded substrings in `classify_openai_error`'s table, so a genuinely deprecated model classifies as `Other` — which the walk loop is required to never advance on — and resolution aborts on candidate 1 every time, silently reproducing the exact "manual pin edit required" failure this project exists to fix. | The route this project was built to fix (ExampleCorp Model Gateway, `gpt-5.1-codex-max`) still 400s on every request after `model_family` is deployed; `resolution_attempts_total{outcome="other"}` increments but `resolution_attempts_total{outcome="success"}` never does for that family; no `Exhausted` alert fires either, because `Other` isn't `Exhausted` — the failure is invisible to the one observability signal (Story 5.1.2) built to catch "all candidates dead." | Before shipping, capture at least one *real* 400/404 response body from the ExampleCorp Model Gateway (via SBN Dev Agent, per Feasibility Risks) and add it as a table entry and a test fixture — don't rely solely on the two strings already quoted in requirements.md. Additionally, add a counter/log specifically for `Other`-classified 4xx on a `model_family`-resolving upstream (distinct from `Transient`), since today `Other` is invisible next to `Exhausted` on the dashboard — an operator has no way to tell "resolution never engaged because it doesn't recognize this error" from "auth is broken." | P1 |
| 2 | The synchronous, in-request candidate walk (probe → 3s spacing → probe → ...) plus its per-probe timeout was sized against requirements.md's "2-5 candidates" assumption but never checked against real client-side timeouts (e.g. a coding-agent's own tool-call/request timeout). The triggering request — precisely the one resolution exists to save — times out client-side before the walk finishes, even though `ResolutionCache` gets populated correctly for every *subsequent* request. | Claude Code (or another coding-agent client) reports a request timeout/dropped-connection error at the exact moment a route recovers from deprecation; consolette's own logs show a successful resolution completing a few seconds *after* the client already gave up; the second request through the same route succeeds instantly (cache hit), making the pattern look like a one-off flake rather than a structural latency problem. | Add an explicit wall-clock budget check to Story 2.3.2/2.3.2c: sum `(candidates_tried × per-probe timeout) + (candidates_tried − 1) × EVAL_PROBE_SPACING_SECS` against a documented "typical client timeout" assumption (e.g. Claude Code's own tool-call timeout, looked up rather than guessed), and either shrink spacing/timeout or explicitly document the known first-request latency cost in the docs (Story 6.2.1) so operators aren't surprised. | P1 |
| 3 | A route whose upstream is genuinely flapping (not cleanly dead, e.g. mid-migration serving a mix of old/new backend versions) causes `ResolutionCache` to invalidate-on-`Deprecated`-failure (Story 2.3.3) repeatedly: each real request that lands on the "old" backend re-triggers a full synchronous multi-candidate walk, so the "must not introduce real per-request cost/latency overhead" NFR is violated repeatedly over the flapping window, not just once at cold start. | Per-upstream p99 latency on the dashboard spikes intermittently and correlates with `resolution_attempts_total` incrementing in bursts, not just once after deploy; `resolution_exhausted_total` may stay flat (each individual walk still finds *a* working candidate) even while user-visible latency is repeatedly bad — so the one alerting signal built (exhaustion) doesn't fire for this failure mode at all. | Add a rate limit / minimum-interval on re-resolution triggered by real-request failure (distinct from Story 2.2.3's post-`Exhausted` backoff, which only covers the all-dead case) — e.g. don't invalidate-and-re-walk more than once per N seconds per family even if a fresh `Deprecated` failure comes in, and briefly stick with the last-known-good candidate as a "still trying" fallback instead. | P2 |
| 4 | Full Responses API streaming/tool/reasoning parity is verified in CI mostly against synthetic fixtures plus (per Story 6.1.2's stated interim-fallback option) generic OpenAI example transcripts, not the real ExampleCorp Model Gateway's actual SSE quirks — the same category of gap (`shutdown_date: null` being unreliable) that produced this project's original bug in the first place. A real, gateway-specific event-ordering or chunking quirk silently mistranslates a tool call or reasoning item in production. | A coding-agent tool loop through a Responses-routed model occasionally drops a tool call, double-emits a content block, or shows garbled/duplicated reasoning text — intermittent, hard to reproduce, and not caught by any test because the test suite's fixtures don't exhibit the real quirk; it looks like "the model behaved oddly" rather than a translation bug. | Treat Story 6.1.2's real-fixture capture as a hard gate for calling Responses API support "done," not an optional nice-to-have with a generic-transcript fallback — if real capture genuinely isn't available before ship, ship Responses API support as explicitly experimental/flagged in docs rather than presenting it as parity-complete. | P2 |
| 5 | `model_family` is a bare prefix match with no minimum-candidate-count or catalog-drift check. An operator typo (`"gpt5"` instead of `"gpt-5"`) or an upstream catalog change that empties the family produces zero candidates every walk, landing in the identical `Exhausted`/red-dashboard state as a genuine total-outage — the operator has no signal distinguishing "you misconfigured this" from "the upstream is actually down," so on-call time is spent debugging a live incident that's actually a typo, or conversely a typo sits unnoticed for weeks looking like "the fallback is being unusually sticky." | Dashboard shows `status-resolution-exhausted` (sticky red) for a route immediately after deploy and it never clears, even though the upstream's `/v1/models` is reachable and healthy — indistinguishable from a real dead-catalog incident without manually curling `/v1/models` and eyeballing whether the prefix matches anything at all. | Add a distinct zero-candidates-at-all classification (checked once at config-validation time by making a best-effort `/v1/models` call, or at minimum a distinct log line / metric label like `resolution_attempts_total{outcome="no_candidates"}`) separate from "walked N candidates, all failed" — so the dashboard/log can say "this family matches nothing in the catalog" instead of conflating it with exhaustion after real attempts. | P3 |

## P1 Items (address before implementation)
- [x] #1 — Capture at least one real ExampleCorp Model Gateway error body before implementation (not just the two strings already in requirements.md) and add an `Other`-classification-on-resolving-upstream observability signal distinct from `Exhausted`, so an unrecognized error phrasing is visible rather than silently indistinguishable from a healthy idle state. **Patched into plan.md**: Story 1.1.2/Task 1.1.2c (real-fixture capture), Story 2.3.2/Task 2.3.2a (`Other` aborts like `Transient` but logged under a distinct label), Story 5.1.1/Tasks 5.1.1b/d (`other` outcome label distinct from `transient`/`exhausted`). Unresolved Questions notes the fixture capture is an environment/access dependency (SBN Dev Agent/VPN), not a design gap.
- [x] #2 — Add an explicit wall-clock budget check/test to Story 2.3.2's walk loop against a documented real client timeout assumption, and surface the first-request latency cost in operator docs (Story 6.2.1) rather than leaving it undiscovered until a production timeout report. **Patched into plan.md**: Story 2.3.2 acceptance criterion + Task 2.3.2f (worst-case 62s vs. Claude Code's 300s request timeout), Story 6.2.1/Task 6.2.1d (documents the ~62s first-request latency cost for operators).
