## Concerns

- [ ] **Task 3.1.2a / Task 1.1.1a — cross-module string-equality gate is fragile and is the wrong boundary.** The plan's own Pattern Decisions table justifies not wrapping `base_url` in a value object by claiming "the endpoint is one string with one default and zero validation rules... no behavior to own." That's not accurate once Story 3.1.2 lands: the feature introduces exactly one piece of behavior — "is this upstream pointed at the default Anthropic endpoint?" — and that predicate gates security/correctness-relevant behavior (Bedrock-id stripping). Implementing it as `base_url != default_anthropic_base_url()` re-derived via string equality inside `normalize_model_name`, called on every request, has two real problems: (1) it forces `default_anthropic_base_url` to widen from private to `pub(crate)` purely so a provider module can peek at a config module's default-value function — a layering smell where `schema.rs`'s visibility is dictated by `anthropic.rs`'s internal gating logic; (2) it's exact-string-equality with no normalization, so an operator who writes `base_url = "https://api.anthropic.com/"` (trailing slash, semantically identical, and a wart the plan explicitly declines to fix elsewhere — Tech Debt Disposition row 3) gets silently routed onto the "custom endpoint" branch and *skips* Bedrock-id normalization against the real Anthropic API — the exact model-id corruption pitfalls.md #2 was trying to close, just relocated to a different, harder-to-notice trigger.
  **Remediation**: compute the "is default endpoint" decision once, at construction time in `build_providers` (which already destructures `{ base_url }` in Story 3.1.1), and pass a plain `bool` (or better, an enum with two variants) into `AnthropicProvider::new` instead of re-deriving it per-request via string comparison inside `normalize_model_name`. This removes the need to widen `default_anthropic_base_url`'s visibility at all (call it once, at the single site that already owns both values), and gives you one place to decide whether trailing-slash / scheme-case variants of the default URL should still count as "default" — instead of baking that decision implicitly into `!=`.

- [ ] **Story 1.1.1 / `entrypoint/mod.rs:173` + `validate.rs:44` — pre-existing duplicate `upstream_kind_label` function, touched but not deduplicated.** `src/entrypoint/mod.rs:166-174` and `src/config/validate.rs:42-50` contain a byte-identical private `fn upstream_kind_label(kind: &UpstreamKind) -> &'static str` with the same five match arms. Task 2.1.1a edits both copies identically (`Anthropic => ...` → `Anthropic { .. } => ...`) without noticing they're duplicates — the reuse-check the architecture-best-practices skill calls out as "do this before touching the file" would have caught this. Not caused by this plan, and fixing it is optional scope, but since the plan is already touching both call sites in lockstep, it's a low-cost moment to extract one shared helper (e.g. into `config/schema.rs` next to the enum, or a small shared module) rather than leave two copies that must be kept in sync by every future variant addition.
  **Remediation**: either extract a shared `upstream_kind_label` (small follow-up, ~5 min, arguably in-scope for Task 2.1.1a since it's already touching both sites) or explicitly note in Tech Debt Disposition that this duplication is left as-is and why (the table currently doesn't mention it at all).

## Nitpicks

- The plan's Migration Plan section states the constructor-signature break is "entirely internal to this crate," which is accurate given `lib.rs`'s stated intent (sharing code across this crate's own three binaries, not serving external consumers) — but the claim would benefit from explicitly noting `AnthropicProvider::new` is technically `pub` and reachable from outside the crate if `consolette` were ever depended on as a library (`Cargo.toml` has no `publish = false`). Low likelihood, zero cost to note in one sentence; not worth blocking on.
- Lens 3/pattern selection: "Transaction Script / plain config plumbing" is the right call for the schema-plumbing parts of this change (field, constructor param, call-site wiring) — no over-engineering there. The mismatch is narrowly in the `normalize_model_name` gating (covered above), not the overall pattern choice.
- Lens 4/"EXTEND-AS-IS" for converting `UpstreamKind::Anthropic` from a unit variant to a struct variant: this verdict is correct. The ~8-9 mechanical fixups fan out because Rust's exhaustive-match sum type is doing its job — every site the compiler flags is a site that must be correct, and none of them hide runtime risk (pitfalls.md #5, confirmed true by inspection: the three label/no-op arms and five test-fixture sites are compile-error-caught, not behavior-changing). Introducing a trait-based dispatch seam to avoid this fan-out would be premature generalization for a closed, 5-variant enum representing a genuinely closed set of upstream kinds — that's exactly the case exhaustive matching is designed for, not a smell to isolate away.
