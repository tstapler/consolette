## Concerns

- [ ] **C1 — `plan.md`'s header and traceability table still carry the pre-fix "mandatory session-scoping" framing that ADR-009's body no longer makes.** Line 6 ("ADR-009 (omission cache backend + mandatory session-scoped MCP retrieval)") and the requirement-traceability table's row 3 ("Omission-cache retrieval via MCP with mandatory session-scoping | ADR-009 — ... every query scoped by `session_id`") both read as an unqualified security claim. A reader who only skims `plan.md` (rather than ADR-009's full corrected text) gets exactly the overclaim the previous blocker was raised against. Update both spots to reflect ADR-009's actual framing (query-shape scoping, with the residual client-supplied-identity caveat and Task 5.1.0's pending finding).

- [ ] **C2 — Epic 2.1's "Goal" line in `plan.md`, and ADR-008's "Consequences" section, still describe the reversed (pre-fix) pruning design.** `plan.md`'s Epic 2.1 Goal states pruning will be "reusing `crate::compression`'s pure primitives" — directly contradicting Story 2.1.1's algorithm note two paragraphs below, which explicitly reverses this ("This plan intentionally does **not** reuse `crate::compression`'s fallback chain... inside `prune_tool_row` at all"). Separately, ADR-008's Consequences section still says "this ADR only adds new call sites into its pure functions" and "Future proxy-side compression changes must... or `claude_code_session::prune` breaks too — a light coupling" — both false under the ADR's own Revision text earlier in the same document, which states `prune.rs` is self-contained and does not call the six primitives at all. This is the same class of self-contradiction as the original Blocker 2, now relocated to the Epic-level summary and the ADR's own Consequences bullets rather than the Story/Task text. Task 2.1.1b itself is unambiguous, so this doesn't block implementation, but it should be fixed for document consistency before someone skims the Epic/ADR summary and implements the wrong thing.

- [ ] **C3 — Story 5.1.1's acceptance criteria don't fork on Task 5.1.0's spike outcome.** Task 5.1.0 explicitly says the spike may replace the client-supplied `session_id` design with binding `session_id` at MCP-process-spawn time if Claude Code launches one MCP server per session. But Story 5.1.1's acceptance criteria (the `list_tools` schema `{session_id: string, content_id: string}` and `call_tool` dispatch reading `session_id` as a tool argument) are written unconditionally for the client-supplied-argument design. If the spike lands on per-session topology, Story 5.1.1 needs a structurally different implementation (no `session_id` tool argument at all) that the plan doesn't currently describe or gate on. Recommend adding an explicit "if per-session topology, Story 5.1.1's schema changes to X" branch, or deferring Story 5.1.1's concrete acceptance criteria until after Task 5.1.0 resolves.

- [ ] **C4 — The mechanism linking "sidechain rows excluded from the main chain" to "dangling-parent tolerance" isn't pinned down in Task 1.2.1a.** Story 1.2.1 requires sidechain rows to be excluded from the main chain, and separately requires a parent_uuid pointing at an excluded sidechain row to be treated as a tolerated dangling reference (not a cycle-detection error). Task 1.2.1a's described algorithm builds "a `uuid -> TranscriptRow` map" from rows and checks dangling references against that same map — but doesn't specify whether sidechain rows are excluded from this map before the walk. If they aren't excluded, a parent_uuid pointing at a sidechain row resolves normally via the map (defeating "excluded from the main chain"); if they are excluded, that's the mechanism that makes the reference "dangling" in the first place, and the task should say so explicitly rather than leaving it implicit. Task 1.2.1c's fixture (d) tests the *outcome* but not which of these two implementations produces it.

- [ ] **C5 — Story 3.2.1's "documented follow-up" for exceeding the 150s timeout isn't actually in the Follow-ups section.** The story's timeout paragraph says "if `turns_to_summarize` is large enough to routinely exceed 150s, that's a documented follow-up (chunked/incremental summarization), not solved here" — but the plan's "Follow-ups" section (6 items) has no entry for this. Either add it as Follow-up #7, or soften the story's "documented" claim to something less specific like "an acknowledged limitation."

- [ ] **C6 — Story 5.2.1's end-to-end integration test doesn't specify which `Summarizer` implementation it uses.** The test ("a fixture session JSONL with 6+ turns and one oversized tool result end-to-end through `compact_session`") would, if it uses the real `ClaudeCliSummarizer`, either require the `claude` CLI in CI (which Story 3.2.1 elsewhere says isn't available/is gated off by default) or hang/fail unpredictably. Recommend explicitly stating this test injects `FakeSummarizer`, consistent with how Story 3.2.1 gates real-CLI invocation behind `COMPACTION_HOOK_LIVE_CLAUDE_TEST=1`.

## Minors

- Task 3.1.1a's "check Cargo.toml first, prefer `impl Future` if `async-trait` needs adding" hedge is still stale (carried over from the previous review, not addressed by this patch round) — both `rusqlite` and `async-trait` are already pinned in `Cargo.toml`/`Cargo.lock`.
- No test is specified for a write failure partway through the atomic tmp-then-rename destination write (carried over from the previous review, not addressed by this patch round).
- Task 5.1.0's "~5 min" estimate is optimistic for an investigation that may require manually configuring two Claude Code project `.claude` configs and observing process/topology behavior — this gates a security-relevant design decision (ADR-009), so it's worth more than a nominal time-box even if the plan's other tasks are similarly terse.
- Story 5.2.1's `compact_session(session, preserve_last_n_turns: usize)` takes a plain `usize` while the CLI's `Command::CompactSession` field is `preserve_last_n_turns: Option<usize>` — the `None` → `0`-default mapping point (presumably in Task 5.2.1a/c) isn't named explicitly.
