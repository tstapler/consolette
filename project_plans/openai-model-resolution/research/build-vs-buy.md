# Research: Build vs. Buy — Dynamic Model Resolution + Responses API + max_completion_tokens

Agent 6 of Phase 2 research for `project_plans/openai-model-resolution/requirements.md`.

## Grounding: consolette's existing pattern and constraints

- `src/providers/openai.rs` is a hand-rolled thin HTTP client (`reqwest`) — no OpenAI SDK crate today. It builds/parses JSON directly with `serde_json::Value`, not typed structs (`json!()`/`Value::get` throughout).
- `src/providers/mod.rs` implements bespoke `translate_*` functions (`translate_openai_to_anthropic`, `translate_anthropic_request_to_openai`, `translate_openai_response_to_anthropic`, etc.) that convert between raw `serde_json::Value` trees. This is the established in-repo pattern the new Responses-API translation must match to stay consistent — not a `TryFrom<TypedStruct>` architecture.
- README/CLAUDE.md framing: consolette is explicitly "a single Rust binary," a "lightweight local proxy" running on `127.0.0.1:47000` with no per-request cost/latency budget for the common (static-pin) case, and "no shared/distributed cache" — a single local daemon, not a hosted multi-tenant service. Any buy option that adds a network hop or a SaaS dependency cuts directly against this framing.
- Cargo.toml has no OpenAI SDK dependency (`async-openai`, `openai-api-rs`, etc.) at any point in the dependency tree.

## Option 1: Existing OSS Rust crate for OpenAI Responses API types

**Candidate**: [`async-openai`](https://github.com/64bit/async-openai) (crates.io, MIT license, maintained by Himanshu Neema). VERIFIED via WebSearch (2026-09-18): ~6.8M all-time downloads, 120+ published versions, latest 0.41.x, repo activity within the last month, spec kept in sync with OpenAI's own Stainless-generated OpenAPI spec. Has a dedicated `responses()` client group with typed `CreateResponseArgs`/`Response` types, a `byot` (bring-your-own-type) feature for custom in/out types, and broad API surface (chat, responses, embeddings, files, etc.) behind granular feature flags.

A narrower alternative, `open-ai-rust-responses-by-sshift`, exists specifically for the Responses API but is a small, single-maintainer, low-adoption crate (UNVERIFIED beyond crates.io listing) — materially higher single-point-of-failure risk than `async-openai`'s ecosystem position.

**Fit assessment**: consolette's established pattern is "deserialize upstream JSON into an internal Anthropic-shaped representation via `serde_json::Value`-level translate functions," not "depend on a typed request/response SDK." Adopting `async-openai` for *types only* would mean:
- Depending on its `serde`-derived `Response`, `ResponseStreamEvent`, `OutputItem`, etc. enums instead of hand-rolled `Value` matching for the deserialize side.
- Still writing 100% of the translation logic in `translate_*` functions — a types crate buys correctness on "does this struct match OpenAI's JSON shape" (the Responses API's own schema drift risk) but does nothing for the actual hard part flagged in the requirements' Rabbit Holes section: mapping Responses API's item-array `output`/typed `input` and its distinct SSE event taxonomy (`response.output_item.added`, `response.output_text.delta`, ...) onto Anthropic's content-block/stop-reason model. That mapping is 100% consolette-specific business logic no crate can supply.
- Adds a large, fast-moving dependency (broad feature surface: audio, images, embeddings, evals, fine-tuning — none of which consolette needs) purely for its Responses API struct definitions, feature-gated but still a supply-chain surface increase.
- Risk of directly-versioned struct definitions going stale against `#[serde(deny_unknown_fields)]`-free-but-strict-enough deserialization if OpenAI (or the ExampleCorp Model Gateway proxy in front of it) emits fields `async-openai`'s enums don't recognize yet — actually a real risk given the plugin's docs). serde by default ignores unknown fields, so this degrades gracefully, but any `#[serde(tag = ...)]` internally-tagged enum mismatch on a genuinely new item type would fail loudly.

**Pros**: mature, actively maintained, MIT-licensed, provides the exact Responses API struct definitions (avoiding hand-transcribing OpenAI's JSON schema mistake-by-mistake); the SSE event enum in particular removes one class of "did I get the taxonomy right" bugs.
**Cons**: doesn't reduce the hardest work (item-array/event-taxonomy → Anthropic translation is still 100% bespoke); introduces a large dependency for a narrow use; a version mismatch/schema-drift risk against a proxy upstream (ExampleCorp Model Gateway) that may not track OpenAI's spec 1:1; breaks from this codebase's established `serde_json::Value`-translation architecture, meaning either an awkward two-styles-of-parsing split (chat/completions stays `Value`-based, Responses becomes typed) or a larger-than-planned refactor to keep both consistent.
**Verdict**: **Viable, not recommended as the primary path.** Worth a narrow, scoped use: pull `async-openai`'s `response-types` feature (types only, no client) as a *reference/validation* aid during implementation — e.g. write a unit test that round-trips real captured Responses API JSON through both consolette's own hand-rolled parser and `async-openai`'s struct, to catch schema misunderstandings — without taking it as a runtime dependency of the translation path itself. This is a build decision augmented by a buy-derived correctness check, not a buy decision.

## Option 2: SaaS / managed universal LLM gateway (LiteLLM proxy, Portkey, OpenRouter, Helicone)

These products (LiteLLM proxy — self-hostable OSS **or** hosted; Portkey, Helicone — hosted SaaS; OpenRouter — hosted marketplace) all implement cross-provider request translation and some form of fallback/retry.

**Cost/latency/fit assessment against consolette's stated design**:
- consolette's README explicitly frames it as a lightweight **local** daemon on loopback (`127.0.0.1:47000`) with zero-overhead passthrough as a stated non-functional requirement for the common case. Any of these products, used as "sit in front of this one upstream," adds a network hop (SaaS) or a second local process to operate/config-sync (self-hosted LiteLLM), directly working against "no real per-request cost/latency overhead."
- Hosted options (Portkey, Helicone, OpenRouter) also mean sending the actual coding-agent traffic (prompts, tool calls) through a third party — a new data-residency/security surface the requirements doc's Security classification section doesn't currently accept ("internal... no new secrets... probe traffic goes to the same upstream").
- LiteLLM specifically *does* implement deprecation-resilient fallback (`fallbacks`/`default_fallbacks` config, sequential fallback across a model list, exception-classified retry — see Option 3 below) — functionally close to what's wanted. But adopting it here means either (a) routing this one upstream's traffic through a self-hosted LiteLLM proxy process sitting between consolette and the ExampleCorp Model Gateway (an extra hop plus a second piece of infrastructure to keep configured and healthy for a single upstream), or (b) replacing consolette's own provider abstraction with LiteLLM's Python router for OpenAI-compatible upstreams generally — a rewrite in a different language, out of all proportion to the actual gap (one upstream's model rotation).
- None of these products solve the Responses API translation problem for consolette's callers: they normalize *outbound* provider calls, but consolette's clients call *it* over `/v1/messages` (Anthropic-shaped) and `/v1/chat/completions` — the translation consolette needs is inbound-shape-preserving, which is exactly the custom logic already living in `providers/mod.rs`. A gateway product doesn't remove that need; it would sit in a different part of the request path.

**Pros**: LiteLLM in particular has a proven, documented fallback engine and exception taxonomy (see Option 3) that consolette could take design inspiration from without adopting the software.
**Cons**: extra network hop / process, conflicts with the explicit "lightweight local proxy, zero-overhead passthrough" design goal; hosted variants introduce a third-party data path for coding-agent traffic; doesn't address the Responses-API-translation-into-Anthropic-shape requirement at all, which is unique to consolette's inbound API surface.
**Verdict**: **Not recommended.** Read LiteLLM's fallback/exception-mapping design (Option 4) for inspiration; do not run traffic through it or any hosted gateway for this feature.

## Option 3: LLM-generated bespoke code vs. battle-tested library, for error classification and SSE translation specifically

Two distinct pieces of logic are in scope here, and they carry very different risk profiles:

1. **Error classification (deprecated vs. transient vs. wrong-endpoint)**: this is inherently upstream-specific pattern matching over HTTP status + JSON error body shape (`error.type`, `error.code`, message substrings like "has been deprecated" / "not supported in the v1/chat/completions endpoint"). No Rust crate exists that classifies *third-party, potentially proxy-mutated* error bodies this way — even `async-openai` only gives typed *success* response shapes, not a deprecation-classification engine, and LiteLLM's own classification (Option 4) is Python-only and tuned to OpenAI's canonical error bodies, not ExampleCorp Model Gateway's proxy-shaped ones (whose 400/404 bodies were observed by hand in this investigation to differ from vanilla OpenAI's). Bespoke code is the *appropriate* choice here, not a corner cut — but "bespoke" must mean: a small number of explicit, testable predicate functions matched against real captured error bodies (already gathered in the manual investigation per the requirements doc), each backed by a unit test using the literal captured JSON, not an LLM-improvised guess at what "OpenAI errors look like." Encode the classification as data (a table of `(status, type/code substring, message substring) -> Classification`) so it's auditable and diffable, matching this repo's existing style of explicit match arms in `translate_*`.
2. **SSE event-taxonomy translation for Responses API streaming**: this is the highest-correctness-risk piece flagged in the requirements' Rabbit Holes section. It is bespoke by necessity (no crate translates Responses-API SSE into Anthropic SSE), but it is *not* the place for improvised/under-tested code given the appetite is "Large" specifically because of this risk. The mitigation is process, not a library: build the event-type enum from the *actual* documented taxonomy (OpenAI's Responses API streaming docs list a closed set of event types — `response.created`, `response.output_item.added`, `response.output_text.delta`, `response.output_item.done`, `response.completed`, etc.), exhaustively match (`match` with no default arm, so a new/unhandled event type is a compile-time-visible gap, or at minimum a logged-and-passed-through unknown-event path rather than silent drop), and test against real captured SSE streams (both non-tool and tool-call/reasoning-item streams) the way `translate_openai_response_to_anthropic`'s existing test suite already does for chat/completions (`translate_openai_response_prefers_content_over_reasoning`, `..._emits_signed_thinking_before_text`, etc. in `src/providers/mod.rs`).

**Verdict**: bespoke is appropriate and unavoidable for both, **conditioned on** treating them with the same test-driven rigor as the existing chat/completions translator (which already has ~30 unit tests per the `#[cfg(test)]` block in `src/providers/mod.rs`) rather than writing them once and trusting review alone.

## Option 4: Fork or adapt an existing proxy's design (not code)

LiteLLM (Python, Apache-2.0-with-commercial-enterprise-tier, [docs.litellm.ai](https://docs.litellm.ai)) is the closest prior art, and reading its design is worth the time even though its code can't be reused (language mismatch, and its fallback engine is deeply wired into its Python `Router` class):

- **Exception taxonomy** (VERIFIED via WebSearch of LiteLLM's own docs, 2026-09-18): LiteLLM maps every provider error into one of a small closed set — `AuthenticationError`, `NotFoundError` (wrong/deprecated model name), `RateLimitError`, `ContextWindowExceededError`, `ServiceUnavailableError`, `BadRequestError` (malformed request) — and its fallback/retry logic explicitly gates on this classification: rate limits/timeouts/server errors are retryable, a `BadRequestError` from a bad prompt is not, but a `NotFoundError`/deprecated-model `BadRequestError` *does* trigger fallback to the next configured model. This maps directly onto the requirements' Rabbit Hole #3 ("distinguishing deprecated model from wrong endpoint from transient error") — a small closed taxonomy plus explicit gating is the validated shape to copy conceptually.
- **Fallback mechanics**: sequential trial across a configured model list, tracked per-request in spend logs with `attempted_fallbacks`/`original_model_group` — directly analogous to what's wanted for observability (Observability Requirements section: "which candidate, which family").
- **Caveat on relevance**: LiteLLM's fallback list is human-curated config (`fallbacks: [...]`), the same "static allowlist" approach the requirements doc's Alternatives Considered section already rejects for this project. What's novel in consolette's ask — discovering candidates live from `/v1/models` because the *next* working model id isn't knowable in advance — has no direct LiteLLM equivalent to borrow from; only the error-classification and fallback-tracking *shape* transfers, not the resolution-discovery mechanism itself.

**Pros**: free, well-documented design reference; validates the "small closed error taxonomy + explicit retryable/non-retryable gating" approach as sound engineering, not reinventing something already known to be fragile.
**Cons**: no code reuse possible (Python vs. Rust); the actual novel mechanism (live catalog discovery + real-request probing) isn't present in LiteLLM's design, so this only informs the error-classification and observability pieces, not the resolution algorithm itself.
**Verdict**: **Recommended as a design reference**, not as a dependency or fork target — read LiteLLM's exception-mapping and fallback docs before finalizing the error-classification design (Rabbit Hole #3 / Open Question #3 in requirements.md), but implement natively in Rust matching this repo's existing `translate_*` style.

## Summary Table

| Option | Verdict |
|---|---|
| 1. `async-openai` crate for Responses API types | Viable, not recommended as a runtime dependency — optionally useful as a schema-validation aid during test-writing only |

## Overall Recommendation

Build natively in Rust, matching consolette's existing `serde_json::Value`-based `translate_*` pattern in `src/providers/mod.rs` and `src/providers/openai.rs` — no new runtime dependency for OpenAI types, no SaaS/gateway hop. Use `async-openai`'s Responses API struct definitions only as an implementation-time correctness check (round-trip real captured JSON through both), and use LiteLLM's published exception taxonomy and fallback-tracking shape as a design reference for the error-classification rule and observability counters called for in the requirements doc.
