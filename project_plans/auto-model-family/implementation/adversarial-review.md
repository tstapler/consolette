# Adversarial Review: auto-model-family

**Date**: 2026-09-12
**Verdict**: PASS (re-review 2026-09-12: B1–B5 RESOLVED)
**Sources read in full**: `project_plans/auto-model-family/implementation/plan.md`, `project_plans/auto-model-family/requirements.md`; verified against `src/routing/router.rs` (dispatch loop), `src/entrypoint/api.rs` + `src/entrypoint/mod.rs` (session endpoints), `src/routing/session_overrides.rs`, `src/routing/health.rs`, `src/config/{schema,load,validate,runtime_overrides}.rs`, `src/providers/{mod,openai,anthropic}.rs`, `src/providers/mod.rs:206` (`translate_openai_to_anthropic`), `src/entrypoint/{messages,chat_completions,observability}.rs`, `src/dashboard.rs`, `src/metrics/{mod,counters}.rs`, `src/cost_metrics/pricing.rs`.

**Session-endpoint question first**: `DELETE /api/sessions/{id}/route` and `GET /api/sessions` both exist (`src/entrypoint/mod.rs:161-167`, handlers in `src/entrypoint/api.rs:140-209`). The risk is not existence but semantics — see C2, C3.

## Blockers

- [x] **B1 — RESOLVED (per-(upstream,model) attempt tracking + same-upstream failover test in Story 3.1 AC3/tasks). Same-upstream members cannot fail over within one request (`already_tried` is index-keyed).** Plan Story 2.2 AC1's own topology is two members via one upstream `openrouter` (`model-a`, `model-b`). Family expansion would emit two `UpstreamRef`s with the *same* `index` but different `model`. The dispatch loop filters `!already_tried.contains(&u.index)` (`src/routing/router.rs:282-286`) and inserts `chosen.index` after each attempt (`:291`). After member A is tried, member B (same index) is filtered out — "the existing loop iterates" over the ordered member list (plan §Pattern Decisions) silently never reaches it. Recommendation: key attempt-tracking per-(upstream, model) for family-expanded candidates, or expand same-upstream members into distinct candidate entries the loop can address; add a same-upstream failover test before E3.
- [x] **B2 — RESOLVED (bypass never overrides 429 cooldowns + shared-upstream 429 test, Story 3.2 AC4/AC5). Per-index `HealthRegistry` contradicts per-member ranking for shared upstreams.** Cooldown is keyed by upstream index (`src/routing/health.rs:32-38`); a 429 on member A trips the shared index, excluding healthy member B too. Worse, Story 3.2's SafetyNetBypass ("cooldown bypassed, least-bad served") would then retry into a rate-limited upstream, hammering backpressure. `can_cooldown=false` (Bedrock, `router.rs:155-157`) adds a third granularity: a Bedrock-backed member can never be excluded. Recommendation: specify the interaction — per-member exclusion (denylist) vs per-upstream cooldown — explicitly; define bypass to never override 429-driven cooldowns, only health-unknown/empty-pool cases; test the shared-upstream 429 scenario.
- [x] **B3 — RESOLVED (metadata passthrough/pre-translate extraction + opencode-shaped pin test, Story 4.1 AC3). Epic 4 is inert on the opencode path: translation drops `metadata`.** `extract_session_id` reads `body.metadata.user_id` (`src/routing/session_overrides.rs:32-37`), but `translate_openai_to_anthropic` builds a fresh body carrying only `model/max_tokens/messages/stream/system/temperature` (`src/providers/mod.rs:252-267`) — no `metadata` passthrough. Opencode (`/v1/chat/completions`, the primary family consumer per requirements) therefore always yields `session_id=None`: pins never apply, `GET /api/sessions` never lists opencode sessions, and Stories 4.1/4.2 pass only for Claude Code traffic. Recommendation: thread a session key through the OpenAI adapter (e.g. preserve `metadata`, or extract from an OpenAI-native field like `user`) before E4; add an opencode-shaped session-pin integration test.
- [x] **B4 — RESOLVED (fail-closed unknown non-`:free` IDs, vendored `PricingTable::load_default`, rotation tests, Story 1.2). FreeGuard's `None` case is unspecified at exactly the boundary it guards.** `price_for` returns `None` for models absent from the snapshot/overrides (`src/cost_metrics/pricing.rs:114-117`), and requirements state free-model IDs rotate on OpenRouter's side. Plan Story 1.2 ("rejects IDs not ending `:free` unless pricing table says free") never says whether `None` means free or paid, nor which pricing source (vendored snapshot vs live-refresh) a *synchronous* config validator reads. Fail-closed breaks config load on every rotation (availability vs the "zero manual swaps" success metric); fail-open lets any unknown ID into the free family (billing). Recommendation: decide fail-open/fail-closed explicitly, name the pricing source and its sync/async fit for validation, and add rotation (unknown-ID) tests for both aliases.
- [x] **B5 — RESOLVED (first-request-fails-then-denylist accepted + 404-vs-400 discrimination with tests, Story 3.2). Story 3.2's promise is unachievable without changing the validation arm.** Both providers map *all* 4xx — including 404 delisted — to `ProviderError::Validation` (`src/providers/openai.rs:246-249`, `src/providers/anthropic.rs:322-325`), and dispatch returns immediately on `is_validation()` with no failover (`src/routing/router.rs:335-338`). Consequences: (a) the first request after a delist still hard-fails the client — the denylist only helps request N+1, so "a 404 member never fails the whole request" (Story 3.2 intro) is false as specified; (b) the denylist writer ("record on Validation-404 path") must discriminate `status==404` from the `Validation(String, u16)` tuple, or any client-caused 400 will quarantine a healthy member for the TTL. Recommendation: specify either a family-scoped 404-continue arm or explicitly accept first-request-fails + document it; require the 404-vs-400 discrimination with tests for both.

## Concerns

- [ ] **C1 — Story 6.1 AC1 is unimplementable as written.** `GET /api/models` passes through each upstream's live catalog (`src/entrypoint/api.rs:58-67`); a synthetic alias will never appear there without new injection code, which no task plans ("passthrough check" is the opposite of what's needed). The other half ("opencode provider config") is repo-external and untestable in-repo. Recommendation: add an explicit alias-injection task in `api.rs` with a test, or rewrite AC1 to cover only the repo-external config + dispatch behavior.
- [ ] **C2 — `GET /api/sessions` hides pinned-but-quiet sessions.** Handler lists only sessions seen in the last-100 ring buffer (`src/entrypoint/api.rs:140-158`); `SessionOverrideStore::list()` — the complete pin snapshot — has no production caller (only its own unit test). Story 4.2 AC2 overclaims. Recommendation: union ring-buffer recency with `list()` output, or scope AC2 to recently-seen sessions.
- [ ] **C3 — Pin-to-outside-route silently no-ops.** `post_session_route` accepts any upstream in on-disk config (`src/entrypoint/api.rs:192`), but `effective_candidates` falls back to normal routing with only a warn log when the pinned upstream isn't in the current route (`src/routing/router.rs:223-230`). "Quarantine per session" (Story 4.2 intro) fails silently for off-route members. Recommendation: reject off-route pins at POST time, or carry the pin through regardless of route membership — pick one and test it.
- [ ] **C4 — Cost attribution records the alias, not the resolved model.** Both handlers capture `model` from the client body and pass it to cost recording (`src/entrypoint/messages.rs:37-58`, `src/entrypoint/chat_completions.rs:43-73`); `price_for(alias)` is `None`, so family traffic (including paid-alias spend) is invisible/mispriced in the cost tracker while Story 7.1 claims paid accountability via a separate counter. Recommendation: thread the resolved model ID back to the cost-tee call sites, or document the blind spot and reconcile the two counters.
- [ ] **C5 — `MemberStats` keyed by upstream *index* misattributes on reorder.** Plan proposes `DashMap<(usize, String), MemberStats>` (Story 2.1 task 1), but indices shift across config edits/hot-swaps while names are stable (ADR-002 says per-"(upstream, model)"). Recommendation: key by `(upstream_name, model_id)`.
- [ ] **C6 — Latency signal is time-to-headers, yet ranks as p50.** `record_attempt` measures `provider.send` return, i.e. headers for streams (documented at `src/routing/router.rs:398-404`); mid-stream stalls/errors never record. A fast-start/slow-stream model outranks wrongly. Recommendation: note the proxy-metric limitation; consider stream-completion recording or demote latency weight for streams.
- [ ] **C7 — Hot-swap wipes all family state, including the audit trail.** `post_route` rebuilds `Router::from_config` (fresh health/registry, `src/entrypoint/api.rs:121-130`); MemberStats, denylist, snapshots, and `ResolutionCounter`s die with the old Router — including on the blessed rollback path — while session pins got an explicit carry-over precedent (`with_session_overrides`). Recommendation: specify what survives a hot-swap (at minimum: counters/denylist carry-over or explicit reset semantics).
- [ ] **C8 — Story 1.1 task 4 targets the wrong seam.** Families load from conf.d on every `post_route` (`candidate = load(...)`), so they already survive hot-swap; what needs building is the `FamilyTable` in `from_config`. Extending `RuntimeOverrides::apply` instead would split family definition across conf.d and `runtime-overrides.toml`. Recommendation: retarget the task to `from_config` table rebuild + test; keep families out of runtime overrides.
- [ ] **C9 — Dashboard work is structurally underestimated and sprawls past requirements.** `handle_dashboard` serves a static const with zero state (`src/dashboard.rs:614-616`); "server-rendered family card" requires a dynamic handler + new JS polling + rework of the string-match test guards — the largest structural change in the feature, not a ~5 min task. Requirements' rabbit hole ("keep it to the two ranking signals") also conflicts with the plan's previous-pick/window-age/runner-up/margins display set. Recommendation: cut dashboard scope to pick + error%/p50 + status, and size the static→dynamic conversion honestly.
- [ ] **C10 — No membership-refresh story for OpenRouter rotation.** Requirements flag rotation as a feasibility risk; the plan only reacts (404 denylist with TTL) and never discovers replacements — a renamed free model still needs a manual conf.d edit, directly taxing the "zero manual swaps for a month" metric. Recommendation: add a refresh story (periodic catalog revalidation in Epic 3/6) or explicitly scope rotation out with metric consequences stated.
- [ ] **C11 — Performance NFR has no acceptance.** Requirements defer "exact budget" to Phase 3; the plan puts a `DashMap` lookup + pure rank on the hot dispatch path with zero measurement story. Recommendation: add a criterion/benchmark task (resolution overhead vs static-pin baseline) to E3 or E5.
- [ ] **C12 — Hysteresis/probe constants are unjustified and probe traffic costs real requests.** err>2pp / lat>10% / every-25th / N=5 appear without single-user volume math (25 requests may span days — demoted models never recover samples), each probe deliberately sends a user-visible request to a worse member, and incumbent-advantage sits uneasily with requirements' "lowest-error then lowest-latency" ranking. Recommendation: justify from request volume or start with hysteresis-only and add probing after evidence.
- [ ] **C13 — Marked "Ready" with five load-bearing questions open.** Naming (E1/E6 surface), decay design (E2), stickiness (E4 semantics), margins (E3), threshold (E2/E3) all default-to-implementer-guess. Recommendation: resolve naming + stickiness with Tyler pre-implementation; the rest can stay implementer-defaults with the spike criterion kept.
- [ ] **C14 — SafetyNetBypass cannot rescue hard failures.** All-404 (all delisted) still ends in the validation immediate-return — the bypass "serves least-bad" then errors to the client anyway, counter notwithstanding. Recommendation: state that bypass covers cooldown/empty-pool only, not 404/auth/validation.
- [ ] **C15 — Figment array-replace vs multi-file families.** `runtime_overrides.rs:20-22` documents conf.d array-replace semantics: families split across two `*.toml` files will clobber, not layer (the plan's verify-task is real, but AC1 tests only a single file). Recommendation: assert single-file convention for `[[model_families]]` or fix/verify merge behavior in E1 with a two-file test.

## Minors

- Story 6.1 AC2's "alias-interception-before-translate" misnames the order: the alias passes *through* `translate_openai_to_anthropic` into dispatch, where resolution overwrites it — test the overwrite, not a pre-translate interception.
- `Router::new` gaining a field churns every test constructor (`router.rs`, `observability.rs`, `messages.rs`, `chat_completions.rs` tests) — mechanical but unmentioned; prefer a builder/`with_family_table` default to keep the diff small.
- Plan cites volatile line numbers (`router.rs:260-294`, `:219-237`, `:318/336/...`) — they already drift; cite symbols (`effective_candidates`, `record_attempt`, error-class arms) instead.
- ExplorationProbe counter scope (global vs per-alias vs per-session) is unspecified; global counter + per-request ranking can starve probes for low-traffic aliases.
- Story 7.1 task 1's OpenRouter-`auto` backing revives an option the Creative Pass "rejected for default" and requirements left "not chosen" — if kept, fence it as paid-alias-only config with `allowed_models`/`max_price` mandatory, not optional.
- Delisted members surface to clients as 400-class `Validation`, not 404 (`errors.rs` maps only `ModelUnsupported` to `not_found_error`) — cosmetic, but dashboard/error-taxonomy stories should not promise 404 fidelity without a mapping change.
