# Adversarial Review: Consolette

**Date**: 2026-07-17
**Reviewer**: Adversarial architecture review (SDD Phase 3)
**Verdict**: BLOCKED

Grounded in `implementation/plan.md`, `requirements.md`, the four `research/*.md`,
and the actual current source (`stapler-scripts/claude-proxy-rs/`:
`config.rs`, `main.rs`, `metrics/counters.rs`, `com.claude-proxy-rs.plist`).

Summary: the routing/rate-limit/config core is well-researched and the refactor
seams are sound, but the plan has three concrete cutover/back-compat gaps that
would regress "zero dropped daily usage" (FR-6.2) and OpenAI-client compat
(NFR-1) the moment it ships, plus several architecture inconsistencies that will
bite during implementation. Resolve the blockers before writing code.

## Blockers

- [ ] **New launchd plist silently drops secrets and uses the wrong port var — breaks daily usage on cutover (FR-6.2, NFR-6).** The live plist (`com.claude-proxy-rs.plist`) injects `CLAUDE_CODE_OAUTH_TOKEN`, `AWS_PROFILE`, `AWS_REGION`, `PROXY_PORT`, `COOLDOWN_SECONDS`, `REQUEST_TIMEOUT`, `BEDROCK_MAX_RETRIES`, `STAPLER_COMPRESS`, `CACHE_ALIGNER`, `VERBOSITY_LEVEL`. But Task 7.1.1's `.plist.j2` template only sets `PORT`, `HOME`, `PATH` — and the config reads `CONSOLETTE_PORT` (or legacy `PROXY_PORT`), never bare `PORT`, so the port silently falls to default and, worse, **the Anthropic OAuth token is not passed at all → Anthropic auth fails on the first request after `make migrate`.** Story 6.3.1 ("mirror the current plist ... env") and Task 7.1.1 (only PORT/HOME/PATH) also contradict each other. — Make the plist template carry the full env set (OAuth token, AWS creds, all tuning vars), name the port var to match what the loader actually reads, and reconcile 6.3.1 vs 7.1.1 into one source of truth.

- [ ] **Back-compat env shim covers only 4 of the 10 live env vars — silent behavior regression (FR-2.4, FR-6.4).** Task 1.5.2 honors `PROXY_PORT`, `COOLDOWN_SECONDS`, `AWS_PROFILE`, `CLAUDE_CODE_OAUTH_TOKEN` only. The current `Config::from_env()` reads six more: `REQUEST_TIMEOUT`, `BEDROCK_MAX_RETRIES`, `STAPLER_COMPRESS`, `COMPRESS_FLOOR_BYTES`, `CACHE_ALIGNER`, `VERBOSITY_LEVEL`, `MEMORY_MAX_ENTRIES`, `AWS_REGION`. With the current plist (which sets `REQUEST_TIMEOUT`, `BEDROCK_MAX_RETRIES`, `STAPLER_COMPRESS`, `CACHE_ALIGNER`, `VERBOSITY_LEVEL`), those settings would silently revert to defaults post-rename. `AWS_REGION` is doubly exposed: bedrock now reads `options.aws_region` from TOML, so an operator relying on env `AWS_REGION` with an empty conf.d gets the hardcoded default. — Enumerate every currently-read env var and either map it in the shim or bake it into `Config::default()`; add a test asserting each legacy name still takes effect.

- [ ] **OpenAI-compatible endpoints are not migrated to the new Router — NFR-1 regression and orphaned handlers.** `main.rs` routes `/chat/completions` and `/v1/chat/completions` to `handle_openai_compat`, but Story 3.4.3 only rewires `handle_messages` and `handle_count_tokens` to `state.router.dispatch(...)` while replacing `AppState.fallback` with `Arc<Router>`. As written this either won't compile (handlers still reference the removed `state.fallback`) or leaves OpenAI clients bypassing the new router entirely — so weighted/rate-limit/model-gateway routing never applies to `/chat/completions`, directly violating NFR-1 ("wire-compatible with OpenAI clients, no client changes") and Success Metric 1's OpenAI-compatible upstream goal. — Add explicit tasks to migrate `handle_openai_compat` (and confirm `handle_dry_run`, `/v1/models`) onto the router seam, with an acceptance criterion covering the OpenAI path.

## Concerns

- [ ] **`ArcSwap<Config>` "reload-ready from day one" (ADR-001) is illusory and adds a divergence hazard.** The Router, `Vec<Arc<Upstream>>` (reqwest clients), `HealthRegistry`, and `RateLimiters` are all built once at startup and stored in `AppState` *outside* the `ArcSwap<Config>`. Swapping the Config would change only the top-level scalars handlers happen to read live — routing, upstreams, and limits would not change — and a per-request `state.config.load()` snapshot can diverge from the router that was built from the startup config. — Either drop ArcSwap and use a plain `Arc<Config>` for v1 (hot-reload is deferred anyway per research Q5), or state explicitly that hot-reload must rebuild+swap the *entire* derived AppState atomically, not just Config.

- [ ] **Rate-limit integration is double-specified and self-contradictory.** Story 3.3 makes rate limiting an `Availability` source (pure `is_available(idx) -> bool`, filters candidates *before* selection, per weighted-router research §5), while Story 4.3.2 calls `AdmissionControl::admit()` *after* selection and re-selects on `Shed` (rate-limiting research §3). `admit()` has a side effect (it charges governor cells), so it cannot serve as a pure `is_available` predicate, and governor has no non-committing peek used here. Running both means the RL-as-Availability seam is dead code, and the post-selection `Delayed`→retry path can double-charge tokens. — Pick one integration (post-selection `admit()` + `already_tried`, which cleanly reuses the cooldown exclusion) and delete the RL `Availability` source; document the accepted TPM double-charge on retries.

- [ ] **Per-upstream request counters are not generalized — Success Metric 2 is unverifiable for new upstreams.** `metrics/counters.rs` hardcodes `requests_anthropic` / `requests_bedrock` and increments by provider. Story 4.4 adds a per-upstream `rate_limits` map but leaves the *request* counters hardcoded, so a weighted split to `model-gateway`/`openai` produces no per-upstream request count — yet Success Metric 2 requires verifying the split ratio "by request counts in metrics." — Generalize the request counters to a per-upstream map keyed by upstream name (mirroring the `rate_limits` map), not just the rate-limit metrics.

- [ ] **Model Gateway upstream hard-depends on the SBN Dev Agent, whose reliability is unverified and whose failure modes are only documented, not handled.** Per `model-gateway-auth.md`, there is no real off-mesh bearer; Option A relies on a Java-oriented agent (`:9123`) whose clean non-Java operation and reboot survival are explicitly flagged MEDIUM-confidence, and everything requires VPN + `go/modelgateway` project + Gandalf membership. Epic 5's acceptance ("returns a completion") cannot run in CI or an unattended soak, and agent-down / VPN-off / Gandalf-401 / project-404 are only described in Story 5.3 docs. — Add a startup reachability probe for gateway upstreams that emits a clear, actionable error (distinguishing agent-down vs 401 vs 404), verify the agent survives a reboot before making it the paved path, and mark FR-5's end-to-end check as manual/gated in the validation plan.

- [ ] **Python `tomllib` portability (CD-1, FR-1.4, NFR-2) is asserted but never executably verified.** Story 1.2's acceptance claims "a Python `tomllib.load` of each example succeeds," but Task 1.2.4 only loads the fixtures via Rust `toml::from_str`; there is no Python step in the crate's test harness. The portability constraint is the whole reason TOML was chosen — it must be checked, not assumed. — Add a CI/test step running the research-provided `python3 -c 'import tomllib; tomllib.load(...)'` against every shipped `conf.d/*.toml` fixture.

- [ ] **Secret-leakage surface: schema permits inline plaintext secrets and the dashboard/metrics config rendering is uncovered (NFR-6, FR-2.3).** `SecretRef::Inline(String)` is allowed and the shipped `00-providers.toml` example (source-controlled into ndotfiles in Epic 7) uses an inline `token = "sk-dummy"`. `Debug` redaction (Task 2.1.1) protects logs, but nothing redacts auth blocks in `dashboard.rs` / `/metrics` if they render config, and nothing discourages a real inline token following the `sk-dummy` pattern into the repo. — Add a redaction pass wherever config is surfaced (dashboard, `/metrics`, `/health` diagnostics), and warn (or reject) on non-dummy `SecretRef::Inline`.

- [ ] **The `dashmap 5 → 6` bump is tree-wide, not the two maps the plan names.** Task 3.2.3 frames it as the health/metrics maps, but dashmap is used across `cache.rs`, `slots.rs`, `memory/`, `metrics/`, and the `mcp-proxy` binary. A major bump can break any of those call sites, and the plan's "low risk" note understates the surface. — Inventory every dashmap call site and confirm it compiles/tests on 6 as an early, standalone commit before the routing work depends on it.

- [ ] **The ansible install does not actually stop the old agent — 47000 double-bind risk (FR-6.2, FR-7.3).** Both `com.claude-proxy-rs` and `com.consolette` bind port 47000, but Task 7.3.3 is only a `debug` note telling the operator to unload the old agent "once"; nothing enforces it. If a playbook run loads `com.consolette` while `com.claude-proxy-rs` is still loaded, one crashloops under KeepAlive. Task 7.1.1 sets `RunAtLoad=true` while Story 6.3.1's plist sets `RunAtLoad=false` — another contradiction that changes cutover behavior. — Make the old-agent unload a real, idempotent task gated on its presence, load the new agent only after the old is confirmed stopped, and settle on one `RunAtLoad` value with a documented rationale.

## Minors

- ADR-001 `figment` has had no release since 2024; accepted with `config` 0.15 as the named fallback. Fine, but pin exactly and note the migration cost if it goes unmaintained.
- `rand` pinned to 0.8 for `WeightedIndex`; if any other dep pulls 0.9 the tree carries two `rand` versions. Verify the lockfile after adding it.
- Token estimation (tiktoken) is described as running once per request even when no upstream declares a TPM limit; gate it to only when a TPM limiter exists (NFR-3 per-request latency).
- A route pointing solely at an `internal` upstream passes `validate_references()` yet fails every request at runtime (Task 2.1.3). Add a startup warning when a reachable route resolves only to not-yet-implemented auth.
- Task 7.3.1's idempotent-build approach (stat source mtime vs binary) reimplements cargo's own change tracking and is fragile (spurious rebuilds or missed ones). Prefer letting `cargo build` decide and set `changed_when` on compile output.
- Arrays-replace deep-merge means "add one upstream" requires re-declaring the entire `[[upstreams]]` array (research config-layering §2). This is in mild tension with Success Metric 1's "zero code changes to add a new upstream" — true for Rust code, but document that adding an upstream means editing the whole array in the owning file.
- TPM `InsufficientCapacity` when a single request's estimate exceeds the bucket burst (rate-limiting §1/§4): ensure the plan's per-upstream guidance ("`tpm` >= largest expected request", clamp-or-shed residual) is captured as an operator note in `20-ratelimit.toml`, not just research.
