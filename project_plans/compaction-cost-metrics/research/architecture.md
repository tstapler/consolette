# Architecture Research: compaction-cost-metrics

Agent 3 (Architecture) — SDD Phase 2

## 1. The `CompactHooks` seam and its ADR-003 precedent

`src/session_compaction/hooks.rs:1-60`:
- `CompactionReport` (currently `tier: Option<CompactionTier>`, `tool_result_stats`, `summarizer_stats`, all `Default`) is handed to `post_compact` hooks. Adding token/cost fields here is additive and `Default`-compatible — no breaking change to the three call sites in `mod.rs` that construct it.
- `CompactHooks` is a two-method trait (`pre_compact(&SessionState)`, `post_compact(&SessionState, &CompactionReport)`), both default no-ops. `CompactHookRegistry` holds `Vec<Arc<dyn CompactHooks>>` and runs them **synchronously, in registration order**, inside `SessionCompactionPipeline::apply` while holding a `read()` guard on the session's `RwLock<SessionState>` (`mod.rs:96-99`, `150-153`). Any hook implementation must be non-blocking and infallible (no `Result`) — this constrains a cost-tracking hook to a cheap, synchronous accumulate-and-return.
- **Correction to the module doc comment**: `hooks.rs:3-4` says this "mirrors the existing `Vec<Arc<dyn Availability>>` seam from ADR-003." That's not literally what ADR-003 built — `Availability` (`src/routing/health.rs:27`, re-exported `src/routing/mod.rs:19`) is a single-method predicate trait with exactly one production implementor, `HealthRegistry`, held as a single `Arc<dyn Availability>` in the router, not a `Vec`. The actual "ordered vec of trait objects invoked in sequence" pattern in this codebase is `CompactHookRegistry` itself. This doesn't block the new feature — it just means "reuse the `CompactHooks` pattern" is the precedent to cite, not a literal ADR-003 `Vec<Arc<dyn Availability>>` that doesn't exist in code.
- **Recommendation**: implement cost accounting as a new `CompactHooks` implementor (e.g. `CostTrackingHook`) registered via `SessionCompactionPipeline::register_hook`, rather than hand-editing `apply()`'s body. This is exactly the seam the trait was built for and keeps `apply()`'s existing logic/tests untouched.

## 2. `SessionKey` and real `usage` tokens live in disjoint, unconnected code today

This is the most important finding for Phase 3 planning.

- `SessionKey` (`src/session_compaction/session_state.rs:24`) is defined and used **only** inside `src/session_compaction/*` and its own tests. `grep -rln "SessionKey" src` returns exactly `providers/mod.rs` (false positive — no, actually returns none outside session_compaction) — verified: only `session_state.rs`, `hooks.rs`, `mod.rs` reference it. No router, provider, or main.rs code constructs or threads a `SessionKey`.
- Real `usage.input_tokens`/`output_tokens` are extracted in exactly one place: `translate_anthropic_to_openai` (`src/providers/mod.rs:243-296`, tokens read at `267-274`). This is a **pure, stateless function** — `fn(&serde_json::Value) -> serde_json::Value` — with no request/session context parameter at all, and today **nothing calls it except its own unit tests** (`grep -rln "translate_anthropic_to_openai" src` → only `providers/mod.rs`).
- Tracing the call path backward: `Provider::send` (trait method, `providers/mod.rs:109`) is implemented by `anthropic.rs:539` and `bedrock.rs` (real `send_request`/`send_streaming_request` at `anthropic.rs:248,302`). `Router::dispatch` (`src/routing/router.rs:62-64`) takes `body: serde_json::Value` — **no `SessionKey`, no request-id parameter**. Neither `Router::dispatch` nor `Provider::send` know about sessions today.
- **There is currently no live HTTP proxy server assembling these pieces at all.** `src/main.rs` only wires a `Run` (prints config summary), `Mcp` (rmcp stdio server for `claude_code_session`), and `CompactSession` (offline transcript-compaction CLI) subcommand — no `axum::serve`/`TcpListener::bind` anywhere in the library crate. The only binary in this repo that runs an actual HTTP/axum server is `src/bin/mcp-proxy` (`main.rs`, `server.rs`), which is a **self-contained MCP-tool-proxy** (`mod` declarations, not `use consolette::…`) unrelated to `providers`/`routing`/`session_compaction` — it has its own `metrics.rs`. `src/metrics/mod.rs`'s `MetricsCollector`/`/metrics` JSON builder and `src/memory/mod.rs`'s `MemoryAppState` are explicitly documented as scaffolding for a future `AppState` ("designed to be held in an `Arc<MetricsCollector>` in `AppState`", `metrics/mod.rs:65`; "called from main.rs after AppState is wired up", `memory/mod.rs:73`) that doesn't exist yet.
- **Consequence**: `SessionCompactionPipeline::apply` is not currently invoked from any live request path either — its only callers are its own unit tests. This feature is being designed one layer ahead of where the proxy's end-to-end request wiring currently stands.

## 3. Existing `/metrics` and CLI patterns to mirror

- `src/metrics/mod.rs`: `MetricsCollector` (held as `Arc<Self>`) exposes `to_metrics_json(&self) -> serde_json::Value` (`mod.rs:233-283`), a single pure aggregation function that both a future axum handler and any other consumer would call — this is precisely the "one function, two callers" shape the requirements ask for. `ProxyMetrics` (`counters.rs:13-67`) is a flat struct of `AtomicU64`s with a `to_json()` method; it is explicitly *not* keyed by session (confirmed: no `HashMap`/`DashMap`/`moka` in `counters.rs`), which is why the requirements' "Alternatives Considered" correctly rejects retrofitting it.
- No axum route registration for `/metrics` exists yet anywhere in the tree (`grep -rn "route(\"/metrics"` → no hits); `dashboard.rs` has an `Html`-returning handler but no confirmed router wiring either. So there is no established "`/metrics`-endpoint conventions" to literally copy for path/verb — the convention to copy is the **shape** (`to_json()`-style pure aggregation method returned as `serde_json::Value`, callable independent of any router), not an existing live route.
- CLI: `src/main.rs`'s `Command` enum (clap derive, `#[derive(Subcommand)]`, `main.rs:20-35`) is the pattern for a new subcommand — e.g. `CostReport { session: String }` — dispatched from the `match` in `main()` (`main.rs:43-50`) to a new async handler function, mirroring `compact_session_command` (`main.rs:88-113`).

## 4. Reconciling pre-request counterfactual with post-response actual usage

The core data-flow problem: `SessionCompactionPipeline::apply` runs pre-request (has pre-compaction `messages: &Value`, can tokenize-and-estimate the counterfactual immediately) but real `usage.input_tokens` only exists after the provider responds, in a different module (`providers::translate_anthropic_to_openai` or wherever the raw Anthropic JSON is first parsed) that has no `SessionKey` or session-scoping concept today.

**Options evaluated:**

1. **Fire `post_compact` after the response instead of before it.** Rejected — `post_compact`'s existing contract and callers (`mod.rs:150-153`) run it synchronously at the end of `apply()`, before the request is even sent; moving it would require `apply()` to await the network round trip, coupling compaction (fast, hot-path bookkeeping) to provider latency and changing an established, tested hook-firing contract for existing consumers (`ConversationSummarizer`/reinjection state updates run before `post_compact` fires, keyed to *this* `apply()` call, not to a future response).
2. **A per-request-id staging area (`DashMap<RequestId, CounterfactualEstimate>`) that `apply()` writes into and a new `record_actual_usage(request_id, usage)` call (inserted into the provider response path) reads from, joins, and clears.** Correctness-wise this needs a `RequestId` that's generated once and threaded through both `apply()` and the eventual provider-response handling — which today doesn't exist (see §2) but is the natural next primitive whenever the request path is actually wired up (`Router::dispatch`/`Provider::send` would need to accept and propagate one `RequestId` alongside `SessionKey`). Risk: orphaned entries if the response never arrives (timeout/failover) — needs a TTL eviction (the same `moka` pattern, short TTL matching request timeout, not the 1hr session TTL) so a staging entry that never gets joined doesn't leak.
3. **A separate `record_actual_usage(session_key, request_id, usage)` call site inserted directly into the provider response path**, writing the *actual* figure into the same per-session aggregator keyed by `SessionKey` (not a separate staging map), with the counterfactual written into the aggregator by `apply()`'s `post_compact` hook under the same `(SessionKey, RequestId)` composite. The aggregator itself absorbs the "join" — each field is written independently and the aggregator's read side (CLI/API) combines whatever has arrived so far, with a per-record flag for which side is populated yet (satisfies the requirements' `exact` vs. `estimated` per-field provenance requirement organically, since "actual not yet arrived" is just another provenance state, not a separate mechanism).

**Recommendation**: option 3, generalized — the aggregator (§5) stores one row per `(SessionKey, RequestId)` inside its per-`SessionKey` cache entry (a small bounded `Vec`/ring, not unbounded — matching the "no new scaling requirement" NFR), with two independently-settable fields (`counterfactual_tokens: Option<TokenEstimate>`, `actual_tokens: Option<Usage>`). `apply()`'s `post_compact` hook writes the counterfactual side immediately (cheap, synchronous, tiktoken-only — no network). A new, separate call — `record_actual_usage(&SessionKey, RequestId, Usage)` — is inserted wherever the real Anthropic/OpenAI response is first parsed (today: nowhere live; the call site to add is the future equivalent of `translate_anthropic_to_openai`'s usage extraction, or immediately after `Provider::send` returns in `Router::dispatch` once that function is extended to carry a `SessionKey`). This keeps `apply()` free of any await-the-response coupling (satisfies the "no added latency" constraint trivially — the write is a synchronous cache mutation either way) and requires only a `RequestId` to be generated once per request and threaded through both call sites — the one new piece of plumbing this feature actually needs, and unavoidable given `SessionKey` doesn't reach the response path at all today. **This dependency (threading `SessionKey`/`RequestId` into `Router::dispatch`/response handling) should be called out explicitly to Phase 3 as in-scope plumbing work**, since it doesn't exist yet independent of this feature.

## 5. Where the aggregator and pricing table should live, and the shared-function design

- **New top-level `src/cost_metrics/` module**, not `src/session_compaction/cost_tracking.rs`. Rationale: `session_compaction`'s existing docs (`mod.rs:1-20`) scope that module tightly to "message-list compaction" (tiered budget, summarizer, reinjection) tied to issue #7; cost accounting is a *consumer* of `CompactionReport` via the public `CompactHooks` seam, not an internal compaction concern, and it also needs to record data from a completely different subsystem (the provider response path, §4) that has nothing to do with compaction. Mirroring `src/metrics/` (sibling top-level module, `pub mod counters`) as the closest analog keeps `session_compaction` from growing a second responsibility and matches this repo's existing pattern of one top-level module per bounded concern (`ratelimit`, `metrics`, `routing`, `providers`).
- Suggested internal shape: `src/cost_metrics/mod.rs` (public API: `CostTracker`, `record_estimate`/`record_actual_usage`, `report_for_session`), `src/cost_metrics/pricing.rs` (built-in static table + config override + optional live-refresh background task per the stack research's LiteLLM-JSON recommendation), `src/cost_metrics/store.rs` (the `moka::future::Cache<SessionKey, Arc<RwLock<CostRecord>>>`, copy-pasted structurally from `session_state.rs:52-75` — same `max_capacity(1000)`/`time_to_live(1hr)` per the NFR).
- **One shared aggregation function**, analogous to `MetricsCollector::to_metrics_json`: `CostTracker::report_for_session(&self, key: &SessionKey) -> CostReport` (a plain `serde_json::Serialize`-able struct, not raw `Value`, to make the "CLI and API agree" success metric type-checked rather than string-matched). The CLI subcommand handler (`main.rs`) calls it and pretty-prints/`serde_json::to_string_pretty`s the result; a future axum handler (`State<Arc<CostTracker>>` extractor, mirroring `memory::MemoryAppState`'s `State<Arc<MemoryAppState>>` pattern at `memory/mod.rs:152,179`) calls the same function and returns `Json(report)`. Both surfaces stay thin wrappers with zero duplicated aggregation logic, satisfying the "share one function" open question directly.
- Because no axum server/router exists yet to attach a route to (§2), the HTTP endpoint's *handler function* should be written and unit-testable in isolation now (it only needs `State<Arc<CostTracker>>` + `Path<String>` for the session key), with actual `.route("/cost/:session_id", get(handler))` registration deferred to whenever the main proxy's `AppState`/router gets assembled — same deferred-wiring state `MemoryAppState`'s handlers are already in.

## Summary of key findings for Phase 3

- Implement cost accounting as a new `CompactHooks` implementor registered on `SessionCompactionPipeline`, not by editing `apply()` directly — extend `CompactionReport` with token/cost fields (backward-compatible, `Default`-preserving).
- `SessionKey` and real provider `usage` tokens are currently threaded through completely disjoint code paths with no live connection — reconciling them requires adding a `RequestId` and threading `SessionKey` into the provider-response path, which doesn't exist as a call site yet. This is unavoidable plumbing work Phase 3 must scope explicitly, not an implementation detail.
- Neither the main HTTP proxy server nor its `/metrics` endpoint is actually wired up anywhere in this codebase today (only `MetricsCollector`/`MemoryAppState`-style scaffolding exists) — the new HTTP endpoint should be built as a router-agnostic handler function following the `MemoryAppState`/`State<Arc<T>>` pattern, ready to attach whenever that wiring lands, rather than assuming an existing route to extend.
- New aggregator belongs in a new top-level `src/cost_metrics/` module (sibling to `metrics`/`ratelimit`), reusing `SessionStateStore`'s exact `moka::future::Cache` shape, with one shared `report_for_session` function consumed by both the CLI subcommand and the future API handler.
