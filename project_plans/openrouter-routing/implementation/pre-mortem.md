# Pre-mortem: openrouter-routing
**Date**: 2026-09-07

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The composite formula's bench component is effectively inert in production because aider-polyglot's leaderboard has sparse coverage of the specific free models OpenRouter actually surfaces, so most candidates default to `bench_score = 0.5`, silently collapsing the intended 3-signal (latency/error/bench) design into a 2-signal one. | `/metrics`' `openrouter_scoring.models` block shows `bench_rank` at the neutral default for nearly every model, and the once-per-model "not in BENCH_TABLE" `tracing::warn!` (Task 4.2.1c) fires for most candidates within days of first deploy. | Before Phase 4 implementation, compute and record the actual *coverage ratio* (live free models with a bench entry ÷ total live free models, from Task 1.2.2a's confirmed list) as an explicit go/no-go note in plan.md — if it's low, either lower `WEIGHT_BENCH` accordingly or add one aggregate startup log line reporting the ratio, rather than only the per-model debug noise. | P2 |
| 2 | Epsilon-greedy's 10% random exploration is statistically correct but reads as unexplained misbehavior in a live interactive coding session: roughly every 10th Claude Code request silently dispatches to a weak/verbose free model instead of the scored-best one, with no visible signal distinguishing "this was exploration" from "the score is wrong" — because the request still counts as a success to `record_outcome`. | Occasional bad completions (wrong format, truncated, tool-schema ignored) with no correlating error in logs or `/metrics`; only the `debug`-level "candidate selected" log line (Story 5.1.4) would show it, and nothing marks that line as an exploration pick versus a greedy one. | Add an `explore: bool` field to Story 5.1.4's log line, `RequestDetail`, and `observability_snapshot()` so an exploration dispatch is distinguishable after the fact from a scoring failure — this is a single boolean, not the "general configurable weighting system" ADR-003 already declined to build. | P2 |
| 3 | ADR-002's foundational assumption — "OpenRouter's free-tier rate limits are account-wide, not per-model" — is sourced from `research/pitfalls.md` and is unconfirmed against OpenRouter's live behavior; plan.md's own Unresolved Questions section already flags this as a "watch item, not a blocker" with no owning story or task. If it's wrong, whole-upstream `HealthRegistry` cooldown (the entire justification for rejecting a per-model rate-limit registry) cools down every free model in the pool whenever a single model gets individually throttled, converting isolated per-model limiting into full-pool `Exhausted` outages far more often than ADR-002 assumes. | Frequent, clustered `ProviderError::Exhausted` responses that correlate with a burst of traffic to only one model id (visible via `RequestDetail.selected_model` history and `/metrics` cooldown state), not with genuine account-wide exhaustion. | Promote the ADR-002 "watch item" from an unowned note to an owned validation task: capture at least one live 429 response's headers/body for a single free model under sustained load and confirm whether OpenRouter's error signature is per-model or account-wide, before or immediately after initial ship — not left for "whoever next touches `record_outcome`." | P2 |
| 4 | `BENCH_TABLE` is a hand-transcribed, hardcoded Rust const with no refresh mechanism, staleness signal, or removal path; as OpenRouter's free-model catalog churns (the exact premise motivating this feature), the table silently drifts — new free models score at the neutral default forever unless someone edits and recompiles, and rows for retired models become dead weight nobody notices to prune. | Months post-ship, `/metrics`' `openrouter_scoring.models` block shows only the handful of model ids present at ship time carrying real bench scores, while every newer model id shows the neutral default — with no metric distinguishing "never looked up" from "genuinely mediocre." | Add a cheap staleness signal now: a `BENCH_TABLE_RETRIEVED` date constant checked at startup against wall-clock, logging one `tracing::warn!` if older than a few months — visible decay instead of silent, and independent of whether the config-layer override mechanism (already flagged by adversarial-review as missing) is ever built or used. | P3 |
| 5 | OpenRouter routes a single model id across multiple independent backend providers/hosts, so per-model rolling latency/error stats actually conflate several backends with different real performance into one bucket. The composite score's real discriminative power in production may be far weaker than unit tests suggest, since those tests use clean, single-source synthetic samples per model — much of the variance a live model shows may be intra-model (which backend got picked this call), not inter-model. | The composite score clusters near the neutral middle for most models, or the "winner" oscillates without stabilizing over days of real traffic — contradicting the Success Metric "measurably shifting traffic away from a model as its live signal worsens," with nothing in `/metrics` to explain why. | Document this as a residual signal-quality risk in plan.md's Risk Control (not a code defect — there's nothing to structurally fix). Add one diagnostic to `observability_snapshot()`: the rolling stddev/IQR of a model's latency samples alongside its p50, so a high-variance (backend-mix) model is visible and distinguishable from a genuinely bad one. | P3 |
