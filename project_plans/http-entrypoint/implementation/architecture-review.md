The one true compile-breaking defect found (see Concerns, first item) is trivial to fix during implementation and doesn't require restructuring the plan, so it's filed as a Concern rather than a Blocker — but it must be corrected before Story 3.1.1's tasks are implemented as literally written.

## Concerns

- **Story 3.1.1 / Task 3.1.1.2 — `translate_and_record` called with an argument it doesn't accept** — the plan's Task 3.1.1.2 and the Domain Glossary (plan.md:43) both call `translate_and_record(&state.cost_tracker, &session_key, request_id, &model, &json).await`, passing `model` as a fourth positional argument before `&json`. The actual function (`src/providers/mod.rs:335-340`) has the signature `translate_and_record(tracker: &CostTracker, session_key: &SessionKey, request_id: RequestId, anthropic: &serde_json::Value) -> serde_json::Value` — four parameters total, no `model` parameter; it derives `model` internally from `anthropic.get("model")` (mod.rs:343-346). As written this is an arity mismatch that fails to compile. **Remediation**: either (a) add Task 3.1.1.0 to extend `translate_and_record`'s signature with an unused `_model: &str` parameter, mirroring the exact pattern already used by its sibling `record_actual_usage_from_anthropic_response` (`src/cost_metrics/mod.rs:46-51`, which documents *why* it keeps an unused `_model` param — "signature parity with plan.md's Task 2.2.1b"), or (b) drop the extra argument in Task 3.1.1.2's call and rely on the function's existing internal `model` extraction. (b) is less code to write and doesn't touch a function outside this feature's `src/entrypoint/` module; (a) matches the sibling function's precedent more closely if a future caller needs the caller-supplied model rather than the response's own `model` field. Either is a one-line fix, but the plan as written names a signature that doesn't exist in the codebase.

- **`CostTrackingStream` (Story 2.2.1) accretes a third responsibility in Story 2.2.3 without a re-evaluation of the Decorator choice** — the Pattern Decisions table justifies Decorator for "the cost-tracking mid-stream tee" as a single concern (byte passthrough + usage extraction). Story 2.2.3 then adds mid-stream error-to-SSE-frame synthesis into the *same* struct's `poll_next` (Task 2.2.3.1), justified only by a one-line file-location comment ("co-located ... since both wrap the same stream"). The resulting type now does three things in one `poll_next` state machine: (1) transparent passthrough, (2) SSE frame-scanning for usage extraction, (3) error-to-frame synthesis and stream termination on the requirements.md Rabbit Hole path ("streaming failover boundary... easy to get subtly wrong and worth explicit test coverage"). Combining exactly the highest-risk logic named in the requirements doc into the most complex existing type increases the chance a change to one concern (e.g. adjusting the error-frame format for Story 3.2.2's OpenAI-side reuse) silently perturbs the other (usage extraction timing). **Remediation**: split into two composable Decorators — an `ErrorFramingStream<S>` (wraps the raw provider stream, converts `Err` into a synthesized `event: error` frame and terminates) applied first, then `CostTrackingStream<ErrorFramingStream<S>>` applied second (scans the now-error-frame-annotated byte stream for usage, including recognizing the synthesized `error` event as an end-of-stream-without-`message_stop` case). This keeps each `poll_next` implementation testable against one concern in isolation (satisfies Lens 1 testability item 4) and still composes into the same one-line `Body::from_stream(...)` call site.

- **Ad hoc `body.get(...)` field extraction duplicated across two handlers, no shared parse-at-boundary helper** — `post_v1_messages` (Task 2.1.1.1) and `post_v1_chat_completions` (Task 3.1.1.1) each independently pull `stream`/`model` out of a raw `serde_json::Value` inline (`body.get("stream").and_then(|v| v.as_bool()).unwrap_or(false)`, and an unspecified equivalent for `model` in Task 3.1.1.1). Nothing pins these two extraction sites to agree on defaults or field names if the request shape needs a third field later (e.g. reading `max_tokens` for `est_tokens`, per Task 2.1.1.2's heuristic). This is Lens 2's "parse-at-boundary" concern: raw `serde_json::Value` is an acceptable choice here since `Router::dispatch` itself takes `serde_json::Value` (an existing, already-shipped ADR-003 contract this plan correctly avoids re-litigating), but the *duplicated ad hoc field-plucking* is the gap, not the choice of `Value` itself. **Remediation**: add one shared helper in `src/entrypoint/mod.rs` or a small `request_meta.rs`, e.g. `fn request_meta(body: &serde_json::Value) -> RequestMeta { RequestMeta { stream: ..., model: ... } }`, called once per handler immediately after `Json` extraction, so both endpoints read the same two fields the same way. Small addition, not a restructure.

- **Unresolved Question in plan.md is a real ambiguity that should be pinned before Phase 1, not deferred to "the feature owner should confirm"** — the plan's own Unresolved Questions section flags that "warn and use the first route on multiple `Route`s" is a judgment call. Given this plan is going straight to implementation without a validate-phase adversarial pass on this specific point, and Task 1.1.2.5's unit tests already assert on this exact behavior (multi-route config uses route 0), this should be confirmed by Tyler now, not discovered as a surprise during Phase 4 review. Not a structural defect — flagged here only because Phase 4 has no dedicated task to re-confirm it before merge, so it could ship un-reviewed if the answer changes.

## Nitpicks

- `CompactionTier::Off`'s cross-feature reuse (ADR-016) is explicitly flagged in the plan already — good practice — but note for future maintainers: if session-compaction ever needs `Off` to trigger tier-specific behavior (e.g. a metrics dashboard filter), that behavior will now also fire for every HTTP-entrypoint request. No action needed now; worth a one-line comment at the `CompactionTier` enum definition pointing back at ADR-016 if one doesn't already exist there.
- `estimate_tokens` (Task 2.1.1.2) is a body-length/4 heuristic with no corresponding heuristic defined for the OpenAI-compat path (Story 3.1.1's tasks don't mention `est_tokens` at all) — worth confirming Task 3.1.1.1/3.1.1.2 reuse the same `estimate_tokens` helper rather than omitting the admission-control token estimate on that path entirely.
- The Domain Glossary's `translate_and_record` row (plan.md:43) should be corrected alongside the Task 3.1.1.2 fix above, since it currently documents the same non-existent 5-argument call shape.
