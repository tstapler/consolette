# Research: comparable features, edge cases, unstated needs

Agent 2 (Features) — SDD Phase 2, `compaction-cost-metrics`

## 1. Industry patterns (LiteLLM / Helicone / Portkey)

- **LiteLLM** ([docs.litellm.ai/docs/proxy/cost_tracking](https://docs.litellm.ai/docs/proxy/cost_tracking), [DeepWiki cost-calc](https://deepwiki.com/BerriAI/litellm/2.6-cost-calculation-and-model-pricing)) is the closest analog to what's being asked here: a central pricing table (`model_prices_and_context_window_backup.json`, fetched live from GitHub with a local fallback — i.e. exactly the "static table + optional live refresh, degrade cleanly" shape this feature's constraints already call for), a `token_counter()` that picks a provider-appropriate tokenizer (tiktoken for OpenAI, a separate Anthropic-specific counter — **not** tiktoken — for Claude), and a `completion_cost()` that combines the two. Session/user attribution is done via request metadata tags (`user_id`, `session_id`) rather than a derived key, and the proxy injects a per-response `x-litellm-response-cost` header for immediate visibility in addition to the aggregated dashboard. This validates two design choices: (a) static-table-first with live-refresh-as-enhancement, and (b) surfacing cost inline per-request, not just in a batched aggregate — worth considering as a cheap addition to the `CompactionReport` even though the requirements only call out CLI+endpoint.
- **Helicone** ([cost-tracking cookbook](https://docs.helicone.ai/guides/cookbooks/cost-tracking)) draws a sharp accuracy line consolette should mirror explicitly: gateway-integrated usage gets "precise" costs from real response `usage`; proxy/logging-only usage gets "best-effort estimates." That's the same `exact` vs. `estimated` split the requirements' Observability Requirements section already specifies — validates labeling per-figure provenance rather than one blended number.
- **Portkey** bundles cost into a broader FinOps/gateway dashboard; less relevant to the token-accuracy question but confirms per-model/per-app breakdown (not just cumulative) is the norm in this product category — relevant to the "unstated need" below (§5).
- Common thread across all three: none of them treat "would it have cost more without X" as a first-class metric — they report actual spend, optionally split by dimension (user/model/key), not a counterfactual comparison. Consolette's actual-vs-counterfactual framing is unusual in this space; it's closer to an A/B-style "compaction dividend" report than a standard cost dashboard, and there's no off-the-shelf UX pattern to copy for that specific comparison. Design should not assume users are familiar with this framing — plan for the comparison itself needing more explanation than a raw cost number would.

## 2. Pricing API feasibility — confirmed dead end (resolves the requirements' Open Question)

Web research (August 2026) confirms Anthropic does **not** publish a machine-readable pricing endpoint: `/v1/models` returns only model identifiers/metadata, not pricing, and the canonical source remains the human-readable `claude.com/pricing` page. LiteLLM's own approach — a maintained JSON file fetched from GitHub with a local backup — is the closest thing to a "live lookup," and even that is really "someone else's maintained static table," not a provider API. **Phase 3 should plan around a static/config-overridable table only; the "optional live lookup" in the requirements' Scope should be scoped down to, at most, fetching LiteLLM's public pricing JSON as a convenience refresh — not a call to Anthropic/OpenAI directly** (no such endpoint exists to call). This should be stated plainly in the plan rather than left as a spike, since it was answered here.

## 3. Tokenizer feasibility — tiktoken confirmed inaccurate for Anthropic, with a better option already latent in this repo

- Confirmed via search: Anthropic's own guidance (their TypeScript tokenizer package) states their pre-Claude-3 algorithm "is no longer accurate" for Claude 3+ and explicitly recommends relying on `usage` in the response body instead. Independent testing found tiktoken and character-count heuristics both have "much higher error rates" than Anthropic's real counts. This confirms the Rabbit Hole in requirements.md is real and not overstated — tiktoken-based counterfactual estimates should be labeled `estimated` unconditionally, never presented with the same confidence as real `usage.input_tokens`.
- `tiktoken-rs` ([github.com/zurawiki/tiktoken-rs](https://github.com/zurawiki/tiktoken-rs)) is actively maintained but is explicitly scoped to OpenAI models only; it's a reasonable dependency choice for the OpenAI-counterfactual case and an *approximation-only* choice for the Anthropic case. Its current release requires Rust 1.85+ (Rust 2024 edition, vendored upstream) — worth a quick MSRV check against this crate's toolchain before Phase 3 locks it in.
- **Important latent capability already in this codebase**: `src/metrics/counters.rs` already has `count_tokens_total`/`count_tokens_failures` fields, and `src/dashboard.rs:227,245` documents that these track "count_tokens Health" because "count_tokens drives Claude Code auto-compaction." This strongly implies the codebase already calls (or is designed to call) Anthropic's real `/v1/messages/count_tokens` endpoint somewhere in the Claude Code integration path — which would give an **exact**, non-approximated token count for the counterfactual (uncompacted) message array, at the cost of a real network round-trip per estimate. I could not find an actual call site (`grep` for `count_tokens` only turned up the counter fields and dashboard HTML, not an HTTP call), so this may be a currently-unimplemented counter or implemented in a part of the codebase I didn't reach — **Phase 3 should verify whether this endpoint is already wired up anywhere before committing to tiktoken as the only option**. If it exists, it's a strictly better source of truth for the counterfactual than tiktoken and could be used for a slower/background "exact re-estimate" reconciliation pass, while tiktoken stays as the cheap inline estimate — this maps directly onto the existing `exact` vs. `estimated` distinction requirements.md already wants surfaced.

## 4. Codebase structure — where "before" and "after" live, and why they don't line up in one function call

Read: `src/session_compaction/mod.rs`, `src/session_compaction/hooks.rs`, `src/session_compaction/session_state.rs`, `src/providers/mod.rs:245-294`, `src/metrics/counters.rs`, `src/ratelimit/mod.rs:1-35`, `src/main.rs`.

- **Pre-compaction ("before") message array** is available synchronously inside `SessionCompactionPipeline::apply(&self, session_key: &SessionKey, messages: &Value, pressure_pct: f32)` ([src/session_compaction/mod.rs:87-92](/Users/tstapler/code/github.com/tstapler/consolette/src/session_compaction/mod.rs)) — `messages` is the full pre-compaction array, cloned once already at line 107 (`let mut out = messages.clone();`) before any tier logic runs. This is the only place the uncompacted array exists in full; by the time a response comes back, it's gone unless something snapshots a size/token-count here.
- **`CompactionReport`** ([src/session_compaction/hooks.rs:19-24](/Users/tstapler/code/github.com/tstapler/consolette/src/session_compaction/hooks.rs)) is built and handed to `post_compact` hooks entirely within `apply()`, before the request is ever sent upstream — it currently has no field for "actual tokens used," and structurally cannot, since that number doesn't exist yet at this point in the pipeline.
- **Real `usage.input_tokens`/`output_tokens`** only exist in `src/providers/mod.rs:267-275`, inside the Anthropic→OpenAI response-shape translation function, which runs strictly *after* the upstream HTTP round trip completes — a different call, a different point in time, and (per `apply()`'s signature) not passed a `SessionKey` at all today. **These two pieces of data structurally cannot be reconciled inside one function call** — the design has to either (a) pass a request/correlation ID out of `apply()` and back into wherever the response is handled so the aggregator can pair them, or (b) have both call sites independently write into the same `SessionKey`-keyed aggregator using session identity as the join key instead of a request ID, accepting that a session with concurrent in-flight requests could pair actual-A with counterfactual-B if ordering isn't preserved. The two-writes-one-key approach mirrors the existing `SessionStateStore` pattern most cleanly, but needs a documented decision on what happens if the "after" write never arrives (see failure modes below) — Phase 3 must pick one and state why.
- **`SessionStateStore`** ([src/session_compaction/session_state.rs:52-75](/Users/tstapler/code/github.com/tstapler/consolette/src/session_compaction/session_state.rs)) is the concurrency pattern to mirror exactly: `moka::future::Cache<SessionKey, Arc<RwLock<T>>>`, `get_or_default` returns/creates the `Arc<RwLock<_>>`, callers take short-lived `.read()`/`.write()` guards rather than holding the cache lock itself. `max_capacity(1000)`, `time_to_live(1 hour)`. A new `SessionCostAggregator` should use the identical shape (`Cache<SessionKey, Arc<RwLock<SessionCostStats>>>`) rather than inventing a new one — this also means it inherits the same TTL/eviction failure mode discussed below for free, for better or worse.
- **No HTTP server/router currently exposes `/metrics`.** `src/main.rs` only defines three CLI subcommands (`Run`, `Mcp`, `CompactSession`) — there is no `axum::Router` wiring a `/metrics` handler today, even though `src/metrics/mod.rs:228-231` builds the JSON payload `to_json()` is meant to serve and `axum`/`tower` are already dependencies. `axum::Router::new()` appears in `src/mcp_gateway.rs` and `src/routing/router.rs`, but neither currently registers a metrics-style route. **This matters for planning the new HTTP endpoint**: it can't simply be "added next to the existing `/metrics` route" because that route isn't wired into a running server yet in this snapshot of the repo — Phase 3 needs to either locate where that wiring is meant to land (possibly a not-yet-implemented proxy-serving path) or explicitly scope "wire up the metrics/cost HTTP surface for the first time" into this feature's plan rather than assuming it already exists.

## 5. Edge cases and failure modes

1. **`CompactionTier::Off` sessions have no counterfactual to compute** — nothing was elided, so "tokens without compaction" *is* "tokens with compaction." The aggregator must special-case this (actual == counterfactual, savings == 0, not "counterfactual estimation failed") rather than either omitting the session from output or reporting a spurious zero-vs-real diff that looks like a bug.
2. **Non-text content blocks defeat text tokenizers.** Anthropic messages routinely carry `tool_use`, `tool_result`, and image blocks (`src/session_compaction/mod.rs`'s own test fixtures use `tool_result` blocks throughout). tiktoken only tokenizes text; a naive `serde_json::to_string` + tokenize approach will count JSON structural overhead as if it were prose, and images have no token-count relationship to their byte size at all (Anthropic prices/tokenizes images by a resolution-based formula, not a text encoding). The estimator needs an explicit per-block-type strategy (text blocks → tokenizer; tool_use/tool_result → count the serialized text but flag lower confidence; images → either a documented fixed-cost approximation or explicit "unsupported, excluded from estimate" with a visible caveat) rather than silently mis-tokenizing structured JSON as text.
3. **Concurrent `apply()` calls on the same `SessionKey`.** `SessionStateStore`'s `Arc<RwLock<SessionState>>` pattern already handles this for compaction state; a new aggregator must use the same per-session lock rather than a global one, and increments (actual/counterfactual token deltas) must be applied under a write-guard as atomic read-modify-write, not read-then-write-later, or concurrent requests to one session (e.g. two tool calls interleaved) can lose an increment.
4. **The actual-usage write can arrive after, or never.** Since `apply()` runs before the request and `usage.*` arrives only after a successful response, a request that times out, errors upstream, or gets cancelled will produce a counterfactual estimate with no matching actual figure. The aggregator needs a defined behavior for orphaned counterfactuals — most likely: don't count them toward cumulative "actual" totals at all until a matching real usage report lands, and expose a distinct "pending/unreconciled" count so operators can tell the difference between "no compaction happened" and "the reconciliation is incomplete."
5. **Session TTL eviction loses accumulated stats mid-comparison.** Same 1-hour TTL as `SessionStateStore` (explicitly accepted as in-scope behavior per the requirements' Out of Scope: "no long-term persistence"). But the observable failure mode operators will actually hit is: query the CLI/endpoint for a session that compacted heavily an hour ago, and it's silently gone with no distinguishing error from "session key never existed." The endpoint/CLI should return a clear "not found (or expired)" rather than an empty/zeroed report that looks like "no compaction happened, no savings" — those two states must not be visually identical to the operator.
6. **Multi-provider/multi-model sessions.** A session could switch models mid-conversation (e.g. Claude Code falling back Anthropic→Bedrock, or a routing config that changes upstream over the session's life — `src/routing/router.rs`'s fallback-switch counter already tracks this scenario at the global level). The pricing table is keyed by model, so cumulative per-session cost must be a sum of per-request (model, actual_tokens) × that model's rate, not "total tokens × one rate" — the aggregator needs to store the model identifier alongside each accounting entry, not just a running token count, or a session that used two different-priced models will get silently wrong dollar totals.
7. **Pricing table gaps.** A model absent from the static/config table (new model release, typo in config override) needs a defined fallback — likely: surface tokens with cost as `null`/`unavailable` rather than defaulting to $0 (which would look like a real "free" result and corrupt cumulative dollar sums) or panicking.

## 6. Unstated needs beyond the literal requirements

- **Breakdown by tier over time, not just cumulative totals.** The Problem Statement's own stated goal is "tune compaction tier thresholds (`TierThresholds`) with real evidence" — but a single cumulative actual-vs-counterfactual number per session can't answer "was `Full` tier worth it compared to `Auto`?" if a session passed through multiple tiers over its life (which `tier_for_pressure` makes routine — pressure rises over a conversation, so most long sessions will cross Off→Micro→Auto→Full). The aggregator likely needs to bucket accumulated actual/counterfactual by `CompactionTier` (or at minimum, by which tier was active per `apply()` call, since `CompactionReport.tier` is already recorded), not just one running total — otherwise the feature answers "did compaction help this session overall" but not the tuning question the user actually stated as their motivation.
- **Per-request cost visibility, not just per-session aggregate.** LiteLLM's inline `x-litellm-response-cost` header pattern suggests operators often want the cheapest possible per-call signal in addition to a batched report. Not explicitly asked for, and explicitly out of scope per "no UI beyond CLI/endpoint," but worth flagging in Phase 3 as a near-zero-cost addition if the per-`apply()` accounting data is being computed anyway.
- **A visible warning when the estimate itself is questionable**, distinct from the already-required `counterfactual_is_estimated` flag: if a session is dominated by non-text content (tool results, images) that the tokenizer can't count reliably, the confidence label should degrade further than a blanket "estimated" — e.g., surfacing what fraction of the counterfactual's content was actually tokenized vs. approximated, so the operator doesn't over-trust a number computed mostly from images.
- **Distinguishing "no compaction ran" from "compaction ran but saved nothing."** Both `CompactionTier::Off` sessions and pathological `Full`-tier sessions that happened to have nothing eligible to elide will report zero savings; operators tuning thresholds need to tell these apart, which argues for surfacing the tier(s) that ran (see bullet 1 above) as a first-class part of the comparison output, not an afterthought.
