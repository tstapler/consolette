# Validation Plan: gemini-provider

**Date**: 2026-09-04

## Happy Path Scenario
Given a `kind = "gemini"` upstream configured in `conf.d` with a valid, unexpired
`~/.gemini/antigravity-cli/antigravity-oauth-token` and `project_id`, when Tyler sends a
non-streaming `/v1/messages` request that the router dispatches (via `Strategy::Fallback`) to the
`gemini` candidate, then `GeminiProvider::send()` translates the Anthropic request into a
`CloudCodeEnvelope`, POSTs it to `v1internal:generateContent`, strictly parses the 200 response,
translates it back into an Anthropic-shaped `content`/`stop_reason: "end_turn"`/`usage` response,
and the request shows up correctly attributed under `"gemini"` in `/metrics` — with zero
Gemini-specific code anywhere in the dashboard/metrics pipeline.

## Test Stack Notes (read before the table)
- **No HTTP-mock crate exists in this repo today** (`Cargo.toml` has no `wiremock`/`httpmock`/
  `mockito`; confirmed via `grep -n dev-dependencies -A5 Cargo.toml`). The existing provider test
  modules (`src/providers/openai.rs:539+`, `anthropic.rs:644+`, `bedrock.rs:933+`) test pure
  translation/stream functions and `build_headers` directly — none spins up a real listener and
  drives `send()` over the wire; `test_provider()` helpers point `base_url` at
  `"https://example.invalid"`, which is never actually dialed.
- **Resolved (2026-09-04, Phase 4 engineering-lens repair loop): plan.md's Tasks 1.3.4f and 2.1.2b
  are scoped to option (b) below, not a mocked-HTTP-server integration test.** The original task
  phrasing ("integration test using a mocked HTTP server") was new territory relative to existing
  precedent and would have required `GeminiProvider`'s `base_url` to be constructor-injectable
  (Task 1.3.4a hardcodes it) plus a new `wiremock` dev-dependency this repo has never needed for
  any of the other three providers. Rather than adding test tooling used nowhere else in the
  codebase, Tasks 1.3.4f/2.1.2b now scope down to what's actually testable without network I/O —
  direct calls to `translate_*`/`classify_gemini_error`/`GeminiToAnthropicStream` against fixture
  `Value`s (already covered as unit tests below) plus a `Router`-level test using a fake `Provider`
  (the `router.rs` pattern already used at `src/routing/router.rs:403,430,882`) for the "does it
  flow through `Router::dispatch` correctly" question. A true wire-level HTTP integration test is
  explicitly deferred as out of scope for this appetite (Task 1.3.4h covers the one real manual
  smoke-test call instead). The rows below reflect this decision directly — "Unit — pure-function
  fixture test, matching existing provider test convention," not "Integration — new tooling
  required."
- Async tests follow the existing `#[tokio::test]` convention; sync tests use `#[test]`.

## Test Stack
- **Unit**: `#[test]` / `#[tokio::test]` inline `#[cfg(test)] mod tests` modules co-located with the
  code under test, matching existing convention in `anthropic.rs`/`openai.rs`/`bedrock.rs`/
  `dashboard.rs`/`router.rs`/`errors.rs`/`counters.rs`. Pure-function translation/classification/
  sanitization logic (`translate_*`, `classify_gemini_error`, `sanitize_function_schema`,
  `map_gemini_finish_reason`) is tested by direct function calls with fixture `Value`s — no network.
- **Integration**: (a) `Router`-level tests using fake `Provider` implementations (existing pattern
  at `src/routing/router.rs:403,430,882`) for dispatch/cooldown/blast-radius behavior; (b) full
  config-file-load tests via `tests/fixtures/toml_parity/` for schema/example-file parsing; (c)
  subprocess tests invoking `antigravity-token-auth.py` directly (`std::process::Command`) for the
  auth-helper CLI contract; (d) `/metrics`/`/dashboard` HTTP-handler tests for cross-cutting JSON
  shape assertions. Two tests (`send_should_return_anthropic_shaped_full_response_when_upstream_returns_stop_finish_reason`,
  `send_should_use_stream_client_and_stream_generate_content_endpoint_when_stream_true`) were
  originally scoped as requiring a local mock HTTP listener (e.g. `wiremock`) not currently in this
  repo's dev-dependencies; **resolved 2026-09-04** (Test Stack Notes above) by rescoping both to
  pure-function/fixture tests against `send()`'s post-parse and request-construction logic — no new
  dev-dependency needed, matching this repo's existing provider-test convention. The one true
  wire-level HTTP call these tests would otherwise cover is verified manually instead (plan.md Task
  1.3.4h), not silently skipped.
- **E2E / UX**: Manual, single-operator verification against the running dashboard/logs/config per
  `design/ux.md` — this is a local tool with no browser-automation harness in the repo today, and
  the UX doc itself frames these as "testable by Tyler looking at the running dashboard/logs/
  config," not unit assertions. Wherever a criterion is actually just a static-string/JSON-shape
  check (cold start, hardcoded-name guard, label text, non-contaminated cooldowns object), this plan
  substitutes a Rust integration test instead, per the task brief's guidance, and says so explicitly
  in the table above rather than leaving it ambiguously "manual."
