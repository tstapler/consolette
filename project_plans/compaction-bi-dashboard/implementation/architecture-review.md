# Architecture Review: compaction-bi-dashboard

**Date**: 2026-08-19 (re-review after Phase 3 repair loop)
**Verdict**: CONCERNS

## Resolved

- [x] **Former Blocker — `CostServerState::build()` / `build_session_bi_snapshot` coupled to `HOME`-rooted `discover_sessions`.** Confirmed resolved. The current plan (Task 2.1.3b, Domain Glossary's `build_session_bi_snapshot`/`spawn_session_bi_refresh_task`/reused-`discover_sessions_glob` entries) has `build_session_bi_snapshot(session_glob: &str, ...)` and `spawn_session_bi_refresh_task(..., session_glob: String, ...)` take the glob as a genuine explicit function parameter and call `discovery::discover_sessions_glob` (`src/claude_code_session/discovery.rs:70`, verified by direct read — takes `pattern: &str`, does no env reads) — never `discovery::discover_sessions` (`discovery.rs:55-61`, verified by direct read — still reads `HOME` internally with no injectable parameter, unchanged from the prior review). `CostServerState` (Task 3.1.1b) is split into `build_with_session_glob(session_glob: &str) -> Self`, which does the real construction and is what new tests (Task 3.1.1b's own acceptance criterion, Task 3.3.1c could but does not use it — see Concerns) call directly with a fixture glob, and a thin `pub async fn build() -> Self` that computes `"{$HOME}/.claude/projects/**/*.jsonl"` once and delegates. Verified against current source (`src/cost_metrics/server.rs:68-96`): `build()`'s signature today is exactly `pub async fn build() -> Self`, matching the plan's premise that it is unchanged, and the pre-existing test `serve_cost_should_expose_apply_result_via_http_route_when_pipeline_and_route_share_same_tracker` at `server.rs:203-206` (line numbers confirmed exact) calls `CostServerState::build().await` with no `HOME` scoping — so it needs zero code changes under the new plan. No task or Domain Glossary entry anywhere in the plan calls `std::env::set_var("HOME", ...)`; the global-env-var test race is genuinely eliminated, not just relocated.

## New Concern Introduced By The Fix (Minor)

- [ ] **The fix does not fully eliminate the "existing test's behavior/timing silently changes" effect the original blocker raised — the plan acknowledges this explicitly rather than resolving it.** The prior blocker's remediation text claimed threading an explicit glob "removes any need to mutate `HOME` in tests, fixes both (a) and (b)" — but effect (a) (a pre-existing regression test starts performing a real, unscoped, potentially-thousands-of-files scan of the operator's actual `~/.claude/projects` tree on every `cargo test` run, with no code change to that test) is only partly addressed. The env-var-race half of (a) is gone, but because `build()`'s signature and behavior are intentionally preserved unchanged, `build()` now *unconditionally* delegates to `build_with_session_glob` and performs the real eager `$HOME`-rooted scan (Task 3.1.1b's own acceptance criterion says as much: "it now transitively performs one real `$HOME`-rooted scan ... exactly as `serve_cost`'s own production call site already would"). So `serve_cost_should_expose_apply_result_via_http_route_when_pipeline_and_route_share_same_tracker` (`server.rs:203-206`) — and the new Task 3.3.1c integration test, which also calls `CostServerState::build()` rather than `build_with_session_glob` — will each do a full real-filesystem scan (bounded concurrency 16, up to 5s/file timeout per Task 2.1.3a) as a side effect of running `cargo test`, on whatever machine runs it. This is not a correctness bug and the plan is transparent about accepting it as intentional (mirroring the identical behavior `serve_cost`'s real production call site already has), so it does not block — but it is a genuine, only partially-resolved instance of the original hermeticity complaint: test runtime and outcome now vary with the operator's real home directory contents rather than being a fixed, fast, deterministic unit test. Worth a one-line note in the plan (or a follow-up task) rather than silent acceptance, and worth confirming CI runners have a sane (ideally near-empty) `$HOME/.claude/projects` so these two tests stay fast.
- No other new architecture problem was introduced by the fix: the `session_glob` parameter's type and name are consistent everywhere it's threaded (Domain Glossary, Task 2.1.3b, Task 2.2.1a, Task 3.1.1b), no task or glossary entry references the old `discover_sessions` call site as still-current, and the `build()`/`build_with_session_glob()` split is unambiguous about which one does real work and which is the thin wrapper — a later implementer has a single, clear place (`build_with_session_glob`) to put the actual logic and cannot accidentally duplicate it in `build()`.

## Concerns (carried over, unaffected by the fix)

- [ ] **Task 3.1.1a (`CostServerState` struct)** — `CostServerState` is accumulating a second, only loosely related responsibility (a periodic full-corpus BI aggregation cache) alongside its original live per-request cost-tracking-pipeline role. This mirrors the existing `_pricing_refresh` field pattern so it's consistent with precedent, but is worth flagging as SRP erosion before a third such concern lands on the same struct. Consider a small `SessionBiState { rx, _refresh }` sub-struct composed into `CostServerState` rather than flattening both concerns' fields at the top level.
- [ ] **Task 3.1.2b (`handler_dashboard_sessions`)** — the plan specifies building the JSON response body ad hoc (an inline object literal: `{ generated_at, rows, parse_failure_count, confidence_legend: {...} }`) rather than via a named `#[derive(Serialize)]` response struct. Per this repo's own CLAUDE.md ("keep transport code thin") and type-driven design's parse/produce-via-named-type principle, the handler should serialize a concrete `DashboardSessionsResponse` type. This also gives the `confidence_legend`'s string keys compiler-checked correspondence to `SessionComparisonRow`'s actual field names instead of free-standing literals (see Nitpicks).

## Nitpicks (carried over, unaffected by the fix)

- `confidence_legend`'s string keys (Task 3.1.2b) are hand-written literals with no mechanism enforcing they match `SessionComparisonRow`'s serialized field names; the stated acceptance criterion only spot-checks one key (`native_tokens_saved == "native_reported"`). A field rename on either side wouldn't be caught by the compiler or by the described test. Consider generating the legend from a shared `const` array of `(field_name, Confidence)` pairs, or add a test asserting all four keys are present and correct.
- `SessionComparisonError.reason: String` (Story 2.1.1) is an unstructured error message rather than a typed enum (`ParseError`/`Timeout`/`ScanError`). Low priority today since only an aggregate `parse_failure_count` is surfaced to the dashboard (Task 3.1.2b); revisit if the UI ever needs to distinguish failure categories.
- `native_tokens_saved`/`consolette_tokens_saved: Option<i64>` (Story 2.1.1/2.1.2) is, in miniature, the same "two independent optional values" shape the plan explicitly rejected when choosing a `CompactionStatus` sum type over "two loose booleans." This is acceptable here since the two fields carry magnitude (not just presence, which `CompactionStatus::from_flags` already models separately on the same struct) — but a one-line doc comment noting the two are intentionally independent of, not redundant with, `status` would help future readers.
