# Pitfalls: webui-trace-model-mapping

Labels: VERIFIED = source opened this session; INFERRED = reasoned, not run. Nothing here was executed against a live server; the wire mismatch is confirmed by reading the serializer and the unit test, not by capturing a real SSE frame (do that first in planning).

## Ranked pitfalls (likelihood x impact)

### 1. SSE field-name mismatch is real, and the existing test pins snake_case (HIGH x HIGH) - VERIFIED by source
- `RequestTraceData` (`src/entrypoint/events.rs:27-38`) has no `rename_all`; the enum is `#[serde(tag = "type", content = "data")]` (`events.rs:~58`). Frames are `{"type":"RequestTrace","data":{"request_id":...,"duration_ms":...,"first_byte_ms":...,"compressed":...,"status_code":200}}`.
- The in-file test `request_trace_event_serialization` asserts `"request_id":"req_123"` (`events.rs`, tests module). Adding `rename_all = "camelCase"` breaks that test and any external consumer.
- UI reads camelCase (`ui/src/app/core/models/telemetry.models.ts:14` `requestId?`), plus `compressionStatus`, which the backend never sends.
- Other consumers: grep found no in-repo consumer of `/v1/dashboard/events` other than the Angular `sse.service.ts` (route registered at `src/entrypoint/mod.rs:280`, one router test at `mod.rs:742`). The legacy `/dashboard` in `src/dashboard.rs:540-546` uses polled `/metrics` JSON (`r.request_id`, `r.duration_ms`, snake_case), not SSE. MCP servers: none found in `src` (INFERRED from grep; external clients can't be ruled out).
- Note `observability.rs:54,159` already uses `camelCase` for its own structs, so the repo has no single convention.
- Mitigation: do not rename the Rust struct. Either (a) add a UI-side adapter that maps snake_case to the view model in one place (`sse.service.ts` or a mapper), or (b) emit both via `#[serde(alias)]`-free duplication only if a non-UI consumer shows up. Prefer (a): zero wire-compat risk. Add a contract test: serialize `RequestTraceData` in Rust, check in the JSON fixture, and parse the same fixture in a UI spec so drift fails CI on either side.
- Also: the SSE handler silently does `unwrap_or_default()` on serialization failure (`events.rs:~74`), sending an empty `data:` frame. Any new field with a non-serializable type (e.g. a map with non-string keys) produces blank events, not an error. Mitigation: unit-test serialization of every new field.

### 2. status_code hardcoded 200 and traces only emitted on success (HIGH x HIGH) - VERIFIED
- Hardcoded at `src/metrics/mod.rs:292`. The only call site of `update_request_timing` is `record_first_attempt_timing` (`src/routing/router/mod.rs:1082`), invoked solely in the `Ok(response)` arm (`router/mod.rs:~754`).
- Consequence: validation/auth errors (`return Err(e)`), exhausted pools (`Err(ProviderError::Exhausted)` at the end of the loop), rate-limit holds and 5xx all return without any `RequestTrace`. Failed requests do not appear in the trace table at all; the "status" column cannot show a failure just by swapping 200 for a real code.
- Also `first_byte_ms` is set equal to `duration_ms` (`router/mod.rs:1088`), so TTFT is a proxy equal to time-to-headers, and for streams `duration_ms` is time-to-headers, not total. Showing it as "TTFT/Duration" is misleading.
- `Upstream { status, body }` can carry `status: 0` (Bedrock, `bedrock.rs:~912`) and Anthropic wraps non-HTTP errors as upstream errors (`anthropic.rs:~403`), so a naive `status_code = status` gives 0 for network errors.
- Mitigation: emit a terminal trace from one place that wraps `dispatch` (success or error), with `status_code: Option<u16>` mapped from `ProviderError` (Exhausted -> 503, RateLimited -> 429, Timeout -> 504, Auth -> 401/403, Validation(_, s) -> s, Upstream{status:0} -> 502). Keep one terminal event per request (id-keyed) so the UI upserts rather than appends.

### 3. Per-attempt data: last-attempt-wins and eviction races (MED-HIGH x HIGH) - VERIFIED
- `set_selected_model` / `set_selected_model_was_exploration` / `update_request_timing` overwrite in place (`metrics/mod.rs:~311`; doc comment states "last attempt wins across retries"). `record_selection` runs per loop iteration (`router/mod.rs:720`), including Shed/rate-limited iterations that `continue` before any send. The "attempt chain" the UI needs does not exist anywhere today; it must be new state, not a read of existing fields.
- Ring buffer: `push_request` pops the back at len 100 (`metrics/mod.rs:248`); `original_bodies`/`compressed_bodies` are evicted in lockstep (`:187-193`). `mutate_request` is a silent no-op after eviction (`:254-258`) - under >100 in-flight or a long stream, late attempt records are dropped without a log.
- Lookup is a linear scan under one `Mutex` (`find(...)` in `mutate_request`); adding per-attempt `Vec` pushes adds lock hold time on the hot path (NFR: no measurable slowdown).
- Mitigation: add `attempts: Vec<AttemptRecord>` to `RequestDetail` with a hard cap (e.g. 8 attempts, drop-oldest + a `truncated` flag); append only small POD fields (provider, model, status, ms, reason enum) - no bodies. Record the attempt inside `record_dispatch_outcome` (`router/mod.rs:~1049`), which already runs once per real send, and separately for Shed. Count and log (`warn!`, structured) when `mutate_request` misses, to satisfy the "trace-emission drops" observability requirement. Decide explicitly that history beyond 100 is out of scope, or the UI will look "empty after a burst".
- "Requested model": the original client `model` is in `body["model"]` before dispatch rewrites it (`router/mod.rs:~735` `b["model"] = ...`), and alias/family resolution happens in `candidates`. Capture it at `push_request` time, before any mutation; capturing later returns the routed model (INFERRED from the clone-then-overwrite flow).

### 4. Secret and prompt leakage (MED x HIGH) - partly VERIFIED
- `ProviderError::Upstream { body }` and `Auth(String)` display the upstream response body verbatim (`providers/mod.rs:41,49-50`). `/api/models` returns `e.to_string()` inline per upstream (`entrypoint/api.rs:~79`), and `config_load_error`/`build_providers` errors are echoed too. Upstream error bodies from some APIs echo the request (Gemini includes the key in URLs in some client errors; reqwest errors include the URL with query string) - INFERRED, not demonstrated.
- Bedrock errors use `e.to_string()` of the AWS SDK (`bedrock.rs:~912`), which can include ARNs/account IDs.
- Traces: `RequestDetail` also stores bodies via `push_original_body`; do not copy them into the trace event. SSE has no auth (Out of Scope: dashboard auth), so any LAN peer on the bind address reads whatever goes into events.
- Mitigation: for both traces and model-list errors, send a classified error (`kind`, `status`, short fixed message) rather than `to_string()`; truncate to ~200 chars and strip URL query strings and `Bearer ...`/`sk-...`/`AIza...` patterns; log the full error server-side only at debug. Add a test with a fake upstream whose error body contains a sentinel secret and assert it never appears in `/api/models` or an SSE frame.

### 5. `/api/models` is not a refresh/cache design (HIGH x MED) - VERIFIED
- Handler (`src/entrypoint/api.rs:54-90`) reloads config from disk and rebuilds every provider (`build_providers`) on each call, then calls `list_models()` sequentially for each. Consequences: (a) every UI poll/page load hits all upstreams and triggers Bedrock/AWS config loading; (b) one slow/hung upstream blocks the whole response (no per-upstream timeout seen in the handler; provider client timeouts are request-level, `openai/mod.rs:76-104`); (c) rate limits and cost land on real keys; (d) no `last_refreshed`/age, and errors are untyped `{ "error": string }` objects in the same slot as the success array, so the UI must type-sniff arrays vs objects.
- Provider differences (VERIFIED existence, details INFERRED): Anthropic `GET /v1/models` returns `data[].id` (`anthropic.rs:574`); Bedrock needs control-plane `ListFoundationModels`, a second IAM permission (`bedrock:ListFoundationModels`) the data-plane role may lack, region-scoped, and returns base model IDs, not the inference-profile IDs (`us.anthropic...`) actually routed (`bedrock.rs:904`) - so "advertised" will not match "routable"; Gemini and OpenRouter have their own `list_models` (`gemini/mod.rs:497`, `openrouter/mod.rs:656`) with different shapes (OpenRouter returns hundreds of models; Gemini ids carry a `models/` prefix - check). Models Consolette routes via aliases/families will not appear verbatim.
- Local discovery (`providers/local_discovery.rs`) is a separate path: 500 ms scan timeout, 15 s interval, capped/sanitized ids (`normalize_models`), ids exposed as prefixed `LocalCatalog::model_ids`. It is not in `/api/models`; a unified UI list must merge two sources with different freshness and a "backend appeared/disappeared" state (backend removed when scan fails: `set(backend, None)`).
- Mitigation: add a background cached catalog (like `run_local_discovery`): refresh on a timer (e.g. 5-10 min) and on-demand with a min-interval, per-upstream timeout (e.g. 5 s) with `tokio::join!`/`JoinSet`, store `{models, fetched_at, error_kind}` per upstream, serve from cache; return a typed envelope `{ upstream: { status: "ok"|"error"|"unsupported", models, fetchedAt, error } }`. Keep the current shape working for the Config Editor (INFERRED: it consumes it; verify in `ui/src/app/features/config`) or version the new endpoint (`/api/models/catalog`).
- Cap the list size sent to the UI (OpenRouter) and paginate/filter client-side.

### 6. Angular/SSE pitfalls (MED x MED) - mostly INFERRED
- `sse.service.ts` registers both `onmessage` AND `addEventListener` for named types (`:~60-75`). The server sends `event: "message"` for every dashboard event (`events.rs:~75`), so `onmessage` fires; the named listeners ('MetricsTick', 'RequestTrace', ...) never fire for server events (the type is inside the JSON, not the SSE event name) - benign today, but adding a named SSE event would double-emit. Keep one path.
- `system_lag` is a named SSE event with `{skipped}` and no `type` wrapper (`events.rs:~81`); only the named listener catches it. Do not remove the listeners as "dead code".
- Broadcast channel capacity is 1024 (`entrypoint/mod.rs:164`); a stalled browser tab causes `Lagged` and dropped trace events. If the UI appends only on events, missed terminal events leave rows with no duration forever. Mitigation: on reconnect/`system_lag`, refetch recent traces from `/requests` or the metrics snapshot (`get_recent_requests`, capped at 100), and upsert by `request_id`.
- Because the trace is emitted at completion (see #2), a row appears only at the end; in-flight requests are invisible. If an "in progress" state is wanted it needs a start event - scope decision.
- Unbounded arrays: not confirmed (grep for the trace list container came back empty; locate the component, `recent-trace-table.component.ts`). Cap in the client to the same 100 and use `@for (...; track t.requestId)` (not `$index`), since rows get upserted.
- `EventSource` auto-reconnects natively AND the service also reconnects manually with backoff (`maxRetryAttempts = 20`); after 20 failures it gives up permanently with no user-visible retry. Native `Last-Event-ID` isn't used (no `id:` sent), so events during the gap are lost - hence the refetch above.
- Mitigation for change detection: use signals (already used in the service) and `ChangeDetectionStrategy.OnPush`; batch updates (coalesce to animation frame) to hold the <100 ms SLO under bursts.

### 7. Build/embedding staleness (MED x MED) - VERIFIED from `build.rs`
- `build.rs` rebuilds when any `UI_INPUTS` file mtime is newer than `ui/dist/consolette/browser/index.html`, if `CONSOLETTE_SKIP_UI` is unset. On failure without `CONSOLETTE_REQUIRE_UI` it only prints `cargo:warning` and keeps the old bundle or writes a placeholder: a TypeScript error silently ships the previous UI while Rust changes compile. Only CI sets `REQUIRE_UI` (`.github/workflows/ci.yml:16`); local `cargo run` does not.
- `rerun-if-changed` is on directories (`ui/src`) and the dist dir; cargo scans directory mtimes recursively, which is fine, but edits made while `CONSOLETTE_SKIP_UI=1` (editor setups) leave a stale bundle that later looks fresh only if `ng build` touches `index.html`.
- Rust-side struct changes do not trigger a UI rebuild and vice versa; a backend/UI contract change can be half-deployed in a dev loop (UI expects new fields from an old binary).
- Mitigation: during this work run with `CONSOLETTE_REQUIRE_UI=1`; verify with `curl localhost:<port>/dashboard/` that the served `main-*.js` hash changed; the contract test in #1 catches drift. Also `rust-embed` in debug may read from disk, not embed (INFERRED, check `src/dashboard.rs`) - confirm the same behavior as release before trusting a manual check.

### 8. Redundant/legacy surfaces drift (LOW-MED x LOW) - VERIFIED existence
- Legacy `src/dashboard.rs` (inline JS, polled `/metrics`) and `src/context_forensics/dashboard.html` are separate consumers of different data; new fields in `RequestDetail` appear in the legacy JSON automatically (snake_case, via `observability.rs`/`metrics`), which is additive and safe. But changing `RequestDetail`'s serialized shape (renames) breaks legacy `r.request_id`/`r.duration_ms` reads (`dashboard.rs:540-546`). Rule: additive only on `RequestDetail`; put new shapes on the trace event/new endpoints.
- `r.request_id`/`r.model` are concatenated into an inline `onclick` string in the legacy dashboard (`dashboard.rs:541`); a client-controlled `model` string containing a quote is an XSS vector once requested-model (client-supplied) is added to those rows. Escape or leave out of legacy rendering (INFERRED; model is currently also client-influenced via body).
